### Question 1 – KMS key policy - IAM delegation

Later, developers whose IAM identity-based policies allow kms:Encrypt and kms:Decrypt on the key's ARN receive AccessDeniedException errors. The security team wants to keep managing day-to-day key access through IAM policies. What should the security engineer do?

```json
{
```

- **B.** Create a KMS grant for each developer role with the Encrypt and Decrypt operations.
- **C.** Attach the AWSKeyManagementServicePowerUser managed policy to the developers' IAM roles.
- **D.** Add an aws:PrincipalAccount condition to the developers' IAM policies that matches 111122223333.

<details>
<summary>Show answer and explanation</summary>

**Answer: A**

✅ **A.** Add a statement to the key policy that allows the account principal arn:aws:iam::111122223333:root to perform kms:\* so that IAM policies in the account can grant access to the key.

A KMS key policy statement that allows the account principal (arn:aws:iam::111122223333:root) delegates authority to IAM, so the developers' existing kms:Encrypt and kms:Decrypt identity-based allows start working immediately. This restores the default-key-policy behavior and keeps day-to-day access management in IAM, exactly as the team wants.

**Summary:** KMS key policies are the primary authority for a key; IAM policies are only effective when the key policy delegates to the account by allowing the account root principal. More IAM permissions do not help because the key policy does not delegate authority to IAM, so IAM allows are ignored.

### Question 2 – KMS encryption context condition

A SaaS provider stores documents for many tenants in a shared Amazon S3 bucket. The application encrypts each document with a single customer managed KMS key by calling the AWS Encryption SDK and includes the encryption context {"tenant": "&lt;tenant-id&gt;"}. Each tenant's workers assume an IAM role session tagged with a tenant principal tag. The company must ensure that a worker can decrypt only its own tenant's data without creating one KMS key per tenant. Which key policy condition meets this requirement?

- **A.** `"Condition": {"StringEquals": {"kms:ViaService": "s3.us-east-1.amazonaws.com"}}`
- **B.** `"Condition": {"StringEquals": {"kms:EncryptionContext:tenant": "${aws:PrincipalTag/tenant}"}}`
- **C.** `"Condition": {"Bool": {"kms:GrantIsForAWSResource": "true"}}`
- **D.** `"Condition": {"StringEquals": {"aws:ResourceTag/tenant": "${aws:PrincipalTag/tenant}"}}`

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** `"Condition": {"StringEquals": {"kms:EncryptionContext:tenant": "${aws:PrincipalTag/tenant}"}}`

The kms:EncryptionContext:tenant condition checks the tenant value in each Decrypt request, and the ${aws:PrincipalTag/tenant} variable resolves to the caller's session tag, so a worker can only decrypt ciphertext bound to its own tenant ID. Because decryption requires the exact encryption context used at encryption time, one shared key still enforces per-tenant isolation.

**Summary:** The kms:EncryptionContext:&lt;key&gt; condition compares the encryption context in the Decrypt request with a value, and policy variables such as ${aws:PrincipalTag/tenant} make the comparison session-specific. Because the ciphertext cannot be decrypted without the exact encryption context used at encryption, a worker can only decrypt data bound to its own tenant ID while all tenants share one key.

❌ **A.** `"Condition": {"StringEquals": {"kms:ViaService": "s3.us-east-1.amazonaws.com"}}`

kms:ViaService limits which AWS service can call KMS but does not separate tenants, and the Encryption SDK calls KMS directly rather than through S3.

❌ **C.** `"Condition": {"Bool": {"kms:GrantIsForAWSResource": "true"}}`

kms:GrantIsForAWSResource controls grant creation by integrated services and has no relationship to tenant data separation.

❌ **D.** `"Condition": {"StringEquals": {"aws:ResourceTag/tenant": "${aws:PrincipalTag/tenant}"}}`

There is only one key, so a resource tag on the key would be identical for every tenant and cannot distinguish tenant data.

</details>

### Question 3 – KMS multi-Region keys

A payments company encrypts card tokens in its application tier by using client-side encryption with an AWS KMS key in us-east-1. The encrypted tokens are written to an Amazon DynamoDB global table that replicates to eu-west-1. During a Regional outage, the eu-west-1 application must decrypt the replicated tokens without making any cross-Region call to us-east-1 and without re-encrypting the data. Which solution meets these requirements?

- **A.** Create a new single-Region KMS key in eu-west-1 and import the same key material that AWS KMS generated in us-east-1.
- **B.** Grant the eu-west-1 application role kms:Decrypt on the us-east-1 key and configure a VPC endpoint for AWS KMS in eu-west-1.
- **C.** Create a multi-Region primary key in us-east-1, replicate it to eu-west-1, and use the replica key in eu-west-1 to decrypt the ciphertext.
- **D.** Enable DynamoDB encryption at rest with the AWS managed key aws/dynamodb in both Regions.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Create a multi-Region primary key in us-east-1, replicate it to eu-west-1, and use the replica key in eu-west-1 to decrypt the ciphertext.

A multi-Region replica shares the same key ID and key material as the us-east-1 primary, so the eu-west-1 application can decrypt the replicated client-side ciphertext by calling KMS locally in eu-west-1. No cross-Region call is needed during the outage and the data does not have to be re-encrypted.

**Summary:** Multi-Region keys share the same key ID and key material across Regions, so ciphertext produced by the primary key can be decrypted by the replica key locally in another Region. Using the replica in eu-west-1 avoids any dependency on us-east-1 during an outage and requires no re-encryption.

❌ **A.** Create a new single-Region KMS key in eu-west-1 and import the same key material that AWS KMS generated in us-east-1.

Key material generated by AWS KMS cannot be exported, so it cannot be imported into another key.

❌ **B.** Grant the eu-west-1 application role kms:Decrypt on the us-east-1 key and configure a VPC endpoint for AWS KMS in eu-west-1.

Calling the us-east-1 key is a cross-Region dependency that fails during the us-east-1 outage, and a KMS endpoint in eu-west-1 cannot reach a us-east-1 key.

❌ **D.** Enable DynamoDB encryption at rest with the AWS managed key aws/dynamodb in both Regions.

Table-level encryption at rest does not decrypt application-level client-side ciphertext produced with the us-east-1 key.

</details>

### Question 4 – KMS automatic and on-demand rotation

A healthcare company's policy requires that AWS KMS-generated key material for its customer managed symmetric encryption keys rotate every 180 days. The policy also requires the ability to rotate key material immediately after a suspected exposure, without changing key IDs referenced by applications or re-encrypting existing data. Which solution meets these requirements with the LEAST operational overhead?

- **A.** Import new key material into each key every 180 days and delete the previous key material.
- **B.** Create a new KMS key every 180 days with an AWS Lambda function and update the alias to point to the new key.
- **C.** Enable automatic key rotation with the default period and schedule an Amazon EventBridge rule to call the RotateKeyOnDemand API every 180 days.
- **D.** Enable automatic key rotation with a rotation period of 180 days, and use on-demand key rotation when an immediate rotation is required.

<details>
<summary>Show answer and explanation</summary>

**Answer: D**

✅ **D.** Enable automatic key rotation with a rotation period of 180 days, and use on-demand key rotation when an immediate rotation is required.

AWS KMS natively supports a custom automatic rotation period (90 to 2,560 days), so setting it to 180 days meets the policy with no custom code. On-demand rotation handles suspected exposure immediately, and both keep the same key ID and ARN while retaining older key material so existing ciphertext still decrypts.

**Summary:** AWS KMS supports a custom automatic rotation period between 90 and 2,560 days (default 365) and on-demand rotation (RotateKeyOnDemand, up to 25 times per key) that does not change the automatic schedule. Rotation keeps the same key ID and ARN, and KMS retains prior key material to decrypt existing ciphertext, so applications and data are unaffected.

❌ **A.** Import new key material into each key every 180 days and delete the previous key material.

These keys have AWS KMS-generated (AWS_KMS origin) key material, so new material cannot be imported into them, and deleting prior key material would make existing ciphertext undecryptable.

❌ **B.** Create a new KMS key every 180 days with an AWS Lambda function and update the alias to point to the new key.

Alias-based manual rotation works but adds custom automation and leaves multiple keys to manage, which is more overhead than native rotation.

❌ **C.** Enable automatic key rotation with the default period and schedule an Amazon EventBridge rule to call the RotateKeyOnDemand API every 180 days.

The default period is 365 days, so this layers custom scheduling on top of native rotation when the period can be set directly to 180 days; on-demand rotation is also limited to 25 rotations per key.

</details>

### Question 5 – KMS imported key material expiration

A bank uses an AWS KMS key with imported key material (origin EXTERNAL) and set an expiration date on the key material. The key material expired over the weekend, and applications now fail to decrypt data that was encrypted under the key. The bank retains an escrowed copy of the original key material in its on-premises HSM. How can the security engineer restore decryption with the existing ciphertext?

- **A.** Download a new wrapping public key and import token for the same KMS key, then reimport the same key material that was originally imported.
- **B.** Cancel the key deletion from the AWS KMS console to restore the key to the Enabled state.
- **C.** Create a new KMS key with AWS KMS-generated key material and update the alias to point to it.
- **D.** Enable automatic key rotation on the KMS key so that AWS KMS generates new key material.

<details>
<summary>Show answer and explanation</summary>

**Answer: A**

✅ **A.** Download a new wrapping public key and import token for the same KMS key, then reimport the same key material that was originally imported.

Expired imported key material leaves the KMS key in the PendingImport state, and only the exact same key material can decrypt ciphertext previously produced by that key. Downloading a fresh wrapping key and import token and reimporting the escrowed material restores the key to Enabled without changing the key ID or re-encrypting anything.

**Summary:** When imported key material expires, AWS KMS deletes it and the key enters the PendingImport state; the key itself is not deleted. Reimporting the exact same key material into the same KMS key, using a new import token, restores the ability to decrypt existing ciphertext.

❌ **B.** Cancel the key deletion from the AWS KMS console to restore the key to the Enabled state.

The key was not scheduled for deletion; it is in the PendingImport state, so there is no deletion to cancel.

❌ **C.** Create a new KMS key with AWS KMS-generated key material and update the alias to point to it.

A new key with different key material cannot decrypt ciphertext produced by the original key.

❌ **D.** Enable automatic key rotation on the KMS key so that AWS KMS generates new key material.

Automatic rotation is not supported for keys with imported key material, and new material could not decrypt old ciphertext anyway.

</details>

### Question 6 – KMS disable key during incident

A security team discovers that an attacker may have obtained credentials for an application role that can call kms:Decrypt on a customer managed key protecting a data lake. The team needs to immediately stop all cryptographic use of the key while it investigates, but it must be able to fully restore service within minutes if the key is found to be safe. Which action is the MOST appropriate containment step?

- **A.** Schedule the key for deletion with a 7-day waiting period.
- **B.** Disable the KMS key.
- **C.** Delete the key alias used by the application.
- **D.** Enable automatic rotation on the KMS key.

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** Disable the KMS key.

Disabling a KMS key immediately makes every cryptographic operation with it fail, which stops the possibly compromised role from decrypting data lake content. It is fully reversible with EnableKey in seconds and never touches the key material, so service can be restored within minutes if the key is cleared.

**Summary:** Disabling a KMS key immediately blocks all cryptographic operations that use it, and the key can be re-enabled at any time with no loss of key material. This provides an instant, fully reversible containment action.

❌ **A.** Schedule the key for deletion with a 7-day waiting period.

Scheduling deletion also blocks use and can be canceled during the waiting period, but it starts a countdown to irreversible destruction of the key material and needs a cancel plus re-enable to restore service, which adds unnecessary risk for temporary containment.

❌ **C.** Delete the key alias used by the application.

Callers could still use the key ID or ARN directly, so deleting an alias does not block cryptographic use.

❌ **D.** Enable automatic rotation on the KMS key.

Rotation does not revoke access; previous key material is retained and the compromised role could still decrypt data.

</details>

### Question 7 – KMS HMAC keys

A gaming company issues session tokens to clients and must be able to verify that tokens were not tampered with. Currently, the backend signs tokens with a shared secret that is stored in an environment variable on every server. The security team requires that the secret key never be exposed in plaintext to application code and that every verification be logged in AWS CloudTrail. Which solution meets these requirements?

- **A.** Store the shared secret in AWS Secrets Manager and retrieve it at startup to compute HMACs locally.
- **B.** Create a symmetric encryption KMS key and use the Encrypt API to produce a token signature.
- **C.** Create an HMAC KMS key with key usage GENERATE_VERIFY_MAC and use the GenerateMac and VerifyMac APIs.
- **D.** Use AWS Certificate Manager to issue a certificate and sign tokens with its private key.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Create an HMAC KMS key with key usage GENERATE_VERIFY_MAC and use the GenerateMac and VerifyMac APIs.

An HMAC KMS key with GENERATE_VERIFY_MAC usage computes and verifies MACs inside AWS KMS, so the secret key material is never exposed in plaintext to the application. Every GenerateMac and VerifyMac request is an AWS KMS API call recorded in CloudTrail, which satisfies the audit requirement.

**Summary:** HMAC KMS keys perform message authentication inside AWS KMS, so the key material never leaves the service in plaintext. GenerateMac and VerifyMac calls are recorded in CloudTrail, which satisfies both the key-protection and auditing requirements.

❌ **A.** Store the shared secret in AWS Secrets Manager and retrieve it at startup to compute HMACs locally.

The application would still hold the plaintext secret in memory, and local HMAC computations are not logged in CloudTrail.

❌ **B.** Create a symmetric encryption KMS key and use the Encrypt API to produce a token signature.

Encryption does not provide a verifiable integrity code, and symmetric encryption keys cannot perform MAC operations.

❌ **D.** Use AWS Certificate Manager to issue a certificate and sign tokens with its private key.

ACM does not let applications use certificate private keys for arbitrary signing operations.

</details>

### Question 8 – KMS asymmetric signing keys

An industrial IoT manufacturer must digitally sign firmware images before distributing them to devices in the field. The devices verify signatures offline and have no AWS credentials. The private signing key must never leave FIPS-validated hardware, and each signing operation must be auditable. Which solution meets these requirements?

- **A.** Use an ACM public certificate and export its private key to the build pipeline for signing.
- **B.** Create a symmetric KMS key, compute an HMAC of each image, and have the devices call VerifyMac.
- **C.** Generate an RSA key pair on a build server, store the private key in AWS Secrets Manager, and sign images during the build.
- **D.** Create an asymmetric KMS key with key usage SIGN_VERIFY, sign images with the Sign API, and embed the key's public key (from GetPublicKey) in device firmware for offline verification.

<details>
<summary>Show answer and explanation</summary>

**Answer: D**

✅ **D.** Create an asymmetric KMS key with key usage SIGN_VERIFY, sign images with the Sign API, and embed the key's public key (from GetPublicKey) in device firmware for offline verification.

An asymmetric SIGN_VERIFY KMS key keeps the private key inside FIPS-validated KMS HSMs, and each Sign call is logged in CloudTrail for auditing. The public key from GetPublicKey can be embedded in firmware so devices verify signatures offline without AWS credentials or network access to KMS.

**Summary:** Asymmetric KMS keys keep the private key inside AWS KMS hardware security modules while exposing the public key for download. Devices can verify signatures offline with the public key, and every Sign call is logged in CloudTrail.

❌ **A.** Use an ACM public certificate and export its private key to the build pipeline for signing.

Exporting a private key places it outside hardware protection, and ACM certificates are intended for TLS rather than code signing.

❌ **B.** Create a symmetric KMS key, compute an HMAC of each image, and have the devices call VerifyMac.

VerifyMac requires calling AWS KMS with credentials, which the offline devices do not have, and symmetric encryption keys cannot perform MAC operations (only HMAC keys can).

❌ **C.** Generate an RSA key pair on a build server, store the private key in AWS Secrets Manager, and sign images during the build.

Generating the key on a build server means the private key exists in plaintext outside HSMs, and Secrets Manager only stores it; this violates the requirement that the key never leave FIPS-validated hardware.

</details>

### Question 9 – Envelope encryption and data key caching

A telemetry service encrypts millions of small records per minute by using the AWS Encryption SDK with a customer managed KMS key. The service is receiving ThrottlingException errors from AWS KMS, and KMS request costs are high. The security team accepts reusing a data key for a bounded number of messages and a short time window. Which change resolves the issue with the LEAST effort?

- **A.** Configure data key caching in the AWS Encryption SDK with limits on maximum age and maximum messages per data key.
- **B.** Switch to a multi-Region KMS key and spread requests across two Regions.
- **C.** Encrypt every record directly with the KMS Encrypt API instead of generating data keys.
- **D.** Enable automatic key rotation to increase the request quota for the key.

<details>
<summary>Show answer and explanation</summary>

**Answer: A**

✅ **A.** Configure data key caching in the AWS Encryption SDK with limits on maximum age and maximum messages per data key.

Data key caching in the AWS Encryption SDK reuses each data key for many records, which cuts GenerateDataKey calls to AWS KMS by orders of magnitude and removes the throttling and cost problem. The maximum-age and maximum-messages limits enforce exactly the bounded reuse the security team accepted, and it is a configuration change rather than a redesign.

**Summary:** Data key caching lets the Encryption SDK reuse a data key for a bounded number of messages or time, which sharply reduces GenerateDataKey calls to AWS KMS. This removes throttling and reduces cost while staying within the security team's stated reuse limits.

❌ **B.** Switch to a multi-Region KMS key and spread requests across two Regions.

Splitting traffic across Regions adds architectural complexity and cross-Region dependencies rather than reducing call volume.

❌ **C.** Encrypt every record directly with the KMS Encrypt API instead of generating data keys.

Direct Encrypt calls still require one KMS request per record and are limited to 4 KB of plaintext, so throttling would continue.

❌ **D.** Enable automatic key rotation to increase the request quota for the key.

Enabling rotation only changes key material on a schedule; it does not raise KMS request quotas or reduce GenerateDataKey calls, so the throttling and cost would continue unchanged.

</details>

### Question 10 – Envelope encryption - data key APIs

**Answer: B**

GenerateDataKeyWithoutPlaintext returns only the KMS-encrypted copy of a new data key, so the ingestion component never sees plaintext key material. The processing fleet later calls Decrypt on that encrypted data key when it actually encrypts video, meeting the separation requirement.

### Question 11 – KMS external key store (XKS)

A European bank must keep its root key material in an HSM that it operates in its own data center, outside AWS. The bank wants Amazon S3 and Amazon EBS to use this key through standard AWS KMS integrations, and it wants the ability to block all AWS use of the key by disconnecting its infrastructure. Which statement describes the correct design and its main trade-off?

- **A.** Create KMS keys in an AWS CloudHSM key store; if the bank disconnects its data center, AWS services continue working because CloudHSM caches the key.
- **B.** Create KMS keys with imported key material; the key material remains only in the bank's HSM and is never stored in AWS.
- **C.** Create KMS keys in an external key store connected through an external key store proxy; cryptographic operations fail whenever the external key manager or proxy is unavailable, so the bank owns availability and latency.
- **D.** Use SSE-C for all services; AWS KMS forwards requests to the bank's HSM automatically.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Create KMS keys in an external key store connected through an external key store proxy; cryptographic operations fail whenever the external key manager or proxy is unavailable, so the bank owns availability and latency.

An external key store keeps the root key material in the bank's own HSM outside AWS, while S3, EBS, and other services still use it through normal AWS KMS integration via the XKS proxy. Because every operation goes through the proxy, disconnecting it blocks all AWS use of the key, and the trade-off is that the bank now owns availability and latency.

**Summary:** An external key store (XKS) keeps key material in an external key manager that the customer operates, and AWS KMS sends each encryption and decryption request through the customer's XKS proxy. The customer can cut off access by disconnecting the proxy, but it also becomes responsible for the availability, latency, and durability of every operation.

❌ **A.** Create KMS keys in an AWS CloudHSM key store; if the bank disconnects its data center, AWS services continue working because CloudHSM caches the key.

CloudHSM key stores run inside AWS, not in the bank's data center, so they do not meet the outside-AWS requirement.

❌ **B.** Create KMS keys with imported key material; the key material remains only in the bank's HSM and is never stored in AWS.

Imported key material is stored in AWS KMS HSMs after import, so it does not remain exclusively on premises.

❌ **D.** Use SSE-C for all services; AWS KMS forwards requests to the bank's HSM automatically.

SSE-C is an S3-only feature where the caller supplies the key per request; it does not integrate with EBS or forward requests to an HSM.

</details>

### Question 12 – AWS CloudHSM design

A government contractor is migrating a PKCS#11 application to Amazon EC2. The application requires single-tenant HSMs validated at FIPS 140-3 Level 3, and the contractor must have exclusive control of key material so that AWS personnel cannot access it. The solution must remain available if one Availability Zone fails. Which actions meet these requirements? (Select TWO.)

- **A.** Create an AWS CloudHSM cluster with at least two HSMs in different Availability Zones.
- **B.** Use a customer managed AWS KMS key with a key policy that denies AWS service principals.
- **C.** Initialize the cluster, activate it, and create crypto users (CUs) that the contractor manages to own and use the keys.
- **D.** Ask AWS Support to create the HSM administrator accounts and store their passwords in AWS Secrets Manager.
- **E.** Create one HSM and rely on automatic backups to restore it in another Availability Zone during a failure.

<details>
<summary>Show answer and explanation</summary>

**Answer: A, C**

✅ **A.** Create an AWS CloudHSM cluster with at least two HSMs in different Availability Zones.

An AWS CloudHSM cluster with HSMs in at least two Availability Zones keeps keys synchronized across HSMs, so the PKCS#11 application keeps working if one AZ fails. CloudHSM provides the single-tenant, FIPS 140-3 Level 3 validated HSMs that the requirement specifies.

✅ **C.** Initialize the cluster, activate it, and create crypto users (CUs) that the contractor manages to own and use the keys.

Initializing and activating the cluster yourself and creating the crypto users means only the contractor holds HSM credentials, so AWS personnel cannot access the keys. Crypto users own and use keys through PKCS#11, giving the contractor exclusive control of key material.

**Summary:** AWS CloudHSM provides single-tenant HSMs in the customer's VPC with the current HSM type validated at FIPS 140-3 Level 3, and the customer alone manages HSM users and keys. Placing at least two HSMs in different Availability Zones provides high availability because keys synchronize across the cluster.

❌ **B.** Use a customer managed AWS KMS key with a key policy that denies AWS service principals.

AWS KMS is a multi-tenant service and does not give the PKCS#11 application exclusive control of HSMs.

❌ **D.** Ask AWS Support to create the HSM administrator accounts and store their passwords in AWS Secrets Manager.

AWS has no access to HSM user credentials; the customer creates and manages all HSM users.

❌ **E.** Create one HSM and rely on automatic backups to restore it in another Availability Zone during a failure.

A single HSM is a single point of failure, and restoring from backup causes downtime rather than providing high availability.

</details>

### Question 13 – S3 Bucket Keys

An analytics company stores billions of small objects in Amazon S3 encrypted with SSE-KMS by using a customer managed key. KMS request charges have become significant and the company occasionally hits KMS request quotas. ### Question 40 – KMS key deletion safety

A security engineer must delete a customer managed KMS key that is believed to be unused. Deleting a key in use would make data permanently unrecoverable. Before the key material is destroyed, the engineer wants evidence of whether any workload still depends on the key and a way to recover if one does. Which actions should the engineer take? (Select TWO.)

- **A.** Review AWS CloudTrail events for cryptographic operations that reference the key's ARN over a representative time period.
- **B.** Delete the key immediately with a waiting period of 0 days.
- **C.** Schedule deletion with a waiting period of up to 30 days and create a CloudWatch alarm that fires when CloudTrail records attempts to use the key while it is pending deletion.
- **D.** Remove the key's alias so that applications fail over to a different key.
- **E.** Enable automatic rotation so that new ciphertext uses new key material.

<details>
<summary>Show answer and explanation</summary>

**Answer: A, C**

✅ **A.** Review AWS CloudTrail events for cryptographic operations that reference the key's ARN over a representative time period.

CloudTrail records every cryptographic operation that references the key, so reviewing a representative period shows which principals and services still depend on it. This gives evidence of use before any key material is at risk.

✅ **C.** Schedule deletion with a waiting period of up to 30 days and create a CloudWatch alarm that fires when CloudTrail records attempts to use the key while it is pending deletion.

Scheduling deletion with a waiting period of up to 30 days keeps the key recoverable, because deletion can be canceled at any time during the wait. A CloudWatch alarm on CloudTrail events showing use of the pending-deletion key alerts the engineer to a hidden dependency in time to cancel.

**Summary:** CloudTrail shows past use of the key by principals and services, which indicates dependencies. Scheduling deletion with a waiting period between 7 and 30 days and alarming on attempted use while pending deletion provides a signal to cancel the deletion before the key material is destroyed.

❌ **B.** Delete the key immediately with a waiting period of 0 days.

AWS KMS requires a waiting period of at least 7 days, and immediate deletion removes the recovery window.

❌ **D.** Remove the key's alias so that applications fail over to a different key.

Removing an alias does not reveal dependencies and callers using the key ARN are unaffected.

❌ **E.** Enable automatic rotation so that new ciphertext uses new key material.

Rotation keeps older key material for existing ciphertext and does not reveal which workloads use the key, so it neither identifies dependencies nor makes deletion safe.
