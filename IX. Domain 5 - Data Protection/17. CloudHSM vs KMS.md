# AWS CloudHSM versus AWS KMS

## Overview

This chapter explains AWS CloudHSM versus AWS KMS and the security decision it supports for AWS Certified Security – Specialty (SCS-C03). The focus is protecting confidentiality and integrity while keeping key custody, authorization, availability, and auditability explicit.

Encryption is effective only when key access, data access, network paths, lifecycle controls, and recovery plans are designed together. A denied key operation, disabled key, expired credential, incompatible TLS client, or missing route can each present as an application failure.

## Core Concepts

- AWS KMS is a multi-tenant managed service with broad AWS integrations, policy-based access, high durability, and low operational overhead.
- CloudHSM supplies dedicated single-tenant HSMs and standard cryptographic APIs, but customers manage clusters, users, keys, clients, availability, and backups.
- KMS best fits envelope encryption and AWS service integration; CloudHSM fits direct HSM control, custom algorithms/interfaces supported by CloudHSM, or specific compliance ownership requirements.
- A KMS custom key store combines KMS APIs with customer-owned CloudHSM key material but inherits additional availability, throughput, and cost concerns.

## How It Works

1. Determine whether the requirement is managed AWS service integration or direct use of a dedicated HSM.
2. With KMS, IAM and the KMS key policy authorize service API operations; AWS manages the HSM fleet, durability, and scaling.
3. With CloudHSM, IAM governs cluster management, but HSM users and application libraries govern cryptographic operations.
4. Design CloudHSM clients, multi-AZ capacity, backups, and operational roles when choosing the dedicated service.
5. Compare evidence sources: CloudTrail for management APIs and KMS cryptographic calls, plus CloudHSM audit logs for HSM activity.

Choose KMS for managed integration; CloudHSM for direct dedicated-HSM control. Scope each control to the correct hop and remember that data access and key access are independent authorization questions when a customer managed KMS key is involved.

## Detection, Logging, and Evidence

CloudTrail records KMS requests and the management APIs for both services. CloudHSM cryptographic activity is instead attributable through HSM audit logs. This distinction mirrors the authorization split: IAM and key policies for KMS, versus IAM management plus HSM-user authorization for CloudHSM.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Access denied | Key/data policy, IAM guardrail, grant, or condition does not allow the request | Inspect CloudTrail and evaluate every applicable policy | Add the least-privilege allow or remove the unintended explicit deny |
| Ciphertext cannot be decrypted | Wrong key, Region, algorithm, encryption context, or unavailable key store | Inspect key metadata and the original encryption parameters | Use the matching enabled key and exact authenticated parameters |
| Operation is slow or throttled | Service quota, high KMS call rate, or custom key-store capacity | Review CloudWatch metrics and service quotas | Use envelope encryption, safe caching, Bucket Keys, or capacity changes when appropriate |

## Security Best Practices

- Apply least privilege and separation of duties to AWS CloudHSM, AWS KMS.
- Prefer managed AWS cryptographic integrations unless explicit key custody, portability, or compliance requirements justify more operational burden.
- Keep plaintext keys and secrets out of code, logs, command history, tags, aliases, and encryption context.
- Design recovery before disabling or deleting keys; retained ciphertext is useless without an available authorized key path.
- Monitor administrative changes and repeated failed cryptographic or secret operations.

## Exam Decision Guide

| Requirement or Clue | Most Likely Control | Why |
| --- | --- | --- |
| Directly implement this lesson's control | AWS CloudHSM | It provides the required data-protection capability |
| Customer controls key policy and lifecycle | Customer managed KMS key | It supports customer policy, grants, rotation configuration, disablement, and deletion scheduling |
| Direct, single-tenant HSM control | AWS CloudHSM | Customer manages dedicated HSM users and key operations |
| Automatic secret rotation and version staging | AWS Secrets Manager | It manages secret lifecycle and integrated or Lambda-based rotation |

## Common Exam Traps

- Choose KMS for managed integration; CloudHSM for direct dedicated-HSM control.
- Encryption at rest does not replace encryption in transit, and neither replaces authorization.
- Creating a KMS key does not give its creator unlimited use unless the effective policies allow it.
- A key policy allow cannot override an explicit deny in an applicable guardrail or identity control.
- Key rotation does not re-encrypt existing ciphertext; old key material remains available to decrypt data while the KMS key is enabled.

| Term | Definition | Exam Relevance |

| AWS CloudHSM | The primary AWS control or component discussed in this lesson. | Know its trust boundary, scope, and nearest alternatives. |
| Encryption at rest | Protection applied to stored data and its managed copies. | Does not automatically protect data in transit or from an authorized read. |
| Explicit deny | A matching deny that overrides applicable allows. | Central to IAM and KMS policy troubleshooting. |
