# KMS Encryption Demonstration

## Overview

This chapter explains KMS Encryption Demonstration and the security decision it supports for AWS Certified Security – Specialty (SCS-C03). The focus is protecting confidentiality and integrity while keeping key custody, authorization, availability, and auditability explicit.

Encryption is effective only when key access, data access, network paths, lifecycle controls, and recovery plans are designed together. A denied key operation, disabled key, expired credential, incompatible TLS client, or missing route can each present as an application failure.

## Core Concepts

- Create a symmetric customer managed KMS key with separate administrative and usage permissions, then create a friendly alias.
- Use the AWS CLI to encrypt a small plaintext file and save the binary ciphertext blob without printing sensitive plaintext.
- Decrypt with an authorized principal and verify the recovered content; test denial after removing key-use permission.
- Treat aliases as mutable pointers and use a key ARN or key ID when stable identity is required by a policy or audit process.

## How It Works

1. A principal authenticates and requests a data or cryptographic operation.
2. IAM guardrails, resource or key policy, grants, and conditions determine whether the operation is authorized.
3. The service obtains or uses protected cryptographic material inside the defined trust boundary; plaintext key exposure is minimized.
4. Ciphertext, encrypted data keys, metadata, or secret versions are stored with the protected resource as required.
5. CloudTrail and service logs provide evidence; disabled keys, missing grants, context mismatch, or unavailable key stores cause explicit failure rather than silent decryption.

## Demonstration Goal

Create a customer managed KMS key and alias, prove authorized command-line encryption and decryption, and confirm the expected denial for an unauthorized principal.

## Demonstration Steps

1. Create a symmetric customer managed KMS key with separate administrative and usage permissions, then create a friendly alias.
2. Use the AWS CLI to encrypt a small plaintext file and save the binary ciphertext blob without printing sensitive plaintext.
3. Decrypt with an authorized principal and verify the recovered content; test denial after removing key-use permission.
4. Treat aliases as mutable pointers and use a key ARN or key ID when stable identity is required by a policy or audit process.

```bash
KMS_KEY_ID="replace-with-key-id-or-arn"
aws kms encrypt --key-id "$KMS_KEY_ID" --plaintext fileb://battleplans.txt --output text --query CiphertextBlob | base64 --decode > battleplans.encrypted
aws kms decrypt --ciphertext-blob fileb://battleplans.encrypted --output text --query Plaintext | base64 --decode > battleplans.decrypted
```

### Line-by-Line Comments

```text
Line 1: Stores the selected KMS key identifier in a task-specific variable.
Line 2: Encrypts the small file with KMS and decodes the returned base64 ciphertext into a binary ciphertext blob.
Line 3: Sends the ciphertext blob to KMS, decodes the returned base64 plaintext, and writes the recovered file.
```

### Code Walkthrough

The commands require `kms:Encrypt` and `kms:Decrypt`, plus permission through the key policy. The first command modifies only a local ciphertext file; the second writes a local recovered plaintext file. The KMS operations are billable API calls and appear in CloudTrail where applicable. Do not use direct KMS encryption for large files; use envelope encryption. Delete recovered plaintext securely when the validation is complete.

- Verify no fallback to an unencrypted, publicly exposed, or unauthorized path occurred.

## What the Demonstration Proves

Encrypt with the key, authorize with policy, prove with a decrypt test and CloudTrail. The exercise also proves that successful resource access does not imply successful key use, and successful TLS or routing does not imply application authorization.

## Detection, Logging, and Evidence

CloudTrail records supported API activity for AWS KMS, including caller identity, Region, request parameters, response elements, and errors. Treat encryption context as non-secret because it can be logged. Use service-specific logs and CloudWatch metrics to distinguish authorization errors, throttling, unavailable dependencies, key-state problems, and cryptographic validation failures.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Access denied | Key/data policy, IAM guardrail, grant, or condition does not allow the request | Inspect CloudTrail and evaluate every applicable policy | Add the least-privilege allow or remove the unintended explicit deny |
| Ciphertext cannot be decrypted | Wrong key, Region, algorithm, encryption context, or unavailable key store | Inspect key metadata and the original encryption parameters | Use the matching enabled key and exact authenticated parameters |
| Operation is slow or throttled | Service quota, high KMS call rate, or custom key-store capacity | Review CloudWatch metrics and service quotas | Use envelope encryption, safe caching, Bucket Keys, or capacity changes when appropriate |

## Security Best Practices

- Apply least privilege and separation of duties to AWS KMS, AWS Command Line Interface (AWS CLI).
- Prefer managed AWS cryptographic integrations unless explicit key custody, portability, or compliance requirements justify more operational burden.
- Keep plaintext keys and secrets out of code, logs, command history, tags, aliases, and encryption context.
- Design recovery before disabling or deleting keys; retained ciphertext is useless without an available authorized key path.
- Monitor administrative changes and repeated failed cryptographic or secret operations.

## Common Exam Traps

- Encrypt with the key, authorize with policy, prove with a decrypt test and CloudTrail.
- Encryption at rest does not replace encryption in transit, and neither replaces authorization.
- Creating a KMS key does not give its creator unlimited use unless the effective policies allow it.
- A key policy allow cannot override an explicit deny in an applicable guardrail or identity control.
- Key rotation does not re-encrypt existing ciphertext; old key material remains available to decrypt data while the KMS key is enabled.
