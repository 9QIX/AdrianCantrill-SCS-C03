# Load Balancer TLS Termination and Session Stickiness

## Overview

This chapter explains Load Balancer TLS Termination and Session Stickiness and the security and availability decisions it supports for AWS Certified Security – Specialty (SCS-C03). The focus is selecting the correct load-balancing layer, protecting each network and TLS hop, and using target health and telemetry to isolate failures.

A load balancer distributes traffic; it does not replace application authentication or authorization. Listener configuration, certificates, TLS policies, security groups, routes, target registration, health checks, and application behavior must be evaluated at their own layers.

## Core Concepts

- TLS offload terminates TLS at the load balancer and forwards plaintext to targets; bridging terminates and creates a new TLS connection to targets; pass-through preserves end-to-end client-to-target TLS where supported by Layer 4 forwarding.
- Offload centralizes certificates but leaves the backend hop unencrypted; bridging protects both hops while creating two trust boundaries.
- Session stickiness directs a client to the same target using load-balancer-generated or application cookies for supported ALB target groups.
- Stickiness can create uneven load and hidden server state, and it does not replace authentication, authorization, or shared session storage.

## How It Works

1. A client resolves the service name and connects to a listener using a protocol and port the load balancer accepts.
2. Listener policy and rules evaluate the connection or HTTP request at the load balancer's supported layer.
3. The load balancer selects a healthy registered target according to its routing algorithm and any configured stickiness.
4. TLS, security groups, target health, logging, and application authorization apply at their respective hops; failure at any layer can prevent a valid response.

Offload ends TLS once; bridging creates two TLS sessions; pass-through leaves TLS for the target. Scope each control to the correct hop: front-end TLS and listener policy, load-balancer routing, backend network access, target health, and application authorization are separate decisions.

## Detection, Logging, and Evidence

AWS CloudTrail records Elastic Load Balancing configuration API activity. Load balancer access logs provide request or connection evidence when enabled, while Amazon CloudWatch metrics expose target health, response codes, connection errors, latency, and capacity behavior. Use the sources together: CloudTrail answers who changed the configuration, access logs describe handled traffic, and metrics reveal operational symptoms.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Requests receive `503` responses | The target group has no healthy registered targets | Check target health reason codes, health-check settings, and target security groups | Correct the target, health-check path or port, and network reachability |
| TLS handshake fails | Certificate, listener security policy, Server Name Indication (SNI), or client protocol mismatch | Inspect the listener certificate and policy; reproduce with a TLS-aware client | Attach the correct certificate or choose a compatible approved security policy |
| Targets time out | Listener rule, route, security group, network ACL, target port, or application failure | Test each hop and review target health, access logs, and application logs | Correct the failing network or application layer without broadening unrelated access |
| Stickiness appears ineffective | Stickiness is disabled, the cookie expired, the client did not return it, or the target became unhealthy | Inspect target-group attributes and the client's cookies | Enable the intended cookie mode and duration; restore target health |

## Security Best Practices

- Deploy across multiple Availability Zones and keep healthy targets in every enabled zone.
- Permit backend traffic only from the load balancer's security group where the load balancer type supports security groups.
- Use AWS Certificate Manager (ACM) certificates and an approved current TLS security policy for encrypted listeners.
- Enable the relevant access logs and alarms, and monitor configuration changes through CloudTrail.
- Treat load balancing as a network and availability control; retain application authentication and authorization.

## Exam Decision Guide

| Requirement or Clue | Most Likely Control | Why |
| --- | --- | --- |
| HTTP/HTTPS host, path, or header routing | Application Load Balancer (ALB) | It provides Layer 7 request-aware routing and integrates with AWS WAF |
| TCP, UDP, TLS, static zonal IP addresses, or AWS PrivateLink endpoint services | Network Load Balancer (NLB) | It operates at Layer 4 and supports high-performance connection routing |
| Insert and scale virtual network appliances | Gateway Load Balancer (GWLB) | It distributes traffic transparently to appliance fleets |
| Manage a public TLS certificate | AWS Certificate Manager (ACM) | It provisions and manages supported certificates for integrated services |

## Common Exam Traps

- A healthy target proves reachability and health-check success, not caller authorization.
- TLS termination at the load balancer does not encrypt the backend hop unless that hop also uses TLS.
- Stickiness improves affinity, not high availability; an unhealthy target cannot remain the destination merely because a cookie names it.
- A certificate and a TLS security policy solve different problems: identity/key material versus allowed protocols and ciphers.
- Application Load Balancers and Network Load Balancers operate at different layers; choose from the protocol and routing requirement.

## Key Terms and Definitions

| Term | Definition | Exam Relevance |
| --- | --- | --- |
| Listener | A configured protocol and port on which a load balancer accepts traffic. | Listener configuration determines the front-end traffic and TLS boundary. |
| Target group | A set of registered destinations plus routing and health-check settings. | Rules forward to target groups, and only healthy targets receive new traffic. |
| Health check | A probe used to determine whether a registered target can receive traffic. | Health is an availability signal, not an authorization decision. |
| TLS security policy | The protocols and cipher suites accepted by a TLS listener. | Do not confuse the policy with the listener certificate. |
