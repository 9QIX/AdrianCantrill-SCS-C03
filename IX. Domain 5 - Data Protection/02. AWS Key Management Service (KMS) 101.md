# AWS Key Management Service Fundamentals

## Overview

This chapter explains AWS Key Management Service Fundamentals and the security decision it supports for AWS Certified Security – Specialty (SCS-C03). The focus is protecting confidentiality and integrity while keeping key custody, authorization, availability, and auditability explicit.

Encryption is effective only when key access, data access, network paths, lifecycle controls, and recovery plans are designed together. A denied key operation, disabled key, expired credential, incompatible TLS client, or missing route can each present as an application failure.

## Core Concepts

- AWS KMS is a Regional, managed service for creating and controlling cryptographic keys backed by FIPS-validated HSMs.
- Current standard KMS keys are protected by FIPS 140-3 Security Level 3 validated HSMs outside the documented China Region exception.
- A KMS key is a logical resource containing metadata, policy, and a reference to protected key material; plaintext key material does not leave KMS HSM boundaries for normal KMS keys.
- Symmetric encryption keys are the standard choice for integrated AWS services and envelope encryption; asymmetric and HMAC keys serve different operations.
- KMS separates key administrators from key users and records supported management and cryptographic API activity in CloudTrail.

## How It Works

1. A principal authenticates and requests a data or cryptographic operation.
2. IAM guardrails, resource or key policy, grants, and conditions determine whether the operation is authorized.
3. The service obtains or uses protected cryptographic material inside the defined trust boundary; plaintext key exposure is minimized.
4. Ciphertext, encrypted data keys, metadata, or secret versions are stored with the protected resource as required.
5. CloudTrail and service logs provide evidence; disabled keys, missing grants, context mismatch, or unavailable key stores cause explicit failure rather than silent decryption.

## Architecture and Service Relationships

```text
Principal or client
       |
       v
AWS Key Management Service (AWS KMS)
       |
       v
Authorization and cryptographic / TLS control
       |
       v
Protected data, target, or verified result
```

KMS controls the key; integrated services encrypt the data. Scope each control to the correct hop and remember that data access and key access are independent authorization questions when a customer managed KMS key is involved.

## Detection, Logging, and Evidence

CloudTrail records supported API activity for AWS Key Management Service (AWS KMS), including caller identity, Region, request parameters, response elements, and errors. Treat encryption context as non-secret because it can be logged. Use service-specific logs and CloudWatch metrics to distinguish authorization errors, throttling, unavailable dependencies, key-state problems, and cryptographic validation failures.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Access denied | Key/data policy, IAM guardrail, grant, or condition does not allow the request | Inspect CloudTrail and evaluate every applicable policy | Add the least-privilege allow or remove the unintended explicit deny |
| Ciphertext cannot be decrypted | Wrong key, Region, algorithm, encryption context, or unavailable key store | Inspect key metadata and the original encryption parameters | Use the matching enabled key and exact authenticated parameters |
| Operation is slow or throttled | Service quota, high KMS call rate, or custom key-store capacity | Review CloudWatch metrics and service quotas | Use envelope encryption, safe caching, Bucket Keys, or capacity changes when appropriate |

## Security Best Practices

- Apply least privilege and separation of duties to AWS Key Management Service (AWS KMS), AWS CloudTrail.
- Prefer managed AWS cryptographic integrations unless explicit key custody, portability, or compliance requirements justify more operational burden.
- Keep plaintext keys and secrets out of code, logs, command history, tags, aliases, and encryption context.
- Design recovery before disabling or deleting keys; retained ciphertext is useless without an available authorized key path.
- Monitor administrative changes and repeated failed cryptographic or secret operations.

## Exam Decision Guide

| Requirement or Clue | Most Likely Control | Why |
| --- | --- | --- |
| Directly implement this lesson's control | AWS Key Management Service (AWS KMS) | It provides the required data-protection capability |
| Customer controls key policy and lifecycle | Customer managed KMS key | It supports customer policy, grants, rotation configuration, disablement, and deletion scheduling |
| Direct, single-tenant HSM control | AWS CloudHSM | Customer manages dedicated HSM users and key operations |
| Automatic secret rotation and version staging | AWS Secrets Manager | It manages secret lifecycle and integrated or Lambda-based rotation |

## Common Exam Traps

- KMS controls the key; integrated services encrypt the data.
- Encryption at rest does not replace encryption in transit, and neither replaces authorization.
- Creating a KMS key does not give its creator unlimited use unless the effective policies allow it.
- A key policy allow cannot override an explicit deny in an applicable guardrail or identity control.
- Key rotation does not re-encrypt existing ciphertext; old key material remains available to decrypt data while the KMS key is enabled.
