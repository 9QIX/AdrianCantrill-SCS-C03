# AWS CloudHSM Architecture

## Overview

This chapter explains AWS CloudHSM Architecture and the security decision it supports for AWS Certified Security – Specialty (SCS-C03). The focus is protecting confidentiality and integrity while keeping key custody, authorization, availability, and auditability explicit.

Encryption is effective only when key access, data access, network paths, lifecycle controls, and recovery plans are designed together. A denied key operation, disabled key, expired credential, incompatible TLS client, or missing route can each present as an application failure.

## Core Concepts

- AWS CloudHSM provides single-tenant HSMs in a customer-controlled cluster inside a VPC.
- AWS manages hardware availability and replacement, while the customer manages HSM users, keys, policies, quorum, backups, clients, and application integration.
- A production cluster should span Availability Zones; keys synchronize across active HSMs and encrypted backups support recovery.
- CloudHSM is selected for direct HSM control, custom cryptographic integration, or compliance requirements not met by standard KMS.

## How It Works

1. IAM controls CloudHSM management-plane operations such as cluster and HSM lifecycle actions.
2. CloudHSM client applications establish an end-to-end encrypted connection to the cluster and authenticate as HSM users; IAM identities do not authorize HSM cryptographic operations.
3. Keys are generated or imported and used within the dedicated HSM security boundary according to HSM user permissions.
4. Active HSMs in the cluster synchronize key material, while encrypted cluster backups support recovery and new-HSM initialization.
5. CloudTrail records management API calls; CloudHSM audit logs provide evidence of HSM user and key operations.

CloudHSM gives dedicated hardware control—and dedicated operational responsibility. Scope each control to the correct hop and remember that data access and key access are independent authorization questions when a customer managed KMS key is involved.

## Detection, Logging, and Evidence

CloudTrail records CloudHSM management-plane API activity, including caller identity, Region, request parameters, response elements, and errors. CloudHSM audit logs record HSM command activity and can be delivered to CloudWatch Logs. Use both sources because IAM governs cluster management while HSM users govern cryptographic data-plane operations.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Access denied | Key/data policy, IAM guardrail, grant, or condition does not allow the request | Inspect CloudTrail and evaluate every applicable policy | Add the least-privilege allow or remove the unintended explicit deny |
| Ciphertext cannot be decrypted | Wrong key, Region, algorithm, encryption context, or unavailable key store | Inspect key metadata and the original encryption parameters | Use the matching enabled key and exact authenticated parameters |
| Operation is slow or throttled | Service quota, high KMS call rate, or custom key-store capacity | Review CloudWatch metrics and service quotas | Use envelope encryption, safe caching, Bucket Keys, or capacity changes when appropriate |

## Security Best Practices

- Apply least privilege and separation of duties to AWS CloudHSM.
- Prefer managed AWS cryptographic integrations unless explicit key custody, portability, or compliance requirements justify more operational burden.
- Keep plaintext keys and secrets out of code, logs, command history, tags, aliases, and encryption context.
- Design recovery before disabling or deleting keys; retained ciphertext is useless without an available authorized key path.
- Monitor administrative changes and repeated failed cryptographic or secret operations.

## Common Exam Traps

- CloudHSM gives dedicated hardware control—and dedicated operational responsibility.
- Encryption at rest does not replace encryption in transit, and neither replaces authorization.
- Creating a KMS key does not give its creator unlimited use unless the effective policies allow it.
- A key policy allow cannot override an explicit deny in an applicable guardrail or identity control.
- Key rotation does not re-encrypt existing ciphertext; old key material remains available to decrypt data while the KMS key is enabled.
