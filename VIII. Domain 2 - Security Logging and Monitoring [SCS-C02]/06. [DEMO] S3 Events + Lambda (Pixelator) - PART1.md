# Demonstration: S3 Event-Driven Image Processing — Part 1

## Overview

This part prepares a serverless image-processing pipeline in which an Amazon S3 object-created event invokes AWS Lambda. The security focus is on separating input/output locations, constraining the execution role, and granting S3 permission to invoke only the intended function.

## Exam Alignment

- **Primary SCS-C03 Domain:** Incident Response
- **Secondary Domain(s):** Identity and Access Management
- **Main AWS Services:** Amazon S3, AWS Lambda, IAM, Amazon CloudWatch Logs
- **Lesson Type:** Demonstration
- **Exam Importance:** Medium
- **Core Skill:** Prepare least-privilege identities and storage for an event-driven workflow.

## Demonstration Goal

Create the buckets, Lambda execution role, and function required for event-driven image processing; notification wiring and validation follow in Part 2.

## Prerequisites

- A lab account and Region that support S3 and Lambda.
- The source deployment package and sample images linked below.
- Permission to create buckets, roles, functions, logs, and resource-based invocation permissions.
- Unique input and output bucket names, or non-overlapping prefixes.

## Demonstration Steps

1. Review the supplied architecture, code, and IAM policy before deployment; replace example resources with lab-specific ARNs.
2. Create separate input and output S3 locations to prevent transformed objects from retriggering the same function.
3. Create a Lambda execution role trusted only by `lambda.amazonaws.com`.
4. Grant read access only to input objects, write access only to the output location, and CloudWatch Logs permissions for the function.
5. Create the Lambda function using a supported runtime and supplied deployment package.
6. Configure memory, timeout, environment values, and architecture to match the code and image library.
7. Invoke a controlled test event or inspect initialization logs before connecting S3.

## Policy or Permission Analysis

The execution-role trust policy allows Lambda to assume the role. Its permissions policy controls what function code may do. A separate Lambda resource policy, added when configuring the trigger, lets S3 invoke the function and should constrain `AWS:SourceArn` to the input bucket and `AWS:SourceAccount` to the owner account.

## Validation

- Function creation succeeds and the execution role is attached.
- Input read and output write ARNs are narrow and distinct.
- A test invocation reaches CloudWatch Logs without leaking object content or credentials.
- No S3 notification is expected until Part 2.

## Cleanup

Cleanup is completed after Part 2 so dependencies can be removed in safe order.

## What the Demonstration Proves

Event-driven code needs two authorization paths: the event source must be allowed to invoke Lambda, and the Lambda execution role must be allowed to access downstream resources.

## Common Exam Traps

- The execution role does not grant S3 permission to invoke the function.
- Broad `s3:*` permissions are unnecessary for object transformation.
- Using the same unfiltered location for input and output can create an invocation loop.

## Quick Review

- Separate input and output.
- Review third-party lab code before executing it.
- Minimize the Lambda role.
- Treat invoke permission and execution permission separately.
- Validate logs before wiring events.

## Self-Check Questions

1. Which policy lets Amazon S3 invoke Lambda?

<details><summary>Answer</summary>

The Lambda function's resource-based policy; the function execution role governs what code can do after invocation.

</details>
