# Demonstration: CloudWatch Agent Logging and Metrics — Part 1

## Overview

This part prepares an Amazon EC2 instance and IAM role for the unified CloudWatch agent. The agent collects guest operating-system metrics, logs, and supported traces that basic EC2 monitoring does not provide.

## Exam Alignment

- **Primary SCS-C03 Domain:** Detection
- **Secondary Domain(s):** Identity and Access Management
- **Main AWS Services:** Amazon CloudWatch, CloudWatch Logs, Amazon EC2, IAM, AWS Systems Manager
- **Lesson Type:** Demonstration
- **Exam Importance:** High
- **Core Skill:** Prepare least-privilege instance access and identify security-relevant telemetry sources.

## Demonstration Goal

Prepare an EC2 instance to collect `/var/log/secure`, Apache access/error logs, and guest metrics without storing AWS access keys on the host.

## Prerequisites

- A supported EC2 instance with the relevant log files and outbound access to required service endpoints.
- Systems Manager connectivity if using Parameter Store or Run Command.
- An instance role with approved CloudWatch agent permissions.
- Permission to install software and read the selected log files.

## Demonstration Steps

1. Identify the exact log paths, owners, permissions, and desired retention. Typical paths are `/var/log/secure`, `/var/log/httpd/access_log`, and `/var/log/httpd/error_log` on compatible distributions.
2. Create or reuse a least-privilege EC2 instance role; do not configure IAM-user access keys on the server.
3. Grant the agent permission to create log streams, put log events, and publish only required metrics.
4. If storing configuration in Systems Manager Parameter Store, separately grant the narrow read/write parameter permissions required by the configuration workflow.
5. Attach the instance profile and verify Instance Metadata Service credential retrieval.
6. Install the current unified CloudWatch agent package from an approved AWS source and verify installation.

## Policy or Permission Analysis

The EC2 trust policy allows `ec2.amazonaws.com` to assume the role through an instance profile. The permissions policy controls agent publication. Parameter Store configuration-authoring permission is more powerful than runtime read access and should be separated where practical.

## Validation

- The instance has role-based temporary credentials and no static access key.
- The agent binary is installed.
- The selected log files exist and are readable by the agent.
- Network/DNS/TLS connectivity to CloudWatch and Systems Manager endpoints succeeds.

## Cleanup

Do not remove the instance, role, or agent after Part 1 because Part 2 uses them. Perform cleanup only after validating the completed pipeline.

## What the Demonstration Proves

An agent requires local data access, network reachability, and AWS authorization; missing any one prevents telemetry delivery.

## Quick Review

- Use an instance role.
- Separate config-authoring from config-reading permissions.
- Verify local file paths and access.
- Plan log retention before ingestion.
- Use supported packages and endpoints.

## Self-Check Questions

1. Why avoid IAM-user keys on an EC2 instance?

<details><summary>Answer</summary>

An instance role supplies automatically rotated temporary credentials and avoids storing a long-term secret on the host.

</details>
