# AWS CloudTrail Architecture

## Overview

AWS CloudTrail records account activity as events for supported API and non-API operations. Event history provides a searchable 90-day view of management events in each Region; trails deliver events to Amazon S3 and optionally CloudWatch Logs, while CloudTrail Lake stores and queries events in event data stores.

## Core Concepts

- Management events capture control-plane operations and console sign-in events.
- Data events capture high-volume resource operations such as S3 object access or Lambda invocation and are not included in trail/event-store defaults unless selected.
- Network activity events record supported VPC endpoint API activity under applicable conditions.
- Insights events identify unusual management API call or error-rate activity when enabled.
- Multi-Region trails and global-service-event settings reduce gaps; event records are not guaranteed to appear in execution order.

## Architecture and Service Relationships

```text
AWS account activity -> CloudTrail event
     |-> Event history (90-day management-event view)
     |-> Trail -> protected S3 archive -> Athena/SIEM
     |          `-> CloudWatch Logs -> filters/alarms
     `-> CloudTrail Lake event data store -> SQL queries
```

## Detection, Logging, and Evidence

Investigators commonly use `eventTime`, `eventSource`, `eventName`, `awsRegion`, `sourceIPAddress`, `userAgent`, request/response elements, resources, error fields, and `userIdentity` session context. Centralize storage, restrict deletion, enable integrity validation, encrypt as required, and monitor trail changes.

## Common Exam Traps

- “Enabled by default” refers to Event history visibility, not an immutable long-term trail archive.
- Data events are high volume and require explicit selection.
- CloudTrail records API activity; AWS Config records resource configuration state.
- CloudTrail log delivery is not a real-time ordered transaction log.

## Memory Hooks

> **CloudTrail answers who called what, when, where, and with what result.**

## Quick Review

- Know management, data, network activity, and Insights events.
- Create a trail or event data store for retention beyond Event history.
- Use advanced event selectors to control coverage and cost.
- Centralize and protect evidence.
- Correlate caller and session context.

## Self-Check Questions

1. Are S3 `GetObject` events included in Event history by default?

<details><summary>Answer</summary>

No. They are data events and must be explicitly selected in a trail or event data store.

</details>
