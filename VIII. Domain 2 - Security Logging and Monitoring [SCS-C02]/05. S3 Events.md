# Amazon S3 Event Notifications

## Overview

Amazon S3 event notifications publish events for selected object operations to supported destinations. They enable event-driven processing and security workflows but are asynchronous and must be treated as at-least-once, potentially duplicated and non-ordered delivery.

## Exam Alignment

- **Primary SCS-C03 Domain:** Incident Response
- **Secondary Domain(s):** Detection
- **Main AWS Services:** Amazon S3, Amazon EventBridge, AWS Lambda, Amazon SNS, Amazon SQS
- **Lesson Type:** Architecture
- **Exam Importance:** Medium
- **Core Skill:** Design reliable, nonrecursive processing of S3 object events.

## Core Concepts

- Bucket notification configurations select event types and optional key-prefix/suffix filters.
- Direct destinations include Lambda, SNS, and standard SQS queues; EventBridge provides broader routing and filtering options.
- Notifications generally include bucket, object key, event, and sequencing metadata—not the object body.
- Consumers should be idempotent because duplicate delivery can occur and ordering is not guaranteed across events.
- Writing processed output back under the same matching notification scope can cause recursion.

## How It Works

```text
Object event -> S3 notification configuration -> Lambda/SNS/SQS
                                             `-> EventBridge -> targets
```

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| No invocation | Destination resource policy missing | Inspect notification validation and target policy | Allow the S3 service principal with scoped source conditions |
| Invocation loop | Output matches input event filter | Inspect repeated object keys/invocations | Separate prefixes or buckets and add idempotency |
| Wrong object key | URL encoding not decoded | Compare event payload with S3 key | Decode safely before retrieving object |

## Common Exam Traps

- S3 events do not replace CloudTrail data events for auditable API history.
- A notification is not guaranteed exactly once.
- S3 does not send the object contents in the notification.
- Direct S3 notifications do not target SQS FIFO queues; use EventBridge when FIFO routing is required.

## Memory Hooks

> **S3 announces the object event; the consumer fetches and processes the object idempotently.**

## Quick Review

- Filter events narrowly.
- Scope destination policies to the source bucket.
- Expect duplicates and unordered delivery.
- Prevent recursive writes.
- Use EventBridge for richer routing.

## Self-Check Questions

1. Why must an S3 event consumer be idempotent?

<details><summary>Answer</summary>

Because event notifications can be delivered more than once and processing may be retried.

</details>
