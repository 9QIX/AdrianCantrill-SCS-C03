# Demonstration: S3 Event-Driven Image Processing — Part 2

## Overview

This part connects the prepared S3 input bucket to Lambda, validates image processing, and cleans up the lab. Reliable event processing requires filtered notifications, resource-policy authorization, idempotent handling, and observable failures.

## Exam Alignment

- **Primary SCS-C03 Domain:** Incident Response
- **Secondary Domain(s):** Detection
- **Main AWS Services:** Amazon S3, AWS Lambda, Amazon CloudWatch Logs
- **Lesson Type:** Demonstration
- **Exam Importance:** Medium
- **Core Skill:** Configure and validate an S3-to-Lambda event path without recursion or overbroad permission.

## Demonstration Goal

Invoke the function when an image arrives, write the processed output separately, and verify execution through objects, metrics, and logs.

## Prerequisites

- Part 1 resources: input/output locations, function, execution role, and deployment package.
- A supported sample image.
- Permission to configure S3 notifications and Lambda invoke permissions.

## Demonstration Steps

1. Add an object-created notification on the input bucket or input prefix.
2. Select the Lambda function and restrict suffixes to supported image types when appropriate.
3. Confirm the Lambda resource policy permits invocation from only the source bucket/account.
4. Upload one uniquely named test image.
5. Wait for asynchronous processing and check the output bucket or prefix.
6. Inspect Lambda invocation/error/throttle metrics and the function log stream.
7. Repeat a controlled upload to confirm idempotent or duplicate-safe behavior.

## Validation

- The upload creates an S3 notification and one or more successful Lambda invocations.
- The expected transformed object appears in the output location.
- Logs identify the source key and completion without exposing sensitive data.
- No recursive chain of output events occurs.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| No invocation | Notification or Lambda resource policy invalid | Inspect bucket configuration and function policy | Correct event filter/source conditions |
| Access denied reading/writing | Execution role ARN scope wrong | Review CloudTrail and Lambda logs | Correct least-privilege object ARNs |
| Repeated invocations | Output matches trigger scope | Compare event keys and notification filters | Separate input/output locations |
| Function errors | Package/runtime/library mismatch | Inspect CloudWatch Logs | Build a compatible package or runtime |

## Cleanup

Delete test objects, remove the bucket notification, remove Lambda invoke permission, delete the function, then remove empty lab buckets and the lab execution role if they have no other use. Confirm exact lab targets before deletion.

## What the Demonstration Proves

S3 events decouple object creation from asynchronous processing, while IAM roles, resource policies, filtering, logs, and idempotency collectively make the workflow secure and supportable.

## Quick Review

- Notifications can duplicate and reorder events.
- Filter triggers and prevent recursion.
- Verify both invocation and data-access policies.
- Use logs and metrics for evidence.
- Remove resources in dependency order.

## Self-Check Questions

1. Why might one upload produce repeated processing?

<details><summary>Answer</summary>

Delivery can be retried or duplicated, or output objects may retrigger an overly broad notification. The consumer should be idempotent and the input scope isolated.

</details>
