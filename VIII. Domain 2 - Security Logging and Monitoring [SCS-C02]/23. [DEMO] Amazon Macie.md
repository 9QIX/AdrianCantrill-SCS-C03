# Demonstration: Discovering Sensitive Data with Amazon Macie

## Overview

This demonstration creates a controlled S3 dataset containing synthetic financial, employee, credential-like, and organization-specific patterns, then uses Macie to detect them. Never use real personal data or active credentials in a lab.

## Exam Alignment

- **Primary SCS-C03 Domain:** Detection
- **Secondary Domain(s):** Data Protection, Incident Response
- **Main AWS Services:** Amazon Macie, Amazon S3, AWS KMS, Amazon EventBridge
- **Lesson Type:** Demonstration
- **Exam Importance:** High
- **Core Skill:** Configure a sensitive-data discovery job, interpret findings and coverage, and clean up synthetic data safely.

## Demonstration Goal

Detect built-in sensitive patterns and a custom license-plate pattern in synthetic S3 objects and distinguish findings from detailed discovery results.

## Prerequisites

- One supported Region used consistently.
- Least-privilege permission to enable/use Macie and create a lab S3 bucket.
- Only synthetic sample files from the source lab: credit-card-like, employee, key-like, and plate-pattern text.
- Budget awareness because object analysis is billable.

## Demonstration Steps

1. Review the linked lab files and confirm all values are fake and inactive.
2. Create a uniquely named private S3 bucket with Block Public Access and default encryption.
3. Upload the synthetic files and verify Macie can access the bucket and KMS key if used.
4. Enable Macie in the selected Region and configure the protected discovery-results repository.
5. Create a custom data identifier for the lab-specific license-plate pattern; include supporting keywords/proximity to reduce false positives.
6. Create a one-time discovery job targeting only the lab bucket and select appropriate managed/custom identifiers.
7. Run the job and review status, coverage, sensitive-data findings, severity, occurrences, and object details.
8. Route a sample finding through EventBridge if testing response integration.

## Validation

- Managed identifiers detect the applicable synthetic financial/personal/credential patterns.
- The custom identifier detects intended plate values without excessive unrelated matches.
- Discovery results show each object's analysis status, including any access or format errors.
- Findings do not expose the complete sensitive value by default.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Object skipped | Unsupported format/class or access issue | Inspect coverage and discovery result | Use supported data or correct bucket/KMS policy |
| Custom match absent | Regex, keyword, or proximity logic wrong | Test against synthetic samples | Refine identifier criteria |
| No finding yet | Job incomplete or wrong Region/scope | Check job status and bucket selection | Wait for completion or correct scope |

## Cleanup

Delete the discovery job if retained, custom identifier, synthetic objects, and empty lab bucket when no longer needed. Disable Macie only if the account has no operational dependency; disabling deletes Macie-managed findings and configuration, so preserve required results first.

## What the Demonstration Proves

Macie provides data classification evidence and S3 posture findings, while humans or automation must decide business criticality, containment, and remediation.

## Quick Review

- Use synthetic test data only.
- Configure a results repository.
- Scope jobs to intended buckets.
- Validate coverage, not only findings.
- Refine custom identifiers to control false positives.
- Preserve evidence before disabling Macie.

## Self-Check Questions

1. Why can an encrypted object remain unclassified?

<details><summary>Answer</summary>

Macie may lack authorization to use the object's KMS key, or the object may otherwise be unsupported or inaccessible.

</details>
