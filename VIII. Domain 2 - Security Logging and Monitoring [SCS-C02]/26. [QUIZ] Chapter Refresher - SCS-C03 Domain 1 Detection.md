### Question 1 – Organization trail long-term retention and querying

A healthcare company uses AWS Organizations with 60 member accounts. Compliance officers must run SQL queries across management events and Amazon S3 data events from every account, and the events must be retained in immutable storage for 7 years. The company does not want to run AWS Glue crawlers, ETL jobs, or scheduled jobs that add partitions as new logs arrive. Which solution meets these requirements with the LEAST operational overhead?

- **A.** Use CloudTrail Event history in each account and create an Amazon Athena table from Event history for SQL queries.
- **B.** Create an organization trail that includes management events and S3 data events and delivers to an S3 bucket with S3 Object Lock in compliance mode and a 7-year default retention period. Query the logs with an Amazon Athena CloudTrail table that uses partition projection.
- **C.** Send each account's CloudTrail events to an Amazon CloudWatch Logs log group with 7-year retention and query them with CloudWatch Logs Insights.
- **D.** Create an organization trail that delivers to an S3 bucket with S3 Versioning enabled, and run an hourly AWS Glue crawler so that Amazon Athena can query the new partitions.

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** Create an organization trail that includes management events and S3 data events and delivers to an S3 bucket with S3 Object Lock in compliance mode and a 7-year default retention period. Query the logs with an Amazon Athena CloudTrail table that uses partition projection.

An organization trail captures management and S3 data events from all 60 accounts into one bucket with a single configuration, and Object Lock compliance mode with 7-year retention makes the log objects WORM so nobody, including the root user, can delete them early. Athena partition projection computes partitions from the S3 key layout, so no crawlers or partition jobs are needed.

**Summary:** An organization trail created in the management account (or CloudTrail delegated administrator account) captures events from every member account into one S3 bucket. S3 Object Lock in compliance mode with a 7-year default retention makes the log objects write-once-read-many (WORM), so no user, including the root user, can delete or overwrite them during the retention period. An Athena table with partition projection calculates partitions from the S3 key layout, so no crawlers or partition-maintenance jobs are needed.

❌ **A.** Use CloudTrail Event history in each account and create an Amazon Athena table from Event history for SQL queries.

Event history keeps only the last 90 days of management events per account and Region and does not include S3 data events. It is not an immutable 7-year store, so it fails both the scope and the retention requirement.

❌ **C.** Send each account's CloudTrail events to an Amazon CloudWatch Logs log group with 7-year retention and query them with CloudWatch Logs Insights.

This requires per-account configuration, and CloudWatch Logs log groups and retention settings can be changed or deleted by administrators, so it is not immutable WORM storage. Long-term log storage is also more costly than S3.

❌ **D.** Create an organization trail that delivers to an S3 bucket with S3 Versioning enabled, and run an hourly AWS Glue crawler so that Amazon Athena can query the new partitions.

Versioning preserves prior versions but does not prevent authorized users from permanently deleting versions, and the hourly crawler is the partition maintenance that the company wants to avoid.

### Question 2 – CloudTrail log file integrity validation

A payments company must prove to external auditors that AWS CloudTrail log files in its central S3 bucket have not been modified, forged, or deleted since CloudTrail delivered them. The auditors also want a repeatable method that they can run themselves by using the AWS CLI. Which actions should a security engineer take? (Select TWO.)

- **A.** Enable log file integrity validation on the trail so that CloudTrail delivers signed hourly digest files.
- **B.** Enable S3 Versioning on the log bucket and compare object version IDs each month.
- **C.** Enable Amazon Macie on the log bucket to detect modified log files.
- **D.** Run the aws cloudtrail validate-logs command against the trail ARN for the audit time range.
- **E.** Encrypt the trail with an AWS KMS customer managed key and treat any decryption failure as evidence of tampering.
- **F.** Enable S3 server access logging on the log bucket and search for DeleteObject requests.

<details>
<summary>Show answer and explanation</summary>

**Answer: A, D**

✅ **A.** Enable log file integrity validation on the trail so that CloudTrail delivers signed hourly digest files.

Integrity validation makes CloudTrail deliver hourly digest files that hold SHA-256 hashes of each log file, are signed with a CloudTrail private key, and chain to the previous digest. This is the cryptographic evidence auditors need to prove files were not modified, forged, or deleted.

✅ **D.** Run the aws cloudtrail validate-logs command against the trail ARN for the audit time range.

The validate-logs command checks the log files against the signed digest chain for a time range and reports any modified, deleted, or forged files and digests. Auditors can run it themselves with the AWS CLI, which gives them the repeatable method they asked for.

**Summary:** Log file integrity validation makes CloudTrail deliver digest files that contain SHA-256 hashes of each log file and are signed with a private key, with each digest chaining to the previous one. The validate-logs CLI command uses these digests to detect modified, deleted, or forged log files and digests. Together they provide the proof and the repeatable verification that auditors require.

❌ **B.** Enable S3 Versioning on the log bucket and compare object version IDs each month.

Versioning keeps prior versions of objects but gives no cryptographic proof that a delivered file is unchanged or that no file was removed. Auditors would have nothing verifiable to check, and comparing version IDs by hand is not a repeatable CLI verification.

❌ **C.** Enable Amazon Macie on the log bucket to detect modified log files.

Macie finds sensitive data and reports bucket security and access issues; it does not verify log file integrity. It cannot prove that CloudTrail log files were not modified, forged, or deleted.

❌ **E.** Encrypt the trail with an AWS KMS customer managed key and treat any decryption failure as evidence of tampering.

SSE-KMS provides confidentiality and access control, not integrity proof. A deleted file causes no decryption failure, and a principal with KMS permissions could replace a file with a validly encrypted forgery, so this gives auditors no evidence.

❌ **F.** Enable S3 server access logging on the log bucket and search for DeleteObject requests.

Server access logs are delivered on a best-effort basis and only show that requests were made. They cannot prove that file contents are unchanged, and they give auditors no cryptographic verification method.

</details>

### Question 3 – CloudTrail SSE-KMS troubleshooting

A security engineer updated an organization trail to encrypt log files with a new AWS KMS customer managed key. The key was created with the key policy shown. Immediately afterward, CloudTrail stopped delivering log files, and analysts in the account must also be able to read the logs after delivery resumes.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnableRootPermissions",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
      "Action": "kms:*",
      "Resource": "*"
    }
  ]
}
```

Which actions should the engineer take? (Select TWO.)

- **A.** Attach an IAM policy that grants kms:Encrypt to the CloudTrail service-linked role.
- **B.** Add a key policy statement that allows the cloudtrail.amazonaws.com service principal to call kms:GenerateDataKey\*, with a condition on the kms:EncryptionContext:aws:cloudtrail:arn key for the account's trails.
- **C.** Change the default encryption of the log bucket to SSE-S3.
- **D.** Enable automatic key rotation on the customer managed key.
- **E.** Grant the analysts' IAM roles kms:Decrypt on the key, either in the key policy or through IAM policies that the root-account key policy statement enables.
- **F.** Add a statement to the S3 bucket policy that grants cloudtrail.amazonaws.com kms:GenerateDataKey\*.

<details>
<summary>Show answer and explanation</summary>

**Answer: B, E**

✅ **B.** Add a key policy statement that allows the cloudtrail.amazonaws.com service principal to call kms:GenerateDataKey\*, with a condition on the kms:EncryptionContext:aws:cloudtrail:arn key for the account's trails.

CloudTrail calls kms:GenerateDataKey\* as the cloudtrail.amazonaws.com service principal, and the current key policy only lets IAM principals in the account use the key, so delivery fails. A key policy statement for the service principal, scoped with the aws:cloudtrail:arn encryption context, restores delivery while limiting use of the key to this account's trails.

✅ **E.** Grant the analysts' IAM roles kms:Decrypt on the key, either in the key policy or through IAM policies that the root-account key policy statement enables.

SSE-KMS log files can only be read by principals that have kms:Decrypt on the key in addition to s3:GetObject. Because the root statement lets IAM policies control access to the key, granting kms:Decrypt either in the key policy or in the analysts' IAM policies lets them read the logs once delivery resumes.

**Summary:** The existing key policy only enables IAM policies in the account; it does not authorize the CloudTrail service principal, so CloudTrail cannot generate data keys and delivery fails. Adding a key policy statement for cloudtrail.amazonaws.com with kms:GenerateDataKey\* (scoped by the CloudTrail encryption context) restores delivery. Readers of SSE-KMS encrypted log files also need kms:Decrypt in addition to s3:GetObject.

❌ **A.** Attach an IAM policy that grants kms:Encrypt to the CloudTrail service-linked role.

CloudTrail encrypts log files as the cloudtrail.amazonaws.com service principal, which must be allowed in the key policy; it does not use a service-linked role for this. CloudTrail also uses kms:GenerateDataKey\*, not kms:Encrypt, so this change would not restore delivery.

❌ **C.** Change the default encryption of the log bucket to SSE-S3.

The trail configuration still names the KMS key, so CloudTrail keeps trying to use it and delivery keeps failing. Changing bucket default encryption also would not help the analysts, and it abandons the customer managed key the engineer intended to use.

❌ **D.** Enable automatic key rotation on the customer managed key.

Key rotation only creates new key material on a schedule. It grants no permissions to CloudTrail or to the analysts, so delivery stays broken and the logs stay unreadable.

❌ **F.** Add a statement to the S3 bucket policy that grants cloudtrail.amazonaws.com kms:GenerateDataKey\*.

KMS permissions cannot be granted in an S3 bucket policy; they must be granted through the key policy or IAM policies that the key policy allows.

</details>

### Question 4 – CloudTrail data events - advanced event selectors

A media company stores signed contracts in an S3 bucket named contracts-prod. The security team must record only PutObject and DeleteObject API calls for objects under the signed/ prefix. The bucket serves millions of GetObject requests each day, and the company wants to minimize AWS CloudTrail data event charges. Which configuration meets these requirements?

- **A.** Add a basic data event selector for arn:aws:s3:::contracts-prod/signed/ with the Read/Write type set to WriteOnly.
- **B.** Enable S3 server access logging on the bucket with a target prefix of signed/.
- **C.** Configure advanced event selectors on the trail with eventCategory equal to Data, resources.type equal to AWS::S3::Object, eventName equal to PutObject or DeleteObject, and resources.ARN starting with arn:aws:s3:::contracts-prod/signed/.
- **D.** Enable write-only management events on the trail and filter the results with Amazon Athena.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Configure advanced event selectors on the trail with eventCategory equal to Data, resources.type equal to AWS::S3::Object, eventName equal to PutObject or DeleteObject, and resources.ARN starting with arn:aws:s3:::contracts-prod/signed/.

Advanced event selectors can filter data events on eventName and on resources.ARN with StartsWith, so the trail records and bills only PutObject and DeleteObject calls under signed/. The millions of GetObject calls and other write APIs are never recorded, which keeps data event charges as low as possible.

**Summary:** Advanced event selectors allow fine-grained filtering of data events on fields such as eventName and resources.ARN with StartsWith. Only matching events are recorded and billed, so millions of GetObject calls and other write operations are excluded. This is the only option that records exactly the required events at minimum cost.

❌ **A.** Add a basic data event selector for arn:aws:s3:::contracts-prod/signed/ with the Read/Write type set to WriteOnly.

WriteOnly also records other write APIs such as PutObjectAcl, PutObjectTagging, and CopyObject, which increases cost beyond the two required events.

❌ **B.** Enable S3 server access logging on the bucket with a target prefix of signed/.

Server access logs are not CloudTrail events and cannot be limited to PutObject and DeleteObject; they record all requests, including the millions of GetObject calls. The target prefix only sets where the log files are written, not which objects are logged.

❌ **D.** Enable write-only management events on the trail and filter the results with Amazon Athena.

Object-level operations are data events, so management events never contain PutObject or DeleteObject calls.

</details>

### Question 5 – CloudTrail Insights

A SaaS company enabled AWS CloudTrail Insights on an existing multi-Region trail for both the API call rate and API error rate insight types. Thirty minutes later, an engineer ran a test script that generated thousands of failed ec2:DescribeInstances calls. One hour after the test, no Insights events appear in the CloudTrail console or in the S3 bucket. What is the MOST likely explanation?

- **A.** CloudTrail Insights analyzes only data events, and DescribeInstances is a management event.
- **B.** Insights events are delivered only to Amazon CloudWatch Logs and never to S3 or the CloudTrail console.
- **C.** The API error rate insight type evaluates only write management events, so read-only Describe calls are ignored.
- **D.** After Insights is first enabled, CloudTrail must establish a baseline, and it can take up to 36 hours to deliver the first Insights event.

<details>
<summary>Show answer and explanation</summary>

**Answer: D**

✅ **D.** After Insights is first enabled, CloudTrail must establish a baseline, and it can take up to 36 hours to deliver the first Insights event.

CloudTrail Insights must first learn a baseline of normal management event activity before it can spot anomalies, and AWS documents that the first Insights event can take up to 36 hours to arrive after Insights is enabled. A test run 30 minutes after enabling it would not be expected to produce an Insights event within the hour.

**Summary:** CloudTrail Insights compares current management event activity against a baseline of normal activity. After Insights is first enabled on a trail, it can take up to 36 hours for the first Insights event to be delivered, even when unusual activity occurs. A test run shortly after enabling the feature is therefore not expected to produce results immediately.

❌ **A.** CloudTrail Insights analyzes only data events, and DescribeInstances is a management event.

Insights analyzes management events, not data events, and DescribeInstances is a management event that Insights can evaluate. This statement is backwards and does not explain the missing Insights events.

❌ **B.** Insights events are delivered only to Amazon CloudWatch Logs and never to S3 or the CloudTrail console.

Insights events are delivered to the trail's S3 bucket and shown in the CloudTrail console, and they can also go to CloudWatch Logs if configured. The missing events are caused by the baseline period, not by where they are delivered.

❌ **C.** The API error rate insight type evaluates only write management events, so read-only Describe calls are ignored.

The API error rate type evaluates both read and write management events; it is the API call rate type that evaluates write management events only.

### Question 6 – CloudWatch metric filters and alarms

A logistics company sends CloudTrail events to a CloudWatch Logs log group. A security engineer created a metric filter with the pattern { ($.errorCode = "AccessDenied") || ($.errorCode = "\*UnauthorizedOperation") } and an alarm that enters ALARM when the Sum is 5 or more in 5 minutes. A test that produced 10 AccessDenied errors triggered the alarm, but most of the time the alarm shows INSUFFICIENT_DATA, which the SOC dashboard treats as a monitoring failure. What should the engineer change?

- **A.** Set the metric filter's default value to 0 so that a data point is published for periods without matching events, or configure the alarm to treat missing data as not breaching.
- **B.** Configure the metric filter to reprocess historical log events so that earlier periods have data points.
- **C.** Increase the log group retention period so that the alarm can evaluate older data.
- **D.** Replace the metric filter with a subscription filter that sends matching events directly to an Amazon SNS topic.

<details>
<summary>Show answer and explanation</summary>

**Answer: A**

✅ **A.** Set the metric filter's default value to 0 so that a data point is published for periods without matching events, or configure the alarm to treat missing data as not breaching.

Without a default value, the metric filter publishes no data point when no log events match, so the alarm has nothing to evaluate and shows INSUFFICIENT_DATA. A default value of 0, or treating missing data as notBreaching, keeps the alarm in OK during quiet periods while still going to ALARM when 5 or more errors occur.

**Summary:** A metric filter publishes no data points when no log events match unless a default value is configured, so the alarm has nothing to evaluate and reports INSUFFICIENT_DATA. Setting the default value to 0, or treating missing data as notBreaching, keeps the alarm in OK during quiet periods. The alarm still transitions to ALARM when matching errors occur.

❌ **B.** Configure the metric filter to reprocess historical log events so that earlier periods have data points.

Metric filters evaluate only log events ingested after the filter is created and cannot be applied to past data. Backfilling would not help anyway, because the problem is quiet periods with no matching events, which will keep happening.

❌ **C.** Increase the log group retention period so that the alarm can evaluate older data.

Retention controls how long log events are stored and has no effect on whether metric data points are published.

❌ **D.** Replace the metric filter with a subscription filter that sends matching events directly to an Amazon SNS topic.

Subscription filters support destinations such as Kinesis Data Streams, Amazon Data Firehose, OpenSearch Service, and Lambda, not SNS. They also have no alarm states, so the SOC dashboard would lose its OK and ALARM signals.

</details>

### Question 7 – CloudWatch Logs cross-account subscriptions

A gaming company has 40 workload accounts that write application security logs to Amazon CloudWatch Logs. The security operations center (SOC) needs these logs streamed in near real time to an Amazon Kinesis Data Streams stream in a central security account for SIEM processing. Application code must not change, and workload accounts must not receive write access to the stream itself. Which combination of steps meets these requirements? (Select TWO.)

- **A.** In each workload account, schedule a daily CreateExportTask operation that exports the log groups to an S3 bucket in the central account.
- **B.** Add a Kinesis resource-based policy that grants each workload account kinesis:PutRecord, and update the applications to write to the stream.
- **C.** In the central account, create a CloudWatch Logs destination that targets the Kinesis stream, with an IAM role that CloudWatch Logs can assume to put records and a destination access policy that allows only the workload accounts or the organization.
- **D.** Configure CloudWatch cross-account observability with the central account as the monitoring account.
- **E.** Create CloudWatch Logs metric filters in each workload account and share the metrics with the central account.
- **F.** In each workload account, create subscription filters on the log groups (or an account-level subscription filter policy) that reference the central account's destination ARN.

<details>
<summary>Show answer and explanation</summary>

**Answer: C, F**

✅ **C.** In the central account, create a CloudWatch Logs destination that targets the Kinesis stream, with an IAM role that CloudWatch Logs can assume to put records and a destination access policy that allows only the workload accounts or the organization.

A CloudWatch Logs destination in the central account wraps the Kinesis stream and uses a role that CloudWatch Logs assumes to write records, so workload accounts never get stream permissions. The destination access policy limits which accounts, or the whole organization, can subscribe, which meets the least-privilege requirement.

✅ **F.** In each workload account, create subscription filters on the log groups (or an account-level subscription filter policy) that reference the central account's destination ARN.

Subscription filters stream matching log events in near real time from existing log groups to the destination ARN, so no application code changes are needed. An account-level subscription filter policy can cover all log groups in an account without configuring each one.

**Summary:** Cross-account log streaming uses a CloudWatch Logs destination in the receiving account, which wraps the Kinesis stream and is protected by a destination access policy. Sender accounts create subscription filters that point to the destination ARN, so logs flow in near real time without code changes. The workload accounts never receive direct permissions on the stream, which preserves least privilege.

❌ **A.** In each workload account, schedule a daily CreateExportTask operation that exports the log groups to an S3 bucket in the central account.

Export tasks are batch jobs, and a daily schedule gives delays of up to 24 hours, which fails the near real-time streaming requirement. Exported files in S3 also do not reach the Kinesis stream that the SIEM reads.

❌ **B.** Add a Kinesis resource-based policy that grants each workload account kinesis:PutRecord, and update the applications to write to the stream.

This requires changing application code to write to Kinesis, which is not allowed. It also gives every workload account direct write access to the stream, which the requirements forbid.

❌ **D.** Configure CloudWatch cross-account observability with the central account as the monitoring account.

Cross-account observability lets the monitoring account view and query data, but it does not stream log events into Kinesis for a SIEM.

❌ **E.** Create CloudWatch Logs metric filters in each workload account and share the metrics with the central account.

Metric filters turn log events into numeric metrics and throw away the raw event content. The SIEM needs the actual log events streamed to Kinesis, which metric sharing cannot provide.

</details>

### Question 8 – CloudWatch Logs Insights

During an active investigation, a security engineer must identify within minutes the 10 source IP addresses with the most rejected connection attempts to TCP port 3389 during the past 72 hours. The VPC Flow Logs for the affected VPC are published to a CloudWatch Logs log group with 30-day retention. No other logging or analytics infrastructure exists. Which approach is the MOST operationally efficient?

- **A.** Create a metric filter that matches REJECT records for destination port 3389 and graph the resulting metric.
- **B.** Run a CloudWatch Logs Insights query on the log group for the past 72 hours that filters action = 'REJECT' and dstPort = 3389, aggregates with stats count(\*) by srcAddr, sorts in descending order, and limits the output to 10.
- **C.** Create an Amazon Athena table that points to the log group and run a SQL query.
- **D.** Create a CloudWatch Contributor Insights rule that ranks source addresses for rejected port 3389 traffic.

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** Run a CloudWatch Logs Insights query on the log group for the past 72 hours that filters action = 'REJECT' and dstPort = 3389, aggregates with stats count(\*) by srcAddr, sorts in descending order, and limits the output to 10.

CloudWatch Logs Insights queries data already stored in the log group, so it can analyze the past 72 hours right away without new infrastructure. Filtering on REJECT and dstPort 3389, then running stats count(\*) by srcAddr with sort and limit 10, returns the top-10 source list in seconds, which fits the time pressure of an active investigation.

**Summary:** CloudWatch Logs Insights runs ad hoc queries directly against data already stored in a log group, including historical events within the retention period. The stats, sort, and limit commands produce a top-N result in seconds without new infrastructure. The other options either work only on future data or require moving data first.

❌ **C.** Create an Amazon Athena table that points to the log group and run a SQL query.

Athena queries data in S3 and cannot read a CloudWatch Logs log group without exporting the data first or deploying a connector. That extra setup costs time during an active investigation when the answer is needed within minutes.

❌ **D.** Create a CloudWatch Contributor Insights rule that ranks source addresses for rejected port 3389 traffic.

Contributor Insights rules evaluate log events ingested after the rule is created, so they cannot analyze the previous 72 hours.

</details>

### Question 9 – EventBridge and global service events

A company operates in the eu-west-1 Region. A security engineer created an Amazon EventBridge rule on the default event bus in eu-west-1 with the pattern {"source": ["aws.iam"], "detail-type": ["AWS API Call via CloudTrail"], "detail": {"eventName": ["CreateAccessKey"]}} to invoke an AWS Lambda function. A multi-Region CloudTrail trail records CreateAccessKey events, but the rule's TriggeredRules metric remains at zero. What is the cause?

- **A.** The event pattern must use aws.cloudtrail as the source for events that are delivered through CloudTrail.
- **B.** EventBridge does not receive IAM API events, so AWS Config must be used instead.
- **C.** IAM is a global service whose CloudTrail events are delivered to EventBridge in the US East (N. Virginia) Region, so the rule must be created in us-east-1 (optionally forwarding events to eu-west-1).
- **D.** The Lambda function's resource-based policy does not allow EventBridge to invoke it.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** IAM is a global service whose CloudTrail events are delivered to EventBridge in the US East (N. Virginia) Region, so the rule must be created in us-east-1 (optionally forwarding events to eu-west-1).

IAM is a global service, so its CloudTrail events are delivered to EventBridge only in US East (N. Virginia). A rule in eu-west-1 never sees CreateAccessKey events, which is why TriggeredRules stays at zero. Creating the rule in us-east-1, optionally forwarding the events to a bus in eu-west-1, fixes it.

**Summary:** Events from global services such as IAM are recorded in the US East (N. Virginia) Region, so EventBridge rules that match them must exist in us-east-1. A rule in eu-west-1 never sees these events, which explains a TriggeredRules value of zero. Creating the rule in us-east-1, or forwarding from us-east-1 to another Region's bus, resolves the issue.

❌ **A.** The event pattern must use aws.cloudtrail as the source for events that are delivered through CloudTrail.

EventBridge uses the service that made the API call as the event source, so aws.iam is the correct source for CreateAccessKey. Changing it to aws.cloudtrail would make the pattern stop matching IAM events altogether.

❌ **B.** EventBridge does not receive IAM API events, so AWS Config must be used instead.

EventBridge does receive IAM management events recorded by CloudTrail, with the detail-type AWS API Call via CloudTrail. The rule fails only because it is in the wrong Region, so switching to AWS Config is unnecessary and would not give event-driven invocation of the function.

❌ **D.** The Lambda function's resource-based policy does not allow EventBridge to invoke it.

A missing invoke permission would produce FailedInvocations after the rule matched; it would not keep TriggeredRules at zero.

</details>

### Question 10 – EventBridge cross-account event bus

A company uses AWS Organizations. EC2 Instance State-change Notification events and AWS Health events from every member account in us-east-1 must be delivered to a custom event bus named security-central in the security account, where rules route them to an incident response workflow. - **E.** In each member account, deploy (for example with CloudFormation StackSets) a rule on the default event bus that matches the events and targets the security-central bus ARN, using an IAM role that allows events:PutEvents on that bus.
- **F.** Create an EventBridge Pipe in each member account with the CloudTrail trail as its source.

<details>
<summary>Show answer and explanation</summary>

**Answer: A, E**

The management account (111111111111) created an organization trail named org-trail that delivers to an S3 bucket named org-trail-logs. Log files for the management account appear, but none appear for member accounts. The bucket policy contains the following statement for log delivery.

```json
{
  "Sid": "AWSCloudTrailWrite",
  "Effect": "Allow",
  "Principal": { "Service": "cloudtrail.amazonaws.com" },
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::org-trail-logs/AWSLogs/111111111111/*",
  "Condition": {
    "StringEquals": {
      "s3:x-amz-acl": "bucket-owner-full-control",
      "aws:SourceArn": "arn:aws:cloudtrail:us-east-1:111111111111:trail/org-trail"
    }
  }
}
```

What should the security engineer change?

- **A.** Add an aws:SourceAccount condition that lists each member account ID.
- **B.** Enable trusted access for CloudTrail separately in each member account.
- **C.** Add arn:aws:s3:::org-trail-logs/AWSLogs/o-exampleorgid/\* (using the organization ID) to the Resource element of the statement.
- **D.** Grant s3:PutObject to the root principal of each member account.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Add arn:aws:s3:::org-trail-logs/AWSLogs/o-exampleorgid/\* (using the organization ID) to the Resource element of the statement.

An organization trail writes member account logs under AWSLogs/&lt;organization-ID&gt;/&lt;account-ID&gt;/, while the statement only allows the management account's AWSLogs/111111111111/ prefix. Adding the organization ID prefix to the Resource element lets the CloudTrail service principal deliver member account logs, and the aws:SourceArn condition still limits writes to org-trail.

**Summary:** An organization trail writes member account logs under the AWSLogs/&lt;organization-ID&gt;/&lt;account-ID&gt;/ prefix, and management account logs under AWSLogs/&lt;management-account-ID&gt;/. The statement allows only the management account prefix, so member account delivery is denied. Adding the organization ID prefix to the Resource element allows CloudTrail to deliver member account logs.

❌ **A.** Add an aws:SourceAccount condition that lists each member account ID.

Member account logs are delivered by the organization trail owned by the management account, and adding conditions further restricts rather than grants access.

❌ **B.** Enable trusted access for CloudTrail separately in each member account.

Trusted access for CloudTrail is enabled once at the organization level, not in each member account, and the organization trail already exists. The failure is the bucket policy Resource element, which trusted access does not change.

❌ **D.** Grant s3:PutObject to the root principal of each member account.

CloudTrail writes all organization trail log files as the cloudtrail.amazonaws.com service principal, not as member account principals. Granting member account roots s3:PutObject does not fix delivery and needlessly lets them write to the log bucket.

### Question 36 – EventBridge event patterns for GuardDuty

A security engineer created an Amazon EventBridge rule in each Region used by the company to send high and critical Amazon GuardDuty findings to an SNS topic. GuardDuty generates findings with severity 8.0 regularly, but the rule never matches. The rule uses the following event pattern.

```json
{
  "source": ["aws.guardduty"],
  "detail-type": ["GuardDuty Finding"],
  "detail": {
    "severity": ["HIGH", "CRITICAL"]
  }
}
```

What should the engineer change?

- **A.** Change the source to aws.securityhub, because GuardDuty findings reach EventBridge only through Security Hub CSPM.
- **B.** Change the detail-type to GuardDuty Findings - Imported.
- **C.** Recreate the rule only in us-east-1, because GuardDuty publishes all findings to that Region.
- **D.** Replace the severity values with numeric matching, such as "severity": [{"numeric": ["&gt;=", 7]}], because GuardDuty represents severity as a number in the event.

<details>
<summary>Show answer and explanation</summary>

**Answer: D**

✅ **D.** Replace the severity values with numeric matching, such as "severity": [{"numeric": ["&gt;=", 7]}], because GuardDuty represents severity as a number in the event.

In GuardDuty finding events, detail.severity is a number, with high findings from 7.0 to 8.9 and critical findings at 9.0 and above. A numeric matching expression of &gt;= 7 matches both high and critical findings, while string values such as HIGH can never match a numeric field.

**Summary:** In GuardDuty finding events, detail.severity is a numeric value, where high findings range from 7.0 to 8.9 and critical findings are 9.0 and above. String values such as HIGH never match that numeric field. An EventBridge numeric matching expression of greater than or equal to 7 captures both high and critical findings.

❌ **A.** Change the source to aws.securityhub, because GuardDuty findings reach EventBridge only through Security Hub CSPM.

GuardDuty publishes findings directly to EventBridge with the aws.guardduty source; Security Hub CSPM is not required. Changing the source would not fix the severity mismatch that stops the rule from matching.

❌ **B.** Change the detail-type to GuardDuty Findings - Imported.

GuardDuty Findings - Imported is not the detail-type that GuardDuty uses; GuardDuty findings use GuardDuty Finding, which the rule already has. Changing it would stop all matches.

❌ **C.** Recreate the rule only in us-east-1, because GuardDuty publishes all findings to that Region.

GuardDuty is Regional and publishes findings to EventBridge in the Region where they are created. Keeping the rule only in us-east-1 would miss findings from other Regions and still would not fix the string-versus-number severity mismatch.

</details>
