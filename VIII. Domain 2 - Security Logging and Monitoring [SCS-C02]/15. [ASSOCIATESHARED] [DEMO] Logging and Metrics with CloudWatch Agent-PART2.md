# Demonstration: CloudWatch Agent Logging and Metrics — Part 2

## Overview

This part creates the agent configuration, starts collection, and validates that logs and guest metrics arrive in CloudWatch. Configuration should explicitly control log groups, streams, retention, dimensions, and metric cardinality.

## Exam Alignment

- **Primary SCS-C03 Domain:** Detection
- **Secondary Domain(s):** Incident Response
- **Main AWS Services:** Amazon CloudWatch, CloudWatch Logs, AWS Systems Manager, Amazon EC2
- **Lesson Type:** Demonstration / Troubleshooting
- **Exam Importance:** High
- **Core Skill:** Configure, start, and validate telemetry collection from an EC2 guest.

## Demonstration Goal

Publish three system/application logs and selected guest metrics, then confirm searchable evidence and useful metric dimensions.

## Prerequisites

- Completed Part 1 instance, role, package, file-access, and network setup.
- Approved log-group names, encryption, retention, and metric namespace.

## Demonstration Steps

1. Run the configuration wizard or author reviewed agent JSON specifying the three file paths, log groups, stream names, timestamps, and selected metrics.
2. Avoid high-cardinality dimensions such as request IDs or unbounded process values.
3. Store configuration in a protected local file or Parameter Store path; grant the instance read access only to its approved parameter.
4. Fetch and start the configuration using the agent control utility or Systems Manager.
5. Generate controlled SSH and HTTP activity so each log source receives new events.
6. Inspect CloudWatch Logs, the `CWAgent` namespace (unless changed), and agent status/log files.

## Validation

- Expected log groups and streams contain fresh events from the instance.
- Guest metrics such as memory or disk usage appear with intended dimensions.
- Retention and KMS settings match policy.
- Agent logs contain no persistent delivery errors.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Agent not running | Invalid JSON or startup error | Query agent status and inspect its local log | Correct configuration and restart |
| One file absent | Wrong path or read permission | Inspect filesystem and agent log | Correct path/permissions |
| Access denied | Role or KMS/log-group policy issue | Review agent errors and CloudTrail | Add narrow permission/key authorization |
| Unexpected cost | Too many metrics/dimensions or logs | Inspect namespace, dimensions, ingestion | Reduce cardinality and noisy collection |

## Cleanup

Stop the lab instance or agent, remove lab-only log groups and parameters only after confirming retention requirements, and detach/delete the role only if no other resource uses it.

## What the Demonstration Proves

Default EC2 metrics do not expose all guest state. The CloudWatch agent closes that visibility gap, while IAM, retention, encryption, and dimension design determine whether the telemetry is secure and sustainable.

## Quick Review

- Validate logs and metrics independently.
- Set retention explicitly.
- Control metric cardinality.
- Use agent and CloudTrail evidence for failures.
- Protect configurations and KMS access.

## Self-Check Questions

1. Why might CPU metrics exist while memory usage does not?

<details><summary>Answer</summary>

EC2 publishes common hypervisor-visible metrics, while guest memory normally requires the CloudWatch agent or custom publication.

</details>
