# Exam Walkthrough: Inspector, Config, CloudTrail, and Shield

## Overview

This walkthrough selects services for two distinct requirements: find vulnerabilities and unintended network exposure affecting Amazon EC2, and evaluate AWS resource configurations against compliance rules over time. Amazon Inspector addresses the first requirement; AWS Config addresses the second.

## Exam Alignment

- **Primary SCS-C03 Domain:** Detection
- **Secondary Domain(s):** Security Foundations and Governance
- **Main AWS Services:** Amazon Inspector, AWS Config, AWS CloudTrail, AWS Shield
- **Lesson Type:** Architecture
- **Exam Importance:** High
- **Core Skill:** Choose a detection or governance service by the evidence it analyzes and the outcome it produces.

## Service Distinctions

| Service | Primary Role | Why It Fits or Does Not Fit |
| --- | --- | --- |
| Amazon Inspector | Continuous vulnerability management for supported compute resources; EC2 network reachability findings | Fits vulnerability and exposed-path assessment. |
| AWS Config | Records supported resource configuration and evaluates AWS Config rules | Fits configuration history and compliance evaluation. |
| AWS CloudTrail | Records supported account activity and API events | Provides who/what/when evidence but does not perform vulnerability scanning. |
| AWS Shield | Managed distributed denial-of-service protection | Protects against DDoS; it is not a vulnerability scanner or configuration recorder. |

## How It Works

Amazon Inspector evaluates supported compute workloads and produces findings. For EC2, package-vulnerability scanning can use agent-based collection through AWS Systems Manager or agentless scanning through Amazon EBS snapshots. Inspector also generates EC2 network-reachability findings by analyzing network paths.

AWS Config records configuration items for supported resources. AWS Config rules evaluate those configurations and assign states such as `COMPLIANT` or `NON_COMPLIANT`. Configuration and compliance timelines support historical investigation. CloudTrail events can complement Config by identifying API activity associated with a change.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| No EC2 package findings | EC2 scanning is disabled or the selected scan method cannot collect inventory | Check Inspector coverage and scan status | Enable coverage and correct Systems Manager or agentless prerequisites. |
| No historical configuration | Resource type or recorder was not enabled during the period | Review Config recorder scope and delivery status | Record the required resource types and configure delivery. |
| Need the actor behind a change | Config shows state but not complete API-event context | Correlate the timeline with CloudTrail | Query the relevant CloudTrail event history or trail logs. |

## Common Exam Traps

- CloudTrail records activity; it does not continuously assess package vulnerabilities.
- AWS Config evaluates configuration, not software packages inside every workload.
- Shield addresses DDoS risk, not general compliance.
- Detection does not equal remediation; route findings into a response workflow when action is required.

## Memory Hooks

> **Inspector finds compute exposure; Config judges configuration; CloudTrail records actions; Shield absorbs DDoS.**

## Quick Review

- Use Inspector for supported workload vulnerabilities and EC2 network reachability.
- Use Config for configuration history and rule-based compliance.
- Use CloudTrail for API and account-activity evidence.
- Use Shield for DDoS protection.
- Match the service to the requested output, not merely to the word “security.”
