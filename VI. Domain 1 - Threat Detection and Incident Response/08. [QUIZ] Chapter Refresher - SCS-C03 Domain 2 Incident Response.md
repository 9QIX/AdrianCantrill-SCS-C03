### Question 1 – Compromised Lambda function containment

A fintech company receives an Amazon GuardDuty Lambda Protection finding showing that a production AWS Lambda function is making network connections to a known cryptocurrency mining pool. The function is invoked by an Amazon SQS event source mapping. The security team must stop the malicious activity immediately while preserving the function code and configuration for forensic analysis. Which actions should a security engineer take? (Select TWO.)

- **A.** Delete the function and redeploy it from the last known good artifact in the CI/CD pipeline.
- **B.** Set the function's reserved concurrency to 0 so that all invocations are throttled.
- **C.** Enable AWS X-Ray active tracing on the function to block the outbound connections.
- **D.** Retrieve the deployment package by using the GetFunction API and store it, together with the function configuration, in the forensic evidence bucket.
- **E.** Rotate the AWS KMS key that encrypts the function's environment variables.

<details>
<summary>Show answer and explanation</summary>

**Answer: B, D**

✅ **B.** Set the function's reserved concurrency to 0 so that all invocations are throttled.

Reserved concurrency of 0 makes Lambda throttle every invocation, so the SQS event source mapping can no longer run the malicious code, and the effect is immediate. Nothing is deleted or changed in the code, so the evidence stays intact and the setting is easy to reverse later.

✅ **D.** Retrieve the deployment package by using the GetFunction API and store it, together with the function configuration, in the forensic evidence bucket.

GetFunction returns a presigned URL for the exact deployment package plus the full function configuration (environment variables, execution role, layers, VPC settings). Saving both to the forensic bucket preserves the code and configuration the team must keep before any eradication step.

**Summary:** Setting reserved concurrency to 0 throttles every invocation, which stops the malicious code from running without deleting anything. GetFunction returns a presigned URL for the deployment package and the full configuration, so the code, environment settings, and execution role reference can be preserved as evidence before any eradication step.

❌ **A.** Delete the function and redeploy it from the last known good artifact in the CI/CD pipeline.

Deleting the function destroys the code and configuration evidence the team must preserve.

❌ **C.** Enable AWS X-Ray active tracing on the function to block the outbound connections.

X-Ray tracing only records request and trace data for analysis; it has no ability to block outbound connections, so the mining traffic and the invocations would continue.

❌ **E.** Rotate the AWS KMS key that encrypts the function's environment variables.

Rotating the KMS key only changes the key material used for future encryption of environment variables; the function keeps being invoked and the malicious code keeps running.

</details>

### Question 2 – KMS key scheduled deletion recovery

A retail company's AWS CloudTrail logs show that an attacker using a compromised administrator role called ScheduleKeyDeletion on a customer managed AWS KMS key. The key encrypts an Amazon RDS database and objects in Amazon S3. The waiting period is 7 days, and the attacker's access has already been revoked. The company must restore normal use of the key as quickly as possible. What should a security engineer do?

- **A.** Import the original key material into a new KMS key that uses the same key ID.
- **B.** Create a new customer managed key and re-encrypt the RDS database and S3 objects with it before the waiting period ends.
- **C.** Call CancelKeyDeletion on the key, and then call EnableKey because the key returns in the Disabled state.
- **D.** Call CancelKeyDeletion on the key. The key immediately returns to the Enabled state and no further action is required.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Call CancelKeyDeletion on the key, and then call EnableKey because the key returns in the Disabled state.

CancelKeyDeletion is the only way to recover a key in PendingDeletion, and it works at any time during the 7-day waiting period. Because the cancelled key comes back Disabled, EnableKey is the required second step before RDS and S3 can decrypt with it again, which gives the fastest full restore.

**Summary:** A KMS key in the PendingDeletion state can be recovered with CancelKeyDeletion at any time during the waiting period. After cancellation the key is Disabled, not Enabled, so EnableKey must be called before RDS and S3 can use it for cryptographic operations again.

❌ **A.** Import the original key material into a new KMS key that uses the same key ID.

Key IDs cannot be reused, and this key uses AWS-generated key material that cannot be exported or imported.

❌ **B.** Create a new customer managed key and re-encrypt the RDS database and S3 objects with it before the waiting period ends.

A key pending deletion cannot be used to decrypt, so the data cannot be re-encrypted under a new key, and this is far slower than canceling deletion.

❌ **D.** Call CancelKeyDeletion on the key. The key immediately returns to the Enabled state and no further action is required.

After cancellation the key is in the Disabled state, so services still cannot use it until EnableKey is called.

</details>

### Question 3 – Revoking role sessions - why the attacker returned

An IAM role named BuildRole is assumed by an IAM user whose long-term access keys are stored on a contractor's laptop. After detecting malicious activity from BuildRole sessions, a security engineer uses the IAM console option to revoke active sessions for the role, which attaches the following inline policy. Twenty minutes later, CloudTrail shows new API calls from the attacker's IP address that use a new BuildRole session.
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": ["*"],
      "Resource": ["*"],
      "Condition": {
        "DateLessThan": {"aws:TokenIssueTime": "2026-09-10T14:05:00Z"}
      }
    }
  ]
}
```
What is the MOST likely reason the attacker regained access?

- **A.** The policy denies only sessions issued before the timestamp, and the attacker still holds the IAM user's long-term keys, which the role trust policy allows to assume the role again.
- **B.** Inline deny policies on a role can take up to 24 hours to propagate to all AWS Regions.
- **C.** Explicit deny statements in a role's permissions policy do not apply to sessions created with AssumeRole.
- **D.** The condition key must be aws:CurrentTime instead of aws:TokenIssueTime for the deny to take effect.

<details>
<summary>Show answer and explanation</summary>

**Answer: A**

✅ **A.** The policy denies only sessions issued before the timestamp, and the attacker still holds the IAM user's long-term keys, which the role trust policy allows to assume the role again.

The aws:TokenIssueTime revocation deny only matches sessions issued before the timestamp, so a session created afterward is not affected. The attacker still holds the IAM user's long-term keys, and the trust policy still lets that user call AssumeRole, so a fresh session works until the source keys are deactivated or the trust policy is tightened.

**Summary:** The revocation policy denies only credentials whose token was issued before the specified time, so any new session created afterward is unaffected. Because the source IAM user's access keys are still valid and trusted by the role, the attacker simply assumed the role again. The source credentials must also be deactivated, or the trust policy tightened, to complete containment.

❌ **B.** Inline deny policies on a role can take up to 24 hours to propagate to all AWS Regions.

IAM changes are eventually consistent within seconds to minutes, not 24 hours, and the new session was issued after the timestamp anyway.

❌ **C.** Explicit deny statements in a role's permissions policy do not apply to sessions created with AssumeRole.

Explicit denies in a role's permissions policies always apply to that role's sessions; the deny did block the old sessions, but the new session was issued after the timestamp so the condition did not match it.

❌ **D.** The condition key must be aws:CurrentTime instead of aws:TokenIssueTime for the deny to take effect.

aws:TokenIssueTime is the correct key for revoking older sessions; a DateLessThan test on aws:CurrentTime would not target sessions by issue time.

</details>

### Question 4 – IAM user temporary credentials persist after key deletion

A security engineer deleted the access keys of an IAM user after the keys were found on a public paste site. An hour later, CloudTrail still shows API calls attributed to the same IAM user from an unknown IP address. The accessKeyId in these events begins with ASIA. What should the engineer do to stop this activity immediately?

- **A.** Delete the IAM user's console login profile.
- **B.** Attach an inline policy to the IAM user that denies all actions when aws:TokenIssueTime is earlier than a timestamp set to the time the policy is applied.
- **C.** Take no further action, because temporary credentials derived from a deleted access key become invalid and the events are delayed CloudTrail deliveries.
- **D.** Remove the IAM user from all of its IAM groups.

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** Attach an inline policy to the IAM user that denies all actions when aws:TokenIssueTime is earlier than a timestamp set to the time the policy is applied.

ASIA keys are temporary credentials (most likely from GetSessionToken) that inherit the IAM user's permissions, and those permissions are evaluated on every request. A deny-all policy conditioned on aws:TokenIssueTime earlier than now takes effect immediately and blocks every token issued before it, without waiting up to 36 hours for them to expire.

**Summary:** ASIA-prefixed keys are temporary credentials, which the attacker likely obtained with GetSessionToken before the long-term key was deleted. Temporary credentials remain valid until they expire (up to 36 hours for GetSessionToken), but their permissions are evaluated on every request. Because they inherit the user's permissions, a deny policy attached to the user that targets tokens issued before the policy was applied blocks them immediately.

❌ **A.** Delete the IAM user's console login profile.

The login profile controls console password access and has no effect on temporary API credentials.

❌ **C.** Take no further action, because temporary credentials derived from a deleted access key become invalid and the events are delayed CloudTrail deliveries.

Temporary credentials stay valid until expiration; deleting the originating access key does not revoke them, so only a permissions change stops their use.

❌ **D.** Remove the IAM user from all of its IAM groups.

Removing group memberships leaves any policies attached directly to the user in place, so the session may still have access.

</details>

### Question 5 – AWS Health exposed-credential automation troubleshooting

A company operates only in the eu-central-1 Region. It created an Amazon EventBridge rule in eu-central-1 that matches AWS Health events with the eventTypeCode AWS_RISK_CREDENTIALS_EXPOSED. When AWS later reported an exposed access key for the account, the state machine never ran. The event pattern syntax is valid. What is the MOST likely cause?

- **A.** AWS Health sends exposed-credential notifications only through AWS Support cases and email, never to EventBridge.
- **B.** EventBridge cannot invoke Step Functions directly, so an AWS Lambda function is required between the rule and the state machine.
- **C.** AWS Health organizational view must be enabled before any Health events are delivered to EventBridge.
- **D.** AWS_RISK_CREDENTIALS_EXPOSED is a global AWS Health event that is delivered to EventBridge in the US East (N. Virginia) Region, so the rule must also exist in us-east-1.

<details>
<summary>Show answer and explanation</summary>

**Answer: D**

✅ **D.** AWS_RISK_CREDENTIALS_EXPOSED is a global AWS Health event that is delivered to EventBridge in the US East (N. Virginia) Region, so the rule must also exist in us-east-1.

AWS_RISK_CREDENTIALS_EXPOSED is a global AWS Health event, and global Health events are delivered to EventBridge in us-east-1, not in the account's workload Region. A rule deployed only in eu-central-1 never sees the event, so the rule and its Step Functions target must also be created in us-east-1.

**Summary:** Global AWS Health events such as AWS_RISK_CREDENTIALS_EXPOSED are not tied to a workload Region and are delivered to EventBridge in US East (N. Virginia). A rule that exists only in eu-central-1 never receives them, so the rule and target integration must be deployed in us-east-1.

AWS Health events, including AWS_RISK_CREDENTIALS_EXPOSED, are delivered to EventBridge, so this is not why the state machine never ran; the rule was in the wrong Region.

❌ **B.** EventBridge cannot invoke Step Functions directly, so an AWS Lambda function is required between the rule and the state machine.

Step Functions state machines are a supported direct EventBridge target, so no Lambda function is required; adding one would not fix a rule that never receives the event.

❌ **C.** AWS Health organizational view must be enabled before any Health events are delivered to EventBridge.

Organizational view only aggregates Health events across accounts; account-level events reach EventBridge without it, so enabling it would not make the eu-central-1 rule fire.

### Question 10 – Immutable forensic evidence storage

A forensics team stores memory dumps, disk images, and log exports in an Amazon S3 bucket in a dedicated forensic account. Legal counsel requires that no one, including the root user of the forensic account, can alter or delete the evidence for 3 years, and that the integrity of each artifact can be demonstrated in court. Which actions meet these requirements? (Select TWO.)

- **A.** Create the bucket with S3 Object Lock enabled, and configure a default retention period of 3 years in compliance mode.
- **B.** Configure S3 Object Lock in governance mode with a 3-year retention period, and restrict the s3:BypassGovernanceRetention permission.
- **C.** Enable MFA delete on the bucket and store the root user's MFA device in a safe.
- **D.** Configure an S3 Lifecycle rule to move all evidence to S3 Glacier Deep Archive immediately after upload.
- **E.** Compute a SHA-256 hash of each artifact at acquisition, record it in a chain-of-custody log, and upload with the S3 SHA-256 additional checksum so the value can be verified later.

<details>
<summary>Show answer and explanation</summary>

**Answer: A, E**

✅ **A.** Create the bucket with S3 Object Lock enabled, and configure a default retention period of 3 years in compliance mode.

Object Lock in compliance mode means no user, including the root user, can delete or overwrite a locked object version or shorten its retention until the 3 years pass. That is the strongest built-in immutability S3 offers and directly meets the legal requirement.

✅ **E.** Compute a SHA-256 hash of each artifact at acquisition, record it in a chain-of-custody log, and upload with the S3 SHA-256 additional checksum so the value can be verified later.

A SHA-256 hash recorded at acquisition in a chain-of-custody log gives an independent reference value, and the S3 additional checksum stores a SHA-256 value that S3 verifies on upload and that can be retrieved later. Recomputing and comparing the hash shows the artifact has not changed since collection, which is what a court needs.

**Summary:** Compliance-mode Object Lock prevents any user, including the root user, from overwriting or deleting protected object versions or shortening retention until the period ends. Hashing each artifact at acquisition and verifying it later proves the evidence has not changed since it was collected.

❌ **B.** Configure S3 Object Lock in governance mode with a 3-year retention period, and restrict the s3:BypassGovernanceRetention permission.

Governance mode can be bypassed by principals with s3:BypassGovernanceRetention, and the root user can grant that permission.

❌ **C.** Enable MFA delete on the bucket and store the root user's MFA device in a safe.

MFA delete protects version deletion but can be disabled by the root user and does not provide retention-based immutability.

❌ **D.** Configure an S3 Lifecycle rule to move all evidence to S3 Glacier Deep Archive immediately after upload.

Moving objects to S3 Glacier Deep Archive only changes storage class and cost; the objects can still be deleted, and nothing proves they are unaltered.

</details>

The analysis instance must have no internet access, analysts must connect through AWS Systems Manager Session Manager without inbound ports, and the instance must write reports only to the evidence bucket. Which network design meets these requirements?

- **A.** Launch the instance in a public subnet with a security group that allows SSH only from the analysts' corporate IP range.
- **B.** Launch the instance in a private subnet of a VPC with no internet gateway or NAT gateway, create interface endpoints for ssm, ssmmessages, and ec2messages, and create an S3 gateway endpoint whose policy allows access only to the evidence bucket.
- **C.** Launch the instance in a private subnet that routes through a NAT gateway, with a security group that has no inbound rules.
- **D.** Launch the instance in a private subnet with no VPC endpoints, because Session Manager and Amazon S3 are reached through the AWS internal network automatically.

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** Launch the instance in a private subnet of a VPC with no internet gateway or NAT gateway, create interface endpoints for ssm, ssmmessages, and ec2messages, and create an S3 gateway endpoint whose policy allows access only to the evidence bucket.

With no internet gateway or NAT gateway the instance has no path to the internet. Interface endpoints for ssm, ssmmessages, and ec2messages let the SSM Agent reach Systems Manager privately, so Session Manager works without inbound ports, and the S3 gateway endpoint policy limits access to the evidence bucket only.

**Summary:** Without an internet gateway or NAT gateway the instance has no internet path. The Systems Manager interface endpoints allow Session Manager connections with no inbound rules, and an S3 gateway endpoint policy limits writes to the evidence bucket.

❌ **A.** Launch the instance in a public subnet with a security group that allows SSH only from the analysts' corporate IP range.

A public subnet with an SSH rule needs an inbound port and gives the instance an internet path, which breaks both the no-internet and no-inbound-port requirements.

❌ **C.** Launch the instance in a private subnet that routes through a NAT gateway, with a security group that has no inbound rules.

A NAT gateway gives the instance outbound internet access, which violates the requirement that the analysis instance has no internet access.

❌ **D.** Launch the instance in a private subnet with no VPC endpoints, because Session Manager and Amazon S3 are reached through the AWS internal network automatically.

Without endpoints or an internet path, the SSM Agent and S3 clients cannot reach the service endpoints.

### Question 27 – Compromised root user response

A company's standalone AWS account, not in AWS Organizations, shows a root user sign-in from an unfamiliar country, followed by the creation of a new IAM user with AdministratorAccess. The company still controls the root user email address. Which actions should the company take immediately? (Select THREE.)

- **A.** Use the root password recovery process through the root email address to reset the password, and then sign in and replace the root MFA device.
- **B.** Close the AWS account and create a new one to eliminate any persistence.
- **C.** Delete any root user access keys, review CloudTrail for actions by the root user and the new identities, and remove unauthorized IAM users, roles, access keys, and resources.
- **D.** Open an Amazon GuardDuty case so that GuardDuty resets the root credentials.
- **E.** Contact AWS Support to report the compromise and get help with any unauthorized charges or resources.
- **F.** Enable IAM Access Analyzer to block the root user from making further changes.

<details>
<summary>Show answer and explanation</summary>

**Answer: A, C, E**

✅ **A.** Use the root password recovery process through the root email address to reset the password, and then sign in and replace the root MFA device.

The attacker is using the root user, and the company still controls the root email address, so password recovery lets it take back the credentials. Replacing the MFA device removes any device the attacker may have registered, ending the attacker's primary access.

✅ **C.** Delete any root user access keys, review CloudTrail for actions by the root user and the new identities, and remove unauthorized IAM users, roles, access keys, and resources.

The attacker may have created root access keys and has already created an administrator IAM user for persistence. Deleting root keys, reviewing CloudTrail for everything the root user and new identities did, and removing unauthorized users, roles, keys, and resources eradicates that persistence.

✅ **E.** Contact AWS Support to report the compromise and get help with any unauthorized charges or resources.

AWS Support can help secure a compromised account and review charges from resources the attacker launched. Reporting early is part of AWS guidance for a suspected account compromise.

**Summary:** Regaining control of the root credentials and adding new MFA removes the attacker's primary access. Deleting root access keys and reviewing CloudTrail finds persistence such as the new administrator user. AWS Support can help with account security and charges from unauthorized use.

❌ **B.** Close the AWS account and create a new one to eliminate any persistence.

Closing the account destroys evidence and workloads, is not an immediate containment step, and gives up an account the company can still recover through the root email.

❌ **D.** Open an Amazon GuardDuty case so that GuardDuty resets the root credentials.

GuardDuty is a threat detection service; it cannot open cases or reset the root password, so it does nothing to take back control of the account.

❌ **F.** Enable IAM Access Analyzer to block the root user from making further changes.

IAM Access Analyzer identifies external and unused access but cannot block the root user, so the attacker could keep making changes.

How can the company recover access with the LEAST effort?

- **B.** Attach an SCP to the member account that allows s3:PutBucketPolicy and s3:DeleteBucketPolicy to override the bucket policy.

<details>
<summary>Show answer and explanation</summary>

**Answer: D**

✅ **D.** From the management account or the delegated administrator for root access management, call sts:AssumeRoot for the member account with the S3UnlockBucketPolicy task policy, and delete the bucket policy.

With centralized root access management, the management account or its delegated administrator can call sts:AssumeRoot for the member account using the S3UnlockBucketPolicy task policy. That short-term root session can delete a bucket policy that denies all principals, restoring access without any root password or support case.

**Summary:** Centralized root access management lets the management account or its delegated administrator start a short-term root session in a member account with sts:AssumeRoot, scoped to a task policy. SCPs cannot grant permissions, and they do not override an explicit deny in a bucket policy.

A support case is slower, and a built-in self-service privileged root task already exists.

### Question 30 – Containing a compromised Amazon EKS pod

GuardDuty Runtime Monitoring reports a reverse shell in a pod on an Amazon EKS cluster. The pod belongs to a Deployment with three replicas, and network policy enforcement is enabled in the Amazon VPC CNI. The team must contain the pod's network access immediately, keep the pod running for forensic analysis, and prevent new workloads from being scheduled on the affected node. Which actions meet these requirements? (Select TWO.)

- **A.** Add a quarantine label to the compromised pod and apply a Kubernetes NetworkPolicy that denies all ingress and egress traffic for pods with that label.
- **B.** Delete the compromised pod so that the Deployment replaces it with a clean replica.
- **C.** Scale the Deployment to zero replicas.
- **D.** Cordon the worker node that runs the compromised pod.
- **E.** Delete the managed node group that contains the affected node.

<details>
<summary>Show answer and explanation</summary>

**Answer: A, D**

✅ **A.** Add a quarantine label to the compromised pod and apply a Kubernetes NetworkPolicy that denies all ingress and egress traffic for pods with that label.

With network policy enforcement enabled in the VPC CNI, a deny-all ingress and egress NetworkPolicy that selects a quarantine label cuts the pod off immediately. The pod keeps running, so its memory and filesystem remain available for forensics.

✅ **D.** Cordon the worker node that runs the compromised pod.

Cordoning marks the node unschedulable, so no new pods are placed on a possibly compromised host. Unlike draining, it does not evict existing pods, so the compromised pod stays in place for analysis.

**Summary:** A deny-all NetworkPolicy selecting the quarantine label cuts the pod's traffic while the pod keeps running for evidence collection. Cordoning the node marks it unschedulable, so no new pods land on a possibly compromised host, and existing pods are not evicted.

❌ **B.** Delete the compromised pod so that the Deployment replaces it with a clean replica.

Deleting the pod destroys its memory and filesystem evidence, which violates the requirement to keep it running for forensic analysis.

❌ **C.** Scale the Deployment to zero replicas.

Scaling to zero terminates every replica, including the compromised pod, so the evidence is lost and the healthy replicas stop serving too.

❌ **E.** Delete the managed node group that contains the affected node.

Deleting the node group terminates the node and all of its pods, destroying the evidence instead of only stopping new scheduling on the node.

</details>

  "detail-type": ["GuardDuty Finding"],

    "severity": ["High"]
  }

Which change will fix the rule?

- **A.** Change the source value to guardduty.amazonaws.com.
- **B.** Change the detail-type value to GuardDuty Finding - High.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Replace the severity filter with numeric matching of [{"numeric": ["&gt;=", 7]}], and add a filter on detail.resource.resourceType equal to Instance.

GuardDuty sends detail.severity as a number, so numeric matching on values of 7 or higher captures High and Critical findings that the string High never matched. Adding detail.resource.resourceType equal to Instance limits the rule to EC2 findings as required.

### Question 32 – Ransomware-resilient backups

A company is concerned that an attacker with administrator credentials in a workload account could delete all backups before encrypting production data. The company must be able to recover even if the workload account and all of its administrators are compromised, with the LEAST operational overhead. Which solution meets these requirements?

- **A.** Increase the retention period of the backup plans that store recovery points in the workload account's backup vault.
- **B.** Use AWS Backup cross-account copy to send recovery points to a vault in a dedicated backup account, and protect that vault with AWS Backup Vault Lock in compliance mode.
- **C.** Apply AWS Backup Vault Lock in governance mode to the vault in the workload account.
- **D.** Use AWS Organizations backup policies to create daily backups in each account's default backup vault.

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** Use AWS Backup cross-account copy to send recovery points to a vault in a dedicated backup account, and protect that vault with AWS Backup Vault Lock in compliance mode.

Cross-account copy places recovery points in a separate backup account that the compromised workload administrators cannot reach. Compliance-mode Vault Lock then prevents anyone, even in the backup account, from deleting recovery points or shortening retention, using managed AWS Backup features with little upkeep.

**Summary:** Copying recovery points to a separate account removes them from the compromised account's control, and compliance-mode Vault Lock prevents anyone from deleting them or shortening retention, even in the backup account. This gives an immutable, isolated recovery source with managed AWS Backup features.

❌ **A.** Increase the retention period of the backup plans that store recovery points in the workload account's backup vault.

Recovery points in the workload account can still be deleted by its compromised administrators.

❌ **C.** Apply AWS Backup Vault Lock in governance mode to the vault in the workload account.

Governance-mode Vault Lock can be removed by users with sufficient IAM permissions, and the vault stays in the compromised account.

❌ **D.** Use AWS Organizations backup policies to create daily backups in each account's default backup vault.

Backup policies automate creation, but the backups stay in vaults the compromised account can control.
