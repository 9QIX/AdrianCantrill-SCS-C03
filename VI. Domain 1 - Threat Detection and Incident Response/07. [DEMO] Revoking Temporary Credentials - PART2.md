# Revoking Temporary Credentials Demo, Part 2: Containment and Recovery

## Overview

This stage compares disruptive containment choices with IAM role-session revocation, then verifies that credentials issued before the cutoff are denied while legitimate instances can obtain newer sessions.

## Exam Alignment

- **Primary SCS-C03 Domain:** Incident Response
- **Secondary Domain(s):** Identity and Access Management
- **Main AWS Services:** AWS IAM, AWS STS, Amazon EC2, AWS CloudTrail, AWS CloudFormation
- **Lesson Type:** Demonstration
- **Exam Importance:** High
- **Core Skill:** Contain older compromised sessions while restoring legitimate role use.

## Core Concepts

- Deleting the shared role or attaching a blanket deny contains access but disrupts every legitimate instance using it.
- Revoke active sessions creates the AWSRevokeOlderSessions inline policy with an aws:TokenIssueTime cutoff.
- The explicit Deny changes authorization for old credentials even though the STS credential strings and expiration remain unchanged.
- New sessions obtained after policy propagation are not matched by the cutoff; the original exposure vector must still be remediated.

## Demonstration Goal

Revoke permissions for the captured role session without permanently deleting a shared production-style role.

## Prerequisites

- Completed Part 1 and recorded session expiration
- Administrative permission including iam:PutRolePolicy on the affected role
- Access to the legitimate lab instance and attacker terminal

## Demonstration Steps

1. Use CloudTrail and the Part 1 evidence to confirm the affected role and preserve the incident timeline.
2. Review the role attachments and assess the blast radius before changing shared permissions.
3. On the role Revoke sessions tab, revoke active sessions and inspect the generated inline Deny and timestamp.
4. Retry the harmless attacker read request and confirm AccessDenied.
5. Verify a legitimate instance obtains a newer session and retains required access after propagation.
6. Remediate the vulnerable application and metadata controls, then empty or terminate lab resources and delete the supplied stack.

## Architecture and Service Relationships

A principal authenticates, AWS builds the request context, and the authorization engine evaluates every applicable policy before the target service permits or denies the operation.

## Policy or Permission Analysis

The generated inline policy denies Action * on Resource * when aws:TokenIssueTime is earlier than the cutoff. It affects all older sessions for that role and overrides the managed-policy allows. It does not target one access key, does not erase credentials, does not apply to new sessions after propagation, and cannot be used for service-linked roles.

Authorization starts with an implicit deny. An applicable allow is required, and any applicable explicit deny overrides it. Service control policies, permissions boundaries, and session policies limit permissions; they do not grant permissions. A role trust policy controls who may assume a role, while its permissions policies control what the resulting session may do. Resource policies and AWS KMS key policies must be evaluated with their service-specific and cross-account rules.

## Detection, Logging, and Evidence

AWS CloudTrail management events provide evidence for IAM and AWS Security Token Service (AWS STS) API activity. For Amazon S3, enable the appropriate data-event logging when object-level evidence is required; management-event history alone is not a complete record of object access.

## Validation

The AWSRevokeOlderSessions policy exists, the old attacker session receives AccessDenied, a session issued after the cutoff works only within the original role permissions, and CloudTrail records response activity.

## Cleanup

After collecting required evidence, remediate the lab vulnerability, empty any deletion-protected resources, and delete only the named CloudFormation stack. Confirm stack deletion completes.

## What the Demonstration Proves

AWS evaluates session permissions on each request, allowing a time-conditioned explicit deny to contain issued role credentials while newer legitimate sessions recover.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Old session continues to succeed | Policy propagation, wrong role, wrong cutoff, or access through a separate resource-policy session grant | Inspect AWSRevokeOlderSessions, caller ARN, TokenIssueTime, and target resource policy | Correct containment scope and add any necessary resource-side explicit deny |
| Legitimate instance remains denied | It still uses cached old credentials or another deny applies | Compare the credential issue time with the cutoff and inspect CloudTrail | Allow credential refresh after propagation and investigate other policy denies |

## Security Best Practices

- Prefer temporary credentials and roles over long-term access keys.
- Grant least privilege and add conditions that are dependable for the request path.
- Record relevant API activity and periodically review unused or external access.

## Pitfalls and Misconfigurations

- An allow in one policy does not defeat an applicable explicit deny in another.
- A permissions boundary or service control policy limits permissions but never grants them by itself.

## Common Exam Traps

- Do not evaluate a policy document in isolation when service control policies, resource policies, boundaries, session policies, or service-specific rules also apply.
- Authentication establishes an identity; authorization still requires all applicable policies to permit the requested action.

## Self-Check Questions

1. What takes precedence when an allow and an applicable explicit deny overlap?

<details>
<summary>Answer</summary>

The explicit deny. An allow is effective only when no applicable explicit deny exists.

</details>

2. What evidence helps explain an IAM or STS API authorization failure?

<details>
<summary>Answer</summary>

The CloudTrail event plus the identity, resource, request attributes, and all applicable policy types.

</details>

3. Do permissions boundaries or service control policies grant permissions?

<details>
<summary>Answer</summary>

No. They define maximum available permissions; an applicable identity- or resource-based allow is still required.

</details>
