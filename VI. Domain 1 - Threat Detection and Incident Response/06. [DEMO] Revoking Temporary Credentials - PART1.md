# Revoking Temporary Credentials Demo, Part 1: Credential Exposure

## Overview

This stage creates a controlled incident in which a vulnerable public web workload exposes EC2 instance-role credentials from instance metadata. It captures the affected role and temporary credential context needed for containment in Part 2.

## Exam Alignment

- **Primary SCS-C03 Domain:** Incident Response
- **Secondary Domain(s):** Infrastructure Security
- **Main AWS Services:** Amazon EC2, EC2 Instance Metadata Service, AWS IAM, AWS STS, AWS CloudFormation
- **Lesson Type:** Demonstration
- **Exam Importance:** High
- **Core Skill:** Recognize an instance-metadata credential incident and preserve facts needed for containment.

## Core Concepts

- An EC2 service role supplies temporary credentials through instance metadata to software on the instance.
- A server-side request forgery or remote-command weakness can turn local metadata reachability into credential theft.
- The stolen credentials represent the instance-role session and remain usable from another host until expiry or authorization containment.
- The incident is not fixed by deleting a local credential file because the exposure path and role-session permissions remain.

## Demonstration Goal

Demonstrate, in an isolated lab, how a vulnerable workload can expose temporary instance-role credentials.

## Prerequisites

- Permission to deploy the supplied stack
- The specified lab Region and two public test endpoints
- An isolated terminal for the simulated attacker
- A plan to continue immediately to Part 2

## Demonstration Steps

1. Deploy the supplied CloudFormation stack in the specified lab account and Region and wait for CREATE_COMPLETE.
2. Record the two public instance endpoints and the shared instance-role name.
3. Use only the provided simulated vulnerable endpoint to retrieve the role name and temporary credential response from one lab instance.
4. Move to the designated attacker terminal and configure the captured access key ID, secret key, and session token only for this isolated exercise.
5. Call a harmless read operation allowed by the role and record the caller identity and result as evidence for Part 2.
6. Leave the stack running for the next part; do not reuse the credentials elsewhere.

## Architecture and Service Relationships

A principal authenticates, AWS builds the request context, and the authorization engine evaluates every applicable policy before the target service permits or denies the operation.

## Policy or Permission Analysis

The EC2 role trust permits the EC2 service to assume the role; its permissions policies define the stolen session capability. The instance profile delivers the role to EC2. Any applicable organization, resource, or explicit-deny policy still limits the attacker request.

Authorization starts with an implicit deny. An applicable allow is required, and any applicable explicit deny overrides it. Service control policies, permissions boundaries, and session policies limit permissions; they do not grant permissions. A role trust policy controls who may assume a role, while its permissions policies control what the resulting session may do. Resource policies and AWS KMS key policies must be evaluated with their service-specific and cross-account rules.

## Detection, Logging, and Evidence

AWS CloudTrail management events provide evidence for IAM and AWS Security Token Service (AWS STS) API activity. For Amazon S3, enable the appropriate data-event logging when object-level evidence is required; management-event history alone is not a complete record of object access.

## Validation

The read-only AWS call succeeds with the captured temporary session, caller identity maps to the EC2 role session, and the credentials have a visible expiration. No resources are modified by the validation call.

## What the Demonstration Proves

Temporary credentials remove permanent-key management but do not make a compromised workload harmless. IMDSv2, application hardening, egress controls, and least-privilege role policies reduce risk and blast radius.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Captured credentials fail immediately | Incomplete session token, expired credentials, Region mismatch, or an applicable deny | Check expiration, all three credential fields, caller identity, and CloudTrail | Repeat only the controlled capture or correct the lab environment |
| Metadata is unreachable from the lab exploit | IMDSv2 required, endpoint disabled, hop limit, or application path no longer permits access | Inspect instance metadata options and lab stack state | Do not weaken production controls; use only the lab design required to understand the scenario |

## Security Best Practices

- Prefer temporary credentials and roles over long-term access keys.
- Grant least privilege and add conditions that are dependable for the request path.
- Record relevant API activity and periodically review unused or external access.

## Pitfalls and Misconfigurations

- An allow in one policy does not defeat an applicable explicit deny in another.
- A permissions boundary or service control policy limits permissions but never grants them by itself.

## Exam Decision Guide

| Requirement or Clue | Most Likely Service or Control | Why |
| --- | --- | --- |
| Workload needs AWS permissions without stored keys | IAM role | Provides automatically rotated temporary credentials. |
| Need to determine why a request failed | Policy evaluation plus CloudTrail | Reconstructs the request context and all applicable guardrails. |

## Common Exam Traps

- Do not evaluate a policy document in isolation when service control policies, resource policies, boundaries, session policies, or service-specific rules also apply.
- Authentication establishes an identity; authorization still requires all applicable policies to permit the requested action.

### Mental Model

Think of authorization as intersecting gates: the request succeeds only when a grant is present and no applicable gate contributes an explicit deny.

## Self-Check Questions

1. What takes precedence when an allow and an applicable explicit deny overlap?

<details>
<summary>Answer</summary>

The explicit deny. An allow is effective only when no applicable explicit deny exists.

</details>

2. What evidence helps explain an IAM or STS API authorization failure?

<details>
<summary>Answer</summary>

The CloudTrail event plus the identity, resource, request attributes, and all applicable policy types.

</details>

3. Do permissions boundaries or service control policies grant permissions?

<details>
<summary>Answer</summary>

No. They define maximum available permissions; an applicable identity- or resource-based allow is still required.

</details>
