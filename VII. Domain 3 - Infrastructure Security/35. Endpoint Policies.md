# VPC Endpoint Policies

## Overview

This lesson explains VPC Endpoint Policies as an infrastructure-security control. It converts the source lesson into the architecture, decision points, and failure modes most relevant to AWS Certified Security – Specialty (SCS-C03).

The central security objective is to create an intentional network or data path, apply controls at the correct layer, and retain enough evidence to distinguish routing, filtering, identity, encryption, and service-configuration failures.

## Core Concepts

- An endpoint policy is a resource-based policy attached to a VPC endpoint that limits use of that endpoint.
- It does not grant permissions by itself; identity policies and service resource policies must also allow the request.
- An explicit deny in any applicable policy overrides an allow.
- Conditions such as aws:SourceVpce and aws:SourceVpc in supported resource policies can require the expected private path.

## Policy or Permission Analysis

- **Principal:** The IAM identity making the service request; the endpoint policy can scope principals but does not authenticate them.
- **Action and resource:** Both should be narrowed to required API operations and ARNs.
- **Policy type:** The endpoint policy is a resource-based policy on the endpoint and acts alongside identity and destination resource policies.
- **Evaluation:** Default implicit deny applies; an applicable allow is required, and an explicit deny in any applicable policy overrides allows. Service control policies, permissions boundaries, and session policies can further reduce permissions.
- **Cross-account:** Both the caller side and resource-owning side must allow the request, and endpoint conditions must use keys supported by the service.

## Detection, Logging, and Evidence

Use AWS CloudTrail for control-plane changes to AWS PrivateLink. For packet-path questions, enable VPC Flow Logs on the relevant interfaces, subnets, or VPC; flow logs show accepted or rejected IP flows but do not capture packet payloads. Combine service status and metrics with route-table, DNS, policy, and firewall configuration evidence.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Connection times out | Missing route, return path, or filtering rule | Inspect effective routes, security groups, network ACLs, and Flow Logs | Restore symmetric routing and least-privilege traffic rules |
| Access is denied | Identity, resource, endpoint, key, or organization guardrail denies the request | Inspect CloudTrail error context and all applicable policies | Add the required allow or remove the unintended explicit deny |
| Expected private path is unused | DNS or a more-specific route selects another destination | Resolve the hostname and compare the route table with destination addresses | Correct private DNS, endpoint associations, or routes |
| Works in one Availability Zone only | Zonal resource, association, or return path is missing | Compare endpoint/gateway placement and route tables per AZ | Deploy and associate the required zonal components |

## Security Best Practices

- Apply least privilege to management and data-plane access for AWS PrivateLink, Amazon S3, AWS Identity and Access Management.
- Prefer private paths and managed controls when they meet the requirement, but validate both routing and authorization.
- Design across Availability Zones where the service is zonal and the workload requires resilience.
- Log configuration changes and network behavior; alert on unauthorized or high-risk changes.
- Test an explicit denial path so an unnoticed public or uninspected fallback is not mistaken for success.

## Common Exam Traps

- Do not assume that creating AWS PrivateLink automatically updates routes, policies, DNS, or filters unless the service explicitly performs that integration.
- Network reachability is not IAM authorization, and an IAM allow cannot repair a missing route.
- Logging observes activity; it does not automatically prevent or remediate it.
- Regional, Availability Zone, and global scope matter. Place dependencies in the scope required by the service.
- Explicit deny overrides an applicable allow; default behavior is implicit deny where IAM authorization applies.
