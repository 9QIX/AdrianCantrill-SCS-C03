### Question 1 – AWS WAF Bot Control

An online ticket reseller protects its Amazon CloudFront distribution with AWS WAF. Scraper bots are harvesting seat inventory from the /events/\* pages. The bots rotate through thousands of residential IP addresses, send realistic browser User-Agent headers, and do not identify themselves as bots. The company wants a managed solution that detects these bots while keeping WAF costs under control for the rest of the site. Which solution meets these requirements?

- **A.** Add the AWS WAF Bot Control managed rule group with the targeted inspection level, and use a scope-down statement so that only requests to /events/\* are evaluated by the rule group.
- **B.** Add the AWS WAF Bot Control managed rule group with the common inspection level and apply it to all requests to the distribution.
- **C.** Create a rate-based rule that aggregates on source IP address and blocks any address that sends more than 100 requests in 5 minutes to /events/\*.
- **D.** Add the Amazon IP reputation list managed rule group and a custom rule that blocks requests whose User-Agent header contains the string bot.

<details>
<summary>Show answer and explanation</summary>

**Answer: A**

✅ **A.** Add the AWS WAF Bot Control managed rule group with the targeted inspection level, and use a scope-down statement so that only requests to /events/\* are evaluated by the rule group.

The targeted inspection level adds browser interrogation, fingerprinting, and behavioral detection, which catches bots that rotate IPs and fake browser User-Agents. The scope-down statement limits Bot Control evaluation, and its per-request charges, to /events/\*, which keeps WAF costs down for the rest of the site.

**Summary:** The targeted inspection level of Bot Control uses browser interrogation, fingerprinting, and behavioral heuristics to detect sophisticated bots that do not self-identify. A scope-down statement limits evaluation (and the associated per-request charges) to the pages being scraped.

❌ **B.** Add the AWS WAF Bot Control managed rule group with the common inspection level and apply it to all requests to the distribution.

The common level primarily identifies self-identifying and verifiable bots, so it will miss bots that mimic real browsers.

❌ **C.** Create a rate-based rule that aggregates on source IP address and blocks any address that sends more than 100 requests in 5 minutes to /events/\*.

The bots rotate through thousands of residential IP addresses, so each IP stays under a per-IP limit and the rule rarely triggers, while shared legitimate IPs could be blocked.

❌ **D.** Add the Amazon IP reputation list managed rule group and a custom rule that blocks requests whose User-Agent header contains the string bot.

Residential IPs are often not on reputation lists, and the bots send normal browser User-Agent strings, so neither rule will match.

</details>

### Question 2 – AWS WAF Fraud Control ACFP

A fintech startup exposes a sign-up page at /register behind an Application Load Balancer protected by AWS WAF. Attackers are creating thousands of fake accounts by using disposable email addresses and automated scripts to claim a new-customer bonus. The security team wants an AWS managed capability that evaluates registration attempts for fraud signals with the LEAST custom development. Which solution meets these requirements?

- **A.** Add the AWS WAF Fraud Control account takeover prevention (ATP) managed rule group and configure the login path as /register.
- **B.** Add the AWS WAF Fraud Control account creation fraud prevention (ACFP) managed rule group and configure the registration page path, account creation path, and the request field names for username, email, and password.
- **C.** Enable Amazon GuardDuty and create an Amazon EventBridge rule that invokes an AWS Lambda function to delete accounts that GuardDuty flags.
- **D.** Add the AWS Managed Rules core rule set (CRS) and set the SizeRestrictions_BODY rule to Block for the /register path.

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** Add the AWS WAF Fraud Control account creation fraud prevention (ACFP) managed rule group and configure the registration page path, account creation path, and the request field names for username, email, and password.

ACFP is the AWS managed rule group built for fake account creation: it inspects the registration and account creation requests and scores signals such as disposable emails, stolen credentials, and automated clients. It is configured only with paths and field names, so no custom code is needed.

**Summary:** ACFP is purpose-built to detect fraudulent account creation attempts on registration endpoints by inspecting the account creation request fields and client signals. It is configured by specifying the registration and creation paths and the payload field names, so no custom code is needed.

❌ **A.** Add the AWS WAF Fraud Control account takeover prevention (ATP) managed rule group and configure the login path as /register.

ATP protects login endpoints against credential stuffing and account takeover, not fake account creation.

❌ **C.** Enable Amazon GuardDuty and create an Amazon EventBridge rule that invokes an AWS Lambda function to delete accounts that GuardDuty flags.

GuardDuty analyzes AWS telemetry such as CloudTrail, VPC Flow Logs, and DNS logs, and it does not inspect application sign-up requests, so it cannot flag fake registrations; the Lambda deletion flow would also be custom development.

❌ **D.** Add the AWS Managed Rules core rule set (CRS) and set the SizeRestrictions_BODY rule to Block for the /register path.

The CRS protects against common web exploits such as injection and oversized payloads, not registration fraud.

### Question 3 – AWS WAF labels and rule overrides

A media company uses the AWS Managed Rules core rule set (CRS) in its AWS WAF web ACL. The SizeRestrictions_BODY rule blocks legitimate large uploads sent to /api/upload. The security team must keep body size protection for every other path and must not disable the entire managed rule group. Which solution meets these requirements with the LEAST operational overhead?

- **A.** Remove the CRS rule group and write custom rules that replicate every CRS rule except SizeRestrictions_BODY.
- **B.** Add a scope-down statement to the CRS rule group that excludes /api/upload so that no CRS rules evaluate upload requests.
- **C.** Override the SizeRestrictions_BODY rule action to Count, and add a custom rule after the rule group that blocks requests that have the SizeRestrictions_BODY label and whose URI path does not start with /api/upload.
- **D.** Create an IP set containing the upload clients and add an Allow rule for that IP set ahead of the CRS rule group.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Override the SizeRestrictions_BODY rule action to Count, and add a custom rule after the rule group that blocks requests that have the SizeRestrictions_BODY label and whose URI path does not start with /api/upload.

A rule overridden to Count stops blocking but still adds its label to matching requests, so the rest of the CRS keeps working normally. A later custom rule that matches the SizeRestrictions_BODY label and excludes /api/upload keeps size protection on every other path with no custom rule maintenance.

**Summary:** A rule overridden to Count still adds its label to matching requests. A later custom rule can match that label combined with a path condition to block oversized bodies everywhere except the upload path, while all other CRS rules continue to block normally.

❌ **A.** Remove the CRS rule group and write custom rules that replicate every CRS rule except SizeRestrictions_BODY.

Rebuilding the managed rules manually creates large ongoing maintenance and loses AWS updates to the rule group.

❌ **B.** Add a scope-down statement to the CRS rule group that excludes /api/upload so that no CRS rules evaluate upload requests.

A scope-down statement would remove all CRS protections (such as injection checks) from upload requests, not only the size rule.

❌ **D.** Create an IP set containing the upload clients and add an Allow rule for that IP set ahead of the CRS rule group.

Upload clients may use changing IP addresses, and an Allow rule would bypass every CRS rule for those clients.

</details>

### Question 4 – AWS WAF logging

A healthcare company must retain AWS WAF logs in Amazon S3 for audit. To reduce storage costs, only requests that AWS WAF blocked should be stored. Compliance also forbids storing the value of the Authorization header in any log. Which actions should a security engineer take to meet these requirements with the LEAST operational overhead? (Select TWO.)

- **A.** Configure a logging filter in the web ACL logging configuration that keeps only logs where the action is BLOCK and drops all others.
- **B.** Stream all logs to Amazon Data Firehose with an AWS Lambda transformation function that removes allowed requests and the Authorization header.
- **C.** Add the Authorization header as a redacted field in the web ACL logging configuration.
- **D.** Create an S3 bucket named company-waf-audit-logs and select it as the logging destination.
- **E.** Enable AWS CloudTrail data events for AWS WAF and filter on the BlockAction event name.
- **F.** Use sampled requests in the AWS WAF console and export them to S3 on a daily schedule.

<details>
<summary>Show answer and explanation</summary>

**Answer: A, C**

✅ **A.** Configure a logging filter in the web ACL logging configuration that keeps only logs where the action is BLOCK and drops all others.

A web ACL logging filter can keep only records whose action is BLOCK and drop the rest before delivery, which cuts storage costs with a native setting and no code.

✅ **C.** Add the Authorization header as a redacted field in the web ACL logging configuration.

Redacted fields in the logging configuration replace the Authorization header value in every log record, so the sensitive value is never stored. It is a native setting, which meets the least operational overhead requirement.

**Summary:** AWS WAF logging natively supports filters that keep or drop log records based on the rule action, and redacted fields that replace sensitive values such as specific headers. Both are configuration settings, so no custom code is required.

❌ **B.** Stream all logs to Amazon Data Firehose with an AWS Lambda transformation function that removes allowed requests and the Authorization header.

This works, but custom Lambda transformation adds code and operational overhead that native filters and redaction avoid.

❌ **D.** Create an S3 bucket named company-waf-audit-logs and select it as the logging destination.

An S3 logging destination bucket name must begin with aws-waf-logs-, so this bucket cannot be selected.

❌ **E.** Enable AWS CloudTrail data events for AWS WAF and filter on the BlockAction event name.

CloudTrail records AWS WAF management API calls such as UpdateWebACL, not the individual web requests that WAF inspects, so there is no BlockAction event to filter and no request logs to retain.

❌ **F.** Use sampled requests in the AWS WAF console and export them to S3 on a daily schedule.

Sampled requests are a limited sample for a short time window and do not provide complete audit logs.

</details>

<summary>Show answer and explanation</summary>

**Answer: A, C, E**

✅ **A.** AWS Organizations must have all features enabled.

Firewall Manager works only with an organization that has all features enabled, because it relies on trusted access and organization-wide policy management to reach every member account.

An organization trail is good practice for auditing, but Firewall Manager does not use CloudTrail to discover resources or apply policies, so it is not a prerequisite.

**Answer: D**

✅ **D.** Create Amazon Route 53 health checks that reflect application health and associate them with the Shield Advanced protected resources.

Shield Advanced health-based detection uses Route 53 health checks associated with the protected resources. When the application is unhealthy, detection triggers faster at lower thresholds, which catches the latency-degrading attack, and when it is healthy, legitimate spikes are less likely to be flagged.

Firewall Manager manages policies across accounts but is not required for SRT engagement; the SRT creates or updates WAF rules directly through the role associated with Shield Advanced.

### Question 8 – AWS WAF rate-based rule custom keys

A logistics company offers a B2B API through an Application Load Balancer protected by AWS WAF. Each partner sends a unique x-partner-key header. Several large partners send all traffic through a single corporate NAT IP address, so an existing IP-based rate-based rule throttles entire partners when one internal team misbehaves. The company wants to limit each partner key to 2,000 requests per 5 minutes. Which solution meets this requirement?

- **A.** Change the rate-based rule to use a custom aggregation key on the x-partner-key header.
- **B.** Change the rate-based rule to aggregate on the forwarded IP address from the X-Forwarded-For header.
- **C.** Move the API behind Amazon API Gateway and configure a stage-level throttling limit of 2,000 requests.
- **D.** Create one rate-based rule per partner, each with an IP set scope-down statement containing the partner's NAT IP address.

<details>
<summary>Show answer and explanation</summary>

**Answer: A**

✅ **A.** Change the rate-based rule to use a custom aggregation key on the x-partner-key header.

Rate-based rules can aggregate on a custom key such as a specific header. Counting per x-partner-key value limits each partner key to 2,000 requests per 5 minutes on its own, so partners that share a NAT IP address are no longer throttled together.

**Summary:** AWS WAF rate-based rules support custom aggregation keys, including a specific request header. Aggregating on x-partner-key counts and limits each partner key independently regardless of the source IP address.

❌ **B.** Change the rate-based rule to aggregate on the forwarded IP address from the X-Forwarded-For header.

Partners route through a single NAT, so the forwarded IP would still be the same shared address.

❌ **C.** Move the API behind Amazon API Gateway and configure a stage-level throttling limit of 2,000 requests.

A stage-level throttle applies to all clients combined and requires re-architecting the API.

❌ **D.** Create one rate-based rule per partner, each with an IP set scope-down statement containing the partner's NAT IP address.

Per-partner IP rules still aggregate by IP and require constant maintenance as partners change or grow.

</details>

### Question 10 – Amazon CloudFront field-level encryption

A travel booking site uses Amazon CloudFront in front of a fleet of microservices. The checkout form posts a passport number field that must be readable only by the identity-verification microservice. Other services behind the origin, including logging and analytics components, must never see the plaintext value, even though they process the same request. Which solution meets these requirements?

- **A.** Configure an HTTPS-only viewer protocol policy and an HTTPS origin protocol policy on the distribution.
- **B.** Configure AWS WAF on the distribution with a rule that redacts the passport number field before forwarding.
- **C.** Configure CloudFront field-level encryption with a public key for the passport number field, and give only the identity-verification microservice access to the private key.
- **D.** Encrypt the passport number in the origin application by using an AWS KMS customer managed key after the request arrives.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Configure CloudFront field-level encryption with a public key for the passport number field, and give only the identity-verification microservice access to the private key.

Field-level encryption encrypts the passport number at the CloudFront edge with a public key, so the value stays encrypted as it passes through every origin component. Only the identity-verification service holds the private key and can decrypt it, which keeps logging and analytics from seeing plaintext.

**Summary:** Field-level encryption encrypts specified POST fields at the edge with a public key, so the value stays encrypted through the entire origin stack. Only the component that holds the private key can decrypt it.

❌ **A.** Configure an HTTPS-only viewer protocol policy and an HTTPS origin protocol policy on the distribution.

End-to-end HTTPS protects data in transit, but every component that terminates TLS at the origin can still read the plaintext field.

❌ **B.** Configure AWS WAF on the distribution with a rule that redacts the passport number field before forwarding.

AWS WAF inspects requests and does not redact or encrypt request fields for downstream services.

❌ **D.** Encrypt the passport number in the origin application by using an AWS KMS customer managed key after the request arrives.

Encrypting after arrival means the plaintext is exposed to the components that handle the request first.

</details>

### Question 11 – CloudFront OAC with SSE-KMS

A company serves assets from an Amazon S3 bucket through Amazon CloudFront with origin access control (OAC). The bucket policy allows s3:GetObject for the cloudfront.amazonaws.com service principal with an AWS:SourceArn condition for the distribution. After the security team changed default bucket encryption to SSE-KMS with a customer managed key and re-uploaded the objects, CloudFront returns 403 errors for every object. What should the security engineer do to resolve the issue?

- **A.** Replace OAC with a legacy origin access identity (OAI) and grant the OAI kms:Decrypt in the bucket policy.
- **B.** Add s3:GetObjectVersion and kms:Decrypt actions to the existing bucket policy statement for the CloudFront service principal.
- **C.** Change the CloudFront origin protocol policy to HTTPS only so that CloudFront can request decryption keys.
- **D.** Add a statement to the KMS key policy that allows the cloudfront.amazonaws.com service principal to perform kms:Decrypt with an AWS:SourceArn condition that matches the distribution ARN.

<details>
<summary>Show answer and explanation</summary>

**Answer: D**

✅ **D.** Add a statement to the KMS key policy that allows the cloudfront.amazonaws.com service principal to perform kms:Decrypt with an AWS:SourceArn condition that matches the distribution ARN.

With SSE-KMS, CloudFront must be allowed to use the key to decrypt objects, and that permission comes from the KMS key policy. Allowing the cloudfront.amazonaws.com principal kms:Decrypt with AWS:SourceArn for the distribution fixes the 403 errors while limiting key use to this one distribution.

**Summary:** With SSE-KMS, the requester must be authorized to use the KMS key, which is controlled by the key policy. OAC supports SSE-KMS when the key policy allows the CloudFront service principal kms:Decrypt, scoped to the specific distribution with AWS:SourceArn.

❌ **A.** Replace OAC with a legacy origin access identity (OAI) and grant the OAI kms:Decrypt in the bucket policy.

OAI does not support SSE-KMS encrypted objects and is a legacy feature, so switching to it would keep the 403 errors and move away from the recommended OAC.

❌ **B.** Add s3:GetObjectVersion and kms:Decrypt actions to the existing bucket policy statement for the CloudFront service principal.

KMS permissions are not granted through an S3 bucket policy; the key policy controls use of the key.

❌ **C.** Change the CloudFront origin protocol policy to HTTPS only so that CloudFront can request decryption keys.

The origin protocol policy only controls whether CloudFront connects to the origin over HTTP or HTTPS; it has no effect on KMS authorization, so the 403 errors remain.

</details>

### Question 12 – Amazon CloudFront VPC origins

A company runs a web application on an Application Load Balancer (ALB) in front of Amazon EC2 instances. Amazon CloudFront with AWS WAF is the only intended entry point. A penetration test showed that attackers can bypass CloudFront by sending requests directly to the internet-facing ALB. - **C.** Keep the internet-facing ALB and configure CloudFront to add a secret custom header that an ALB listener rule validates, rotating the secret with AWS Secrets Manager.
- **D.** Associate an AWS WAF web ACL with the ALB that allows only an IP set of CloudFront edge IP ranges, updated by a scheduled AWS Lambda function.

<details>
<summary>Show answer and explanation</summary>

**Answer: A**

✅ **A.** Recreate the ALB as an internal ALB in private subnets and configure it as a CloudFront VPC origin.

CloudFront VPC origins deliver traffic to an internal ALB in private subnets, so the ALB has no public IP address and cannot be reached directly from the internet. That removes the bypass completely, with no secret headers or IP lists to maintain.

- **E.** Disable AWS Systems Manager Session Manager and SSH on the instance.
- **F.** Encrypt the instance's EBS volumes with a customer managed KMS key.

<summary>Show answer and explanation</summary>

**Answer: A, C**

✅ **A.** Run the decryption application in an AWS Nitro Enclave that communicates with the parent instance only through the vsock channel.

A Nitro Enclave is an isolated environment with no persistent storage, no interactive access, and no external networking, and it is isolated even from root on the parent instance. Talking only over vsock keeps plaintext inside the enclave.

✅ **C.** Add a condition to the KMS key policy that requires the enclave attestation document, such as kms:RecipientAttestation:ImageSha384 matching the approved enclave image measurement.

KMS attestation condition keys such as kms:RecipientAttestation:ImageSha384 make KMS use the key only for an enclave whose signed attestation document matches the approved image measurement. This ties decryption to the approved application image.

**Summary:** Nitro Enclaves create isolated compute environments with no persistent storage, interactive access, or external networking, isolated even from the parent instance's root user. KMS key policy attestation conditions ensure the key can be used only by an enclave whose signed measurements match the approved image.

❌ **B.** Launch the instance on an EC2 Dedicated Host so that no other customers share the hardware.

Dedicated Hosts isolate the hardware from other AWS customers but give no isolation from administrators with root access on the instance itself.

❌ **D.** Move the keys to AWS CloudHSM and allow the parent instance's IAM role to call the HSM directly.

CloudHSM access from the parent instance would still expose plaintext to parent instance administrators.

❌ **E.** Disable AWS Systems Manager Session Manager and SSH on the instance.

Removing access paths does not isolate the processing from root users who already have access.

❌ **F.** Encrypt the instance's EBS volumes with a customer managed KMS key.

EBS encryption protects data at rest on the volume, but decrypted cardholder data in the instance's memory is still readable by root on the running instance.

### Question 40 – Instance credential exfiltration prevention

GuardDuty reported an UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS finding: temporary credentials from an EC2 instance role were used from an external IP address. The company wants a preventive control that stops EC2 instance role credentials from being used anywhere except from the instance's own VPC, applied centrally with minimal changes to each role. All workloads already reach AWS services through VPC endpoints. Which solution meets these requirements?

- **A.** Require IMDSv2 on all instances in the organization by using a service control policy on ec2:MetadataHttpTokens.
- **B.** Apply a service control policy that denies requests signed with EC2 role credentials when aws:SourceVpc does not equal the aws:Ec2InstanceSourceVpc value, excluding calls made by AWS services on the principal's behalf.
- **C.** Reduce the maximum session duration of each instance profile role to 15 minutes.
- **D.** Create an EventBridge rule that revokes role sessions whenever GuardDuty reports the finding.

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** Apply a service control policy that denies requests signed with EC2 role credentials when aws:SourceVpc does not equal the aws:Ec2InstanceSourceVpc value, excluding calls made by AWS services on the principal's behalf.

aws:Ec2InstanceSourceVpc records the VPC where the role credentials were delivered, and aws:SourceVpc is present for requests made through VPC endpoints. An SCP that denies EC2 role credentials when these do not match, excluding aws:ViaAWSService calls, blocks the credentials from being used outside the VPC, centrally and without editing each role.

**Summary:** The aws:Ec2InstanceSourceVpc key identifies the VPC where EC2 role credentials were delivered. A deny statement that compares it with aws:SourceVpc (which is present only for requests made through a VPC endpoint), limited to EC2 role credentials with ec2:SourceInstanceARN and excluding aws:ViaAWSService calls, blocks use of the credentials from outside that VPC. An SCP applies the control centrally without editing each role.

❌ **A.** Require IMDSv2 on all instances in the organization by using a service control policy on ec2:MetadataHttpTokens.

IMDSv2 reduces the risk of credential theft through SSRF but does not stop stolen credentials from being used elsewhere.

❌ **C.** Reduce the maximum session duration of each instance profile role to 15 minutes.

Instance profile credentials are rotated by EC2, and the role maximum session duration does not control their lifetime.

❌ **D.** Create an EventBridge rule that revokes role sessions whenever GuardDuty reports the finding.

An EventBridge rule that revokes sessions reacts only after GuardDuty sees the misuse, so it is not a preventive control and the stolen credentials work until then.

</details>
