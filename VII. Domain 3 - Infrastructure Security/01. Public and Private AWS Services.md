# Public and Private AWS Service Networking

## Overview

This lesson explains Public and Private AWS Service Networking as an infrastructure-security control. It converts the source lesson into the architecture, decision points, and failure modes most relevant to AWS Certified Security – Specialty (SCS-C03).

The central security objective is to create an intentional network or data path, apply controls at the correct layer, and retain enough evidence to distinguish routing, filtering, identity, encryption, and service-configuration failures.

## Exam Alignment

- **Primary SCS-C03 Domain:** Infrastructure Security
- **Secondary Domain(s):** None
- **Main AWS Services:** Amazon VPC, AWS public service endpoints
- **Lesson Type:** Architecture
- **Exam Importance:** High
- **Core Skill:** Explain, configure, and troubleshoot Public and Private AWS Service Networking without confusing reachability with authorization.

## Core Concepts

- The public internet, the AWS public zone, and VPC private address space are distinct network zones.
- A service can be publicly addressed without being outside the AWS network; public endpoints still require authorization.
- Private VPC resources reach public endpoints through an internet/NAT path or reach supported services privately through VPC endpoints.
- Public reachability, authentication, authorization, and encryption are separate controls.

## Detection, Logging, and Evidence

Use AWS CloudTrail for control-plane changes to Amazon VPC. For packet-path questions, enable VPC Flow Logs on the relevant interfaces, subnets, or VPC; flow logs show accepted or rejected IP flows but do not capture packet payloads. Combine service status and metrics with route-table, DNS, policy, and firewall configuration evidence.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Connection times out | Missing route, return path, or filtering rule | Inspect effective routes, security groups, network ACLs, and Flow Logs | Restore symmetric routing and least-privilege traffic rules |
| Access is denied | Identity, resource, endpoint, key, or organization guardrail denies the request | Inspect CloudTrail error context and all applicable policies | Add the required allow or remove the unintended explicit deny |
| Expected private path is unused | DNS or a more-specific route selects another destination | Resolve the hostname and compare the route table with destination addresses | Correct private DNS, endpoint associations, or routes |
| Works in one Availability Zone only | Zonal resource, association, or return path is missing | Compare endpoint/gateway placement and route tables per AZ | Deploy and associate the required zonal components |

## Security Best Practices

- Apply least privilege to management and data-plane access for Amazon VPC, AWS public service endpoints.
- Prefer private paths and managed controls when they meet the requirement, but validate both routing and authorization.
- Design across Availability Zones where the service is zonal and the workload requires resilience.
- Log configuration changes and network behavior; alert on unauthorized or high-risk changes.
- Test an explicit denial path so an unnoticed public or uninspected fallback is not mistaken for success.

## Common Exam Traps

- Do not assume that creating Amazon VPC automatically updates routes, policies, DNS, or filters unless the service explicitly performs that integration.
- Network reachability is not IAM authorization, and an IAM allow cannot repair a missing route.
- Logging observes activity; it does not automatically prevent or remediate it.
- Regional, Availability Zone, and global scope matter. Place dependencies in the scope required by the service.
- Explicit deny overrides an applicable allow; default behavior is implicit deny where IAM authorization applies.
