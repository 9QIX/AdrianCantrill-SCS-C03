# AWS Shield DDoS Protection

## Overview

This lesson explains AWS Shield DDoS Protection as an infrastructure-security control. It converts the source lesson into the architecture, decision points, and failure modes most relevant to AWS Certified Security – Specialty (SCS-C03).

The central security objective is to create an intentional network or data path, apply controls at the correct layer, and retain enough evidence to distinguish routing, filtering, identity, encryption, and service-configuration failures.

## Exam Alignment

- **Primary SCS-C03 Domain:** Infrastructure Security
- **Secondary Domain(s):** Detection
- **Main AWS Services:** AWS Shield Standard, AWS Shield Advanced, AWS WAF
- **Lesson Type:** Concept
- **Exam Importance:** High
- **Core Skill:** Explain, configure, and troubleshoot AWS Shield DDoS Protection without confusing reachability with authorization.

## Core Concepts

- Shield Standard provides automatic baseline DDoS protection for AWS customers at no additional charge.
- Shield Advanced adds enhanced detection, protected-resource configuration, visibility, specialized response support, and eligible cost-protection features subject to its terms.
- CloudFront, Route 53, and other supported edge architectures reduce exposure before traffic reaches an origin.
- AWS WAF handles application-layer request rules; Shield focuses on DDoS detection and mitigation, and the services are complementary.

## Detection, Logging, and Evidence

Use CloudWatch metrics, AWS WAF logs, load-balancer or CloudFront access logs, and VPC Flow Logs where applicable to characterize an availability event. AWS Shield Advanced customers also receive attack diagnostics and can engage the Shield Response Team under the service's support workflow. CloudTrail records protection and configuration changes; it does not describe every attack packet.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Traffic volume spikes | Legitimate demand, volumetric attack, or scanning | Compare baseline metrics, source patterns, protocol distribution, and application errors | Scale safely and apply the control at the matching network or application layer |
| Layer 7 requests exhaust the application | HTTP request flood bypasses coarse network controls | Review AWS WAF and application logs | Add rate-based or request-specific AWS WAF controls and protect the origin |
| Protected resource is not visible in Shield Advanced | Resource type, account, Region, or protection association is incorrect | Inspect Shield protections and organization configuration | Associate the supported resource and centralize coverage as designed |
## Security Best Practices

- Apply least privilege to management and data-plane access for AWS Shield Standard, AWS Shield Advanced, AWS WAF.
- Prefer private paths and managed controls when they meet the requirement, but validate both routing and authorization.
- Design across Availability Zones where the service is zonal and the workload requires resilience.
- Log configuration changes and network behavior; alert on unauthorized or high-risk changes.
- Test an explicit denial path so an unnoticed public or uninspected fallback is not mistaken for success.

## Common Exam Traps

- Do not assume that creating AWS Shield Standard automatically updates routes, policies, DNS, or filters unless the service explicitly performs that integration.
- Network reachability is not IAM authorization, and an IAM allow cannot repair a missing route.
- Logging observes activity; it does not automatically prevent or remediate it.
- Regional, Availability Zone, and global scope matter. Place dependencies in the scope required by the service.
- Explicit deny overrides an applicable allow; default behavior is implicit deny where IAM authorization applies.

<details>
