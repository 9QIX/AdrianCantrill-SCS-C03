# Amazon S3 Access Points

## Overview

This lesson explains Amazon S3 Access Points as an infrastructure-security control. It converts the source lesson into the architecture, decision points, and failure modes most relevant to AWS Certified Security – Specialty (SCS-C03).

The central security objective is to create an intentional network or data path, apply controls at the correct layer, and retain enough evidence to distinguish routing, filtering, identity, encryption, and service-configuration failures.

## Exam Alignment

- **Primary SCS-C03 Domain:** Infrastructure Security
- **Secondary Domain(s):** Identity and Access Management
- **Main AWS Services:** Amazon S3, Amazon VPC
- **Lesson Type:** Architecture
- **Exam Importance:** High
- **Core Skill:** Explain, configure, and troubleshoot Amazon S3 Access Points without confusing reachability with authorization.

## Core Concepts

- An S3 Access Point supplies a unique hostname and access-point policy for a specific bucket.
- Multiple access points simplify distinct application, team, and network access patterns without one monolithic bucket policy.
- An access point can be restricted to a VPC, and account-level or bucket-level S3 Block Public Access guardrails still apply.
- The access point and underlying bucket authorization interact; an explicit deny remains decisive.

## Detection, Logging, and Evidence

CloudTrail management events record access-point configuration changes; enable the relevant S3 data events when object-level API evidence is required. Use IAM Access Analyzer for S3 and policy review to identify unintended external access. A network-origin restriction is proven by the request context and policy evaluation, not by the access-point name.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Request through an access point is denied | Identity, access-point, bucket, VPC-origin, or organization policy does not allow the request | Inspect the CloudTrail data event and all applicable policies | Add the minimum required allow or remove the unintended explicit deny |
| Request uses the bucket endpoint instead | Application is not using the access-point alias or ARN | Inspect the request host or resource ARN | Configure the client to address the intended access point |
| VPC-only access point fails | Request did not originate through the associated VPC context | Review endpoint, DNS, route, and request context | Use the approved VPC endpoint and access-point path |
## Security Best Practices

- Apply least privilege to management and data-plane access for Amazon S3, Amazon VPC.
- Prefer private paths and managed controls when they meet the requirement, but validate both routing and authorization.
- Design across Availability Zones where the service is zonal and the workload requires resilience.
- Log configuration changes and network behavior; alert on unauthorized or high-risk changes.
- Test an explicit denial path so an unnoticed public or uninspected fallback is not mistaken for success.

## Common Exam Traps

- Do not assume that creating Amazon S3 automatically updates routes, policies, DNS, or filters unless the service explicitly performs that integration.
- Network reachability is not IAM authorization, and an IAM allow cannot repair a missing route.
- Logging observes activity; it does not automatically prevent or remediate it.
- Regional, Availability Zone, and global scope matter. Place dependencies in the scope required by the service.
- Explicit deny overrides an applicable allow; default behavior is implicit deny where IAM authorization applies.

<details>
