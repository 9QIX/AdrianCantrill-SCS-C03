The source exercise uses the same Linux storage workflow against the discovered instance-store device:

```bash
lsblk -f
sudo mkfs -t xfs /dev/nvme1n1
sudo mkdir -p /instance-store
sudo mount /dev/nvme1n1 /instance-store
sudo sh -c 'printf "%s\n" "ephemeral test data" > /instance-store/instance-store.txt'
```

### Line-by-Line Comments

```text
Line 1: Identifies the local instance-store block device and any existing filesystem.
Line 2: Creates an XFS filesystem on the selected empty lab device and destroys prior content.
Line 3: Creates a mount-point directory.
Line 4: Mounts the instance-store filesystem.
Line 5: Creates a file used to test lifecycle persistence.
```

### Code Walkthrough

These commands need guest administrative privileges and do not require AWS API permissions. Confirm the correct local device with `lsblk` before the destructive `mkfs` operation. Reboot the instance and verify the file remains; then stop and start only if the instance type and lab instructions permit it. Data on instance store is lost when the instance is stopped, hibernated, terminated, or its underlying disk fails, so it must never be the sole copy of durable data.

## What the Demonstration Proves

The exercise proves that reboot can preserve instance store; stop/start can move hosts and lose it. It also shows that a successful console configuration is not enough: effective routes, policies, filters, and observed behavior must agree.

## Detection, Logging, and Evidence

AWS CloudTrail records Amazon EC2, Amazon EBS, and AWS KMS API activity, including volume, snapshot, key, principal, Region, and error context. AWS Config can evaluate configuration state, while Amazon CloudWatch exposes volume performance. Correlate these sources when distinguishing a permissions problem from key state, attachment state, or storage performance.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Encrypted volume cannot be attached or used | The instance role or service path cannot use the KMS key, or the key is disabled | Inspect the EC2 and KMS CloudTrail events and key state | Correct the key policy or grant and ensure the key is enabled |
| Snapshot copy fails | The source key cannot be used or the destination key/Region is incorrect | Review snapshot-copy status and KMS permissions in both Regions | Grant the required decrypt/encrypt path and select the intended destination key |
| Volume is attached but the file system is unavailable | Operating-system mount, device mapping, or file-system issue | Inspect EC2 device and OS state | Correct the OS-level configuration without recreating encryption controls |
| I/O is slow | Volume performance limits or instance bandwidth, not encryption itself | Review EBS and EC2 CloudWatch metrics | Select or configure storage and instance performance for the workload |
## Security Best Practices

- Apply least privilege to management and data-plane access for Amazon EBS, Amazon EC2.
- Prefer private paths and managed controls when they meet the requirement, but validate both routing and authorization.
- Design across Availability Zones where the service is zonal and the workload requires resilience.
- Log configuration changes and network behavior; alert on unauthorized or high-risk changes.
- Test an explicit denial path so an unnoticed public or uninspected fallback is not mistaken for success.

## Common Exam Traps

- Do not assume that creating Amazon EBS automatically updates routes, policies, DNS, or filters unless the service explicitly performs that integration.
- Network reachability is not IAM authorization, and an IAM allow cannot repair a missing route.
- Logging observes activity; it does not automatically prevent or remediate it.
- Regional, Availability Zone, and global scope matter. Place dependencies in the scope required by the service.
- Explicit deny overrides an applicable allow; default behavior is implicit deny where IAM authorization applies.
