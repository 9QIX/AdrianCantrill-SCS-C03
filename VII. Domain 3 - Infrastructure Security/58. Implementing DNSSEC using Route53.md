# DNSSEC Signing with Amazon Route 53

## Overview

This lesson explains DNSSEC Signing with Amazon Route 53 as an infrastructure-security control. It converts the source lesson into the architecture, decision points, and failure modes most relevant to AWS Certified Security – Specialty (SCS-C03).

The central security objective is to create an intentional network or data path, apply controls at the correct layer, and retain enough evidence to distinguish routing, filtering, identity, encryption, and service-configuration failures.

## Core Concepts

- DNS Security Extensions (DNSSEC) authenticate DNS data with digital signatures; they do not encrypt DNS queries or responses.
- Route 53 hosted-zone signing uses a key-signing key backed by an asymmetric customer managed KMS key in us-east-1 with required permissions.
- The parent zone must publish a delegation signer (DS) record to establish the chain of trust.
- Enable signing, publish the DS at the registrar or parent, validate with a DNSSEC-aware resolver, and monitor signing-key health before key changes.

```bash
dig +dnssec example.com A
dig +dnssec example.com DS
```

### Line-by-Line Comments

```text
Line 1: Requests the domain's A record and asks the resolver to include DNSSEC records.
Line 2: Requests the delegation signer record that links the parent zone to the child zone's key.
```

### Code Walkthrough

Both commands are read-only DNS queries and require no AWS permissions. Replace `example.com` with the hosted-zone name. Inspect the response for signatures and use a validating resolver to confirm the authenticated chain; the presence of an `RRSIG` alone does not prove that the parent DS is correct. A `SERVFAIL` from validating resolvers after DS publication commonly indicates a broken chain of trust.

## What the Demonstration Proves

The exercise proves that dNSSEC signs answers; the parent DS links trust to the child zone. It also shows that a successful console configuration is not enough: effective routes, policies, filters, and observed behavior must agree.

## Detection, Logging, and Evidence

CloudTrail records Route 53 DNSSEC configuration and key-signing-key API activity. Monitor key-signing-key status, hosted-zone DNSSEC status, and DNS resolution failures. Resolver query logging can help identify queries made through Route 53 Resolver, while an external validating resolver or diagnostic tool is needed to prove the public chain of trust.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Validating resolvers return `SERVFAIL` | Broken delegation signer record, expired/missing signatures, or invalid chain of trust | Trace DNSKEY, DS, and RRSIG records from the parent zone | Correct the parent DS record or signing configuration |
| Key-signing key is not active | AWS KMS key, permissions, or signing-key state is invalid | Inspect Route 53 status and CloudTrail errors | Restore the supported KMS key and required permissions |
| Failure occurs during rollover | Parent and child records were changed in the wrong sequence | Compare old and new DS/DNSKEY publication and TTLs | Restore overlap and complete the rollover in the safe sequence |
## Security Best Practices

- Apply least privilege to management and data-plane access for Amazon Route 53, AWS KMS.
- Prefer private paths and managed controls when they meet the requirement, but validate both routing and authorization.
- Design across Availability Zones where the service is zonal and the workload requires resilience.
- Log configuration changes and network behavior; alert on unauthorized or high-risk changes.
- Test an explicit denial path so an unnoticed public or uninspected fallback is not mistaken for success.

## Common Exam Traps

- Do not assume that creating Amazon Route 53 automatically updates routes, policies, DNS, or filters unless the service explicitly performs that integration.
- Network reachability is not IAM authorization, and an IAM allow cannot repair a missing route.
- Logging observes activity; it does not automatically prevent or remediate it.
- Regional, Availability Zone, and global scope matter. Place dependencies in the scope required by the service.
- Explicit deny overrides an applicable allow; default behavior is implicit deny where IAM authorization applies.
