# CloudFormation Change Sets

## Overview

A CloudFormation change set previews the resource-level actions a proposed stack create or update would perform. It improves review and separation of duties, but it does not guarantee that execution will succeed or that application behavior is safe.

## Exam Alignment

- **Primary SCS-C03 Domain:** Security Foundations and Governance
- **Secondary Domain(s):** Infrastructure Security
- **Main AWS Services:** AWS CloudFormation, IAM, AWS CloudTrail
- **Lesson Type:** Change Review / Troubleshooting
- **Exam Importance:** Medium
- **Core Skill:** Review replacements, deletions, IAM impact, and dynamic evaluation before executing infrastructure changes.

## Configuration or Workflow

1. Submit the revised template and parameters to create a change set.
2. Wait for CloudFormation to calculate proposed actions.
3. Review additions, modifications, removals, replacements, condition effects, and IAM resources.
4. Obtain approval under the organization's change process.
5. Execute the approved change set.
6. Monitor stack events, CloudTrail, resource health, and rollback state.

## Security Implications

- Replacement of a stateful or security-control resource may affect data and availability.
- Broad IAM changes, security-group exposure, logging changes, and encryption-key changes deserve explicit review.
- Dynamic references and runtime values may prevent the preview from showing every final property value.
- Separate permissions for creating and executing change sets can support separation of duties.

## Common Exam Traps

- Creating a change set does not change resources; execution does.
- A change set is a preview, not a policy-compliance engine or success guarantee.
- “Modify” can include replacement details that must be inspected.
- Out-of-band drift can make expected and actual effects differ.

## Memory Hooks

> **Change sets preview intent; execution changes reality; monitoring verifies outcome.**

## Quick Review

- Review replacement and deletion first.
- Inspect IAM, network, logging, and encryption changes.
- Separate creation from execution when approval is required.
- Check drift and dynamic values.
- Monitor execution and rollback.

## Self-Check Questions

1. Does an approved change set guarantee successful deployment?

<details><summary>Answer</summary>

No. Runtime permissions, quotas, service behavior, dependencies, and resource state can still cause failure.

</details>

2. Does a change set guarantee that an update will succeed?

<details>
<summary>Answer</summary>

No. It previews modeled stack changes. Runtime permissions, quotas, service validation, custom resources, and application effects can still fail.

</details>

3. What should be reviewed before executing a security-sensitive change set?

<details>
<summary>Answer</summary>

Review replacements, deletions, IAM changes, policy changes, networking exposure, encryption changes, and the execution role, then use an approval process appropriate to the risk.

</details>
