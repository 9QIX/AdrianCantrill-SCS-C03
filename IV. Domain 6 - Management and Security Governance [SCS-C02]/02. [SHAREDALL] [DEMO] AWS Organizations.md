# Creating and Accessing AWS Organization Member Accounts

## Overview

This lesson demonstrates how to build a basic multi-account AWS environment by:

1. Creating an organization from an existing AWS account.
2. Inviting an existing production account.
3. Creating the required cross-account access role in the invited account.
4. Creating a new development account directly within the organization.
5. Accessing member accounts through temporary role credentials.

The original demonstration uses manual AWS Identity and Access Management (IAM) users and the AWS Management Console **Switch Role** feature. This remains technically valid, but **AWS IAM Identity Center is the current recommended service for centrally managing workforce access across multiple AWS accounts**. ([AWS Documentation][1])

The main security objective is to manage accounts centrally without creating and maintaining separate long-term IAM user credentials in every account.

## Exam Alignment

* **Primary SCS-C03 Domain:** Identity and Access Management
* **Secondary Domain(s):** Security Foundations and Governance
* **Main AWS Services:** AWS Organizations, AWS IAM, AWS Security Token Service (AWS STS), AWS IAM Identity Center
* **Lesson Type:** Demonstration / Architecture / Troubleshooting
* **Exam Importance:** High
* **Core Skill:** Create and access AWS Organization member accounts while distinguishing account invitations, account creation, trust policies, permissions policies, and temporary role credentials.

## Demonstration Goal

Build the following AWS account structure:

```text
AWS Organization
|
+-- Management account: General
|
+-- Member account: Production
|   |
|   +-- Manually created OrganizationAccountAccessRole
|
+-- Member account: Development
    |
    +-- Automatically created OrganizationAccountAccessRole
```

After completing the demonstration:

* The General account is the organization’s management account.
* The existing Production account is an invited member account.
* The Development account is created directly by AWS Organizations.
* Authorized principals can assume administrative roles in the member accounts.
* Cross-account access uses temporary AWS STS credentials instead of separate IAM users in each member account.

## Prerequisites

The original demonstration assumes the following resources already exist:

* A General AWS account.
* A Production AWS account.
* Administrative access to both accounts.
* A unique email address for the Development account.
* Separate authenticated browser sessions for the General and Production accounts.

For a current production design, also consider:

* AWS IAM Identity Center for workforce access.
* Multi-factor authentication (MFA) for privileged identities.
* A dedicated security or identity account.
* Minimal workloads in the management account.
* AWS CloudTrail enabled across the organization.
* Service control policies (SCPs) for organization-wide guardrails.

> The AWS Region selected in the console does not determine where the AWS Organization exists. AWS Organizations is operated as a global service, although some related integrations and services have Regional configuration.

## Core Concepts

### Management Account

The account used to create an AWS Organization becomes its **management account**.

The management account:

* Creates and manages the organization.
* Invites existing AWS accounts.
* Creates new member accounts.
* Manages organizational units (OUs).
* Applies organization policies.
* Is responsible for consolidated billing.
* Has elevated authority over organization administration.

The older term **master account** has been replaced by **management account**.

AWS recommends limiting access to the management account, avoiding application workloads there, and using it only for tasks that require management-account permissions. ([AWS Documentation][2])

### Member Account

A member account is an AWS account that belongs to an organization.

An account can become a member account in two ways:

1. An existing account accepts an invitation.
2. AWS Organizations creates a new account directly inside the organization.

Member accounts remain security and resource isolation boundaries. Each account maintains its own:

* Resources.
* IAM roles and policies.
* Root user.
* Service quotas.
* CloudTrail events.
* Resource policies.
* Encryption resources and keys.
* Network configurations.

### Invited Account Versus Created Account

This distinction is highly exam-relevant.

| Account Onboarding Method                   | Invitation Required | `OrganizationAccountAccessRole` Created Automatically | Initial Access Method                                 |
| ------------------------------------------- | ------------------: | ----------------------------------------------------: | ----------------------------------------------------- |
| Invite an existing account                  |                 Yes |                                                    No | Existing credentials in that account                  |
| Create an account through AWS Organizations |                  No |                                       Yes, by default | Assume the generated role from the management account |

When an existing account joins through an invitation, AWS Organizations **does not automatically create** `OrganizationAccountAccessRole`. It must be created manually when that access model is required. ([AWS Documentation][3])

When AWS Organizations creates a new member account, it creates `OrganizationAccountAccessRole` by default and grants it administrative permissions. Principals in the management account can assume the role when their own permissions permit it. ([AWS Documentation][4])

### IAM Role Switching

Console role switching is a user-interface workflow for calling AWS STS `AssumeRole`.

The process is:

```text
Authenticated principal
in source account
        |
        | sts:AssumeRole
        v
IAM role in target account
        |
        | AWS STS issues temporary credentials
        v
Role session in target account
        |
        v
Actions allowed by the role's permissions
```

The principal does not permanently become the role. AWS STS creates a temporary role session with:

* An access key ID.
* A secret access key.
* A session token.
* An expiration time.

The AWS Management Console manages these temporary credentials during the switched session.

### Authentication Versus Authorization

The source account authenticates the user or workload.

The target account authorizes role assumption through the role’s trust policy.

After assumption, the role’s permissions policies determine what the role session can do.

```text
Authentication:
Who signed in?

Trust policy:
Who may assume the target role?

Source permissions:
May this principal call sts:AssumeRole?

Role permissions:
What may the resulting role session do?

Organization guardrails:
Do SCPs permit the requested action?
```

## How It Works

### 1. Create the AWS Organization

An administrator signs in to the General account and creates an AWS Organization.

That account becomes the management account.

AWS currently recommends creating an organization with **all features** enabled instead of consolidated-billing-only functionality. All features are enabled by default for newly created organizations. ([AWS Documentation][5])

### 2. Verify the Management Account Email

AWS may require verification of the email address associated with the management account.

Verification can be necessary before performing operations such as inviting existing accounts.

### 3. Invite the Production Account

From the management account:

* Specify the Production account ID or associated email address.
* Send an invitation.
* Sign in to the Production account.
* Review and accept the invitation.

Only the management account can send account invitations. The invited account’s administrator can accept or decline the invitation. ([AWS Documentation][6])

### 4. Create Cross-Account Access in the Invited Account

Because Production was invited rather than created by AWS Organizations, the access role is not automatically created.

An administrator in Production creates an IAM role with:

* A trust relationship allowing the General management account to assume it.
* A permissions policy granting the intended target-account permissions.
* The conventional role name `OrganizationAccountAccessRole`, when matching the AWS Organizations default.

### 5. Assume the Production Role

An authorized principal in General initiates a role switch to Production.

AWS evaluates:

1. Whether the target role’s trust policy trusts the source principal or source account.
2. Whether the source principal is allowed to call `sts:AssumeRole`.
3. Whether any applicable SCP, permissions boundary, session policy, or explicit deny blocks the request.

If allowed, AWS STS issues temporary credentials for the Production role.

### 6. Create the Development Account

The administrator creates Development directly through AWS Organizations.

The account requires:

* A unique account name.
* A unique email address.
* An IAM role name, normally `OrganizationAccountAccessRole`.

AWS Organizations creates the account and automatically configures the specified access role. ([AWS Documentation][4])

### 7. Assume the Development Role

An authorized principal in the management account assumes the automatically created role in Development.

The access mechanics are the same as for Production, but no manual role creation was required.

## Configuration or Workflow

## Demonstration Steps

### Step 1: Sign In to the General Account

Sign in to the account that will become the management account.

For the historical workflow, this may be an IAM administrator. In a current environment, privileged access should preferably originate from a federated identity or IAM Identity Center.

**Security control provided:** Establishes an authenticated administrative session.

**Possible failure conditions:**

* The identity lacks permission to create an organization.
* The account is already a member of another organization.
* An SCP or permissions policy blocks Organizations API calls.
* The root email address has not been verified when verification is required.

### Step 2: Create the Organization

Open AWS Organizations and create an organization with all features enabled.

**Why it is required:** The organization becomes the central account-governance boundary.

**Security control provided:** Enables centralized policies, account lifecycle management, service integrations, and consolidated governance.

**Possible failure conditions:**

* The account already belongs to an organization.
* The caller lacks `organizations:CreateOrganization`.
* Account verification requirements are incomplete.

### Step 3: Verify the Management Account Email

Complete any email-verification request sent by AWS.

**Why it is required:** AWS needs verified ownership before certain sensitive organization operations are permitted.

**Possible failure conditions:**

* The verification message expires.
* The email address is inaccessible.
* The organization administrator is using the wrong account.

### Step 4: Create a Separate Session for Production

Sign in to Production using a different browser profile, private session, or isolated browser.

**Why it is required:** Both accounts must have independent authenticated sessions during the invitation workflow.

**Security consideration:** Confirm the active account ID before accepting invitations or creating roles. Console sessions for different accounts can otherwise be confused.

### Step 5: Record the Production Account ID

Copy the 12-digit Production account ID.

Account IDs are identifiers, not secrets. However, they should still be handled accurately to prevent granting trust to the wrong account.

### Step 6: Send the Invitation

From the management account:

1. Open AWS Organizations.
2. Choose to add an AWS account.
3. Select the option to invite an existing account.
4. Enter the Production account ID or email address.
5. Send the invitation.

**Security control provided:** The invitation requires acceptance by the target account. The management account cannot silently take ownership of an unrelated existing account.

**Possible failure conditions:**

* Incorrect account ID or email address.
* Production already belongs to another organization.
* The invitation quota is exceeded.
* The organization account quota is reached.
* The invitation expires or is declined.

### Step 7: Accept the Invitation

From Production:

1. Open AWS Organizations.
2. Review pending invitations.
3. Confirm the inviting organization and management account.
4. Accept the invitation.

**Validation:** Production appears as a member account in the management account’s Organizations console.

**Security warning:** Confirm the organization owner before accepting. Joining an organization can subject the account to SCPs and centralized billing.

### Step 8: Create the Access Role in Production

In the Production account, create an IAM role named:

```text
OrganizationAccountAccessRole
```

Configure the management account as the trusted AWS account.

Attach only the permissions required by the operating model.

The historical demonstration attaches the AWS managed `AdministratorAccess` policy. That reproduces the default role behavior for organization-created accounts, but it is highly privileged and should not automatically be used for routine workforce access.

**Security control provided:** Separates authentication in the source account from authorization in Production.

**Possible failure conditions:**

* Wrong source account ID in the trust policy.
* Missing `sts:AssumeRole` permission for the source principal.
* Incorrect role name.
* An SCP blocks an intended administrative action.
* The role permissions are insufficient.
* The trust policy is overly broad.

### Step 9: Switch Into Production

From an authorized source-account session:

1. Enter the Production account ID.
2. Enter `OrganizationAccountAccessRole`.
3. Use a clear display label such as `prod`.
4. Visually distinguish production sessions.

The display name and color are browser conveniences. They are not IAM security controls and do not affect authorization.

**Validation:**

* The console displays the Production account.
* The active identity is an assumed-role session.
* CloudTrail records an AWS STS `AssumeRole` event.
* Authorized actions succeed.

### Step 10: Create the Development Account

From AWS Organizations in the management account:

1. Choose to create a new AWS account.
2. Enter the Development account name.
3. Provide a unique email address.
4. Retain or specify `OrganizationAccountAccessRole`.
5. Submit the account-creation request.
6. Wait for the asynchronous request to complete.

**Security control provided:** AWS creates the member account with a standardized cross-account administrative role.

**Possible failure conditions:**

* Duplicate email address.
* Invalid email address.
* Account quota reached.
* Account creation is still in progress.
* Account-creation failure reported by AWS Organizations.
* An invalid or inconsistent role name is used.

### Step 11: Access Development

Use the Development account ID and the configured role name to assume the generated role.

**Validation:**

* The Development account appears in AWS Organizations.
* `OrganizationAccountAccessRole` exists in Development.
* Its trust relationship points to the management account.
* An authorized principal can assume it.
* The role session receives temporary credentials.

## Policy or Permission Analysis

### Trust Policy

A simplified role trust policy may resemble:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::<MANAGEMENT_ACCOUNT_ID>:root"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

### Line-by-Line Comments

```text
Line 1: Opens the JSON policy document.
Line 2: Uses the current IAM policy language version.
Line 3: Begins the list of policy statements.
Line 4: Begins the role-assumption statement.
Line 5: Allows the matching principal to request the action.
Lines 6-8: Identifies the trusted management account.
Line 9: Allows the AWS STS AssumeRole operation.
Lines 10-12: Close the statement and policy document.
```

### Code Walkthrough

**Purpose:** Defines which principal may assume the role.

**Policy type:** IAM role trust policy.

**Principal:** The management account.

**Action:** `sts:AssumeRole`.

**Resource:** Trust policies do not include a `Resource` element because the policy is attached directly to the role being assumed.

**Required source permission:** The calling IAM principal normally also needs permission to invoke `sts:AssumeRole` for the target role.

**Security implication:** Trusting the account principal does not mean every identity automatically receives access. Administrators in the trusted account can delegate permission to eligible identities, so the trusted account must be strongly protected.

**Common failure:** Trusting the wrong account ID or failing to grant the source principal `sts:AssumeRole`.

### Source Identity Policy

A source principal could receive permission such as:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AssumeProductionAdministrationRole",
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::<PRODUCTION_ACCOUNT_ID>:role/OrganizationAccountAccessRole"
    }
  ]
}
```

### Line-by-Line Comments

```text
Line 1: Opens the identity-based policy.
Line 2: Sets the IAM policy language version.
Line 3: Begins the statement list.
Line 4: Gives the statement a descriptive identifier.
Line 5: Allows the action when all applicable policies permit it.
Line 6: Permits the AWS STS AssumeRole API operation.
Line 7: Limits the permission to the named role in the Production account.
Lines 8-10: Close the statement and policy.
```

### Code Walkthrough

**Purpose:** Allows the source identity to request a session for the specific Production role.

**Policy type:** Identity-based policy.

**Required permission:** `sts:AssumeRole`.

**Expected result:** The principal can request temporary credentials for the target role when the trust policy and organization guardrails also allow it.

**Read-only or modifying:** Calling `AssumeRole` does not modify target resources, but the resulting role session may have modifying permissions.

**Common failure conditions:**

* The role ARN is incorrect.
* The role trust policy does not trust the source.
* An SCP explicitly denies `sts:AssumeRole`.
* A permissions boundary excludes the permission.
* A session policy restricts access.
* MFA or other trust-policy conditions are unmet.

### Permissions Policy

The target role’s permissions policy controls what the assumed role may do after the session is issued.

The historical demonstration uses:

```text
AdministratorAccess
```

This grants broad AWS administrative permissions but does not override:

* Service control policies.
* Resource-based explicit denies.
* Permissions boundaries when applicable.
* Session policies.
* AWS KMS key-policy requirements.
* Other service-specific authorization controls.

### IAM Decision Model

When an action is attempted through the assumed role:

1. The request begins with an implicit deny.
2. An applicable allow is required.
3. An applicable explicit deny overrides an allow.
4. SCPs determine the maximum available permissions for affected accounts.
5. The role’s permissions policies must allow the action.
6. A permissions boundary can restrict identity-based permissions.
7. A session policy can further restrict the role session.
8. A resource policy may grant or restrict access depending on the service and principal.
9. Service-specific controls, such as AWS KMS key policies, must also permit access.

### Important SCP Limitation

SCPs do not grant permissions.

An SCP that allows an action only makes that action available for delegation. The role or identity still needs a corresponding IAM allow.

```text
SCP allows
    +
IAM role allows
    +
Resource and service controls allow
    =
Request can potentially succeed
```

An explicit deny in an applicable SCP blocks the action even when the role has `AdministratorAccess`.

## Modern Workforce Access with IAM Identity Center

The manual Switch Role workflow remains useful for understanding AWS STS and cross-account role assumption. However, the preferred workforce-access architecture is:

```text
Corporate identity provider
or Identity Center directory
        |
        v
AWS IAM Identity Center
        |
        | Account assignments
        | Permission sets
        v
AWS accounts in the organization
        |
        v
IAM roles provisioned and managed
for assigned access
```

IAM Identity Center provides:

* Centralized user and group assignments.
* Permission sets.
* Single sign-on through the AWS access portal.
* Integration with external identity providers.
* Temporary role-based credentials.
* Reduced reliance on IAM users.
* Consistent access across multiple AWS accounts.

AWS identifies IAM Identity Center as the recommended service for workforce access to multiple AWS accounts. ([AWS Documentation][7])

### Manual Role Switching Versus IAM Identity Center

| Requirement                            | Manual IAM Role Switching                         | IAM Identity Center                           |
| -------------------------------------- | ------------------------------------------------- | --------------------------------------------- |
| Learn AWS STS role assumption          | Strong fit                                        | Abstracts much of the manual process          |
| Small temporary lab                    | Acceptable                                        | May add setup overhead                        |
| Central workforce access               | Manual and difficult to scale                     | Recommended                                   |
| External identity provider integration | Requires direct federation design                 | Built-in supported model                      |
| Account assignments                    | Managed through individual IAM policies and roles | Centrally managed                             |
| Permission templates                   | Manually maintained                               | Permission sets                               |
| Hundreds of AWS accounts               | High administrative overhead                      | Designed for centralized multi-account access |
| Long-term IAM users                    | Often used in older designs                       | Generally avoided for workforce access        |

## Detection, Logging, and Evidence

### AWS CloudTrail

CloudTrail records relevant control-plane events, including:

* `CreateOrganization`
* `InviteAccountToOrganization`
* `AcceptHandshake`
* `CreateAccount`
* `DescribeCreateAccountStatus`
* `CreateRole`
* `UpdateAssumeRolePolicy`
* `AttachRolePolicy`
* `AssumeRole`

### Evidence for Role Assumption

Useful CloudTrail fields include:

| Field                               | Investigative Value                                 |
| ----------------------------------- | --------------------------------------------------- |
| `eventSource`                       | Identifies the service, such as `sts.amazonaws.com` |
| `eventName`                         | Identifies the operation, such as `AssumeRole`      |
| `userIdentity`                      | Shows the calling identity                          |
| `recipientAccountId`                | Identifies the target account                       |
| `requestParameters.roleArn`         | Shows the role requested                            |
| `requestParameters.roleSessionName` | Identifies the role session                         |
| `sourceIPAddress`                   | Shows the request source                            |
| `userAgent`                         | Indicates console, CLI, SDK, or another client      |
| `responseElements.assumedRoleUser`  | Identifies the resulting role session               |
| `errorCode`                         | Shows authorization or request failures             |

### Detection Versus Response

* **CloudTrail records** the organization or STS activity.
* **CloudWatch Logs** can store and query delivered CloudTrail events.
* **EventBridge can route** matching events.
* **Security Hub can aggregate** supported security findings.
* **GuardDuty can detect** certain suspicious credential behavior.
* **Lambda or Systems Manager Automation can respond** when connected to an approved workflow.

CloudTrail does not automatically remediate risky role assumptions.

## Security Best Practices

* Use AWS IAM Identity Center for centralized workforce access across multiple accounts.
* Avoid creating separate IAM users in every member account.
* Require MFA for privileged access.
* Restrict access to the management account.
* Do not deploy normal application workloads in the management account.
* Use delegated administrator capabilities for supported AWS services.
* Apply least privilege instead of routine full administrator access.
* Record organization-wide activity with CloudTrail.
* Use SCPs as guardrails, not as permission grants.
* Verify account IDs before creating trust relationships.
* Use descriptive role-session names for auditability.
* Separate production, development, security, logging, and shared-services workloads into appropriate accounts.
* Regularly review trusted principals and unused cross-account roles.
* Avoid relying on browser shortcut colors as a security control.
* Protect account root users and minimize root-user usage.
* Consider centralized root-access management for member accounts where appropriate. ([AWS Documentation][8])

## Pitfalls and Misconfigurations

### Treating Organization Membership as Automatic Access

Adding an account to an organization does not automatically allow administrators to access all resources in that account.

Cross-account access still requires:

* A trusted IAM role.
* Source permission to assume it.
* Target-role permissions.
* Compliance with SCPs and other applicable controls.

### Assuming Invited Accounts Receive the Default Access Role

Only accounts created through AWS Organizations receive the default access role automatically.

An invited account retains its existing IAM configuration.

### Using the Management Account as the Daily Login Account

The historical demonstration centralizes IAM users in the management account. This increases management-account exposure and is not the preferred modern production architecture.

Use IAM Identity Center and limit direct management-account access.

### Trusting the Management Account Root Principal Too Broadly

A role trust policy that trusts:

```text
arn:aws:iam::<MANAGEMENT_ACCOUNT_ID>:root
```

delegates control to the trusted account’s administrators to decide which identities may assume the role.

This can be appropriate for the default AWS Organizations access model, but sensitive roles may require additional controls, such as:

* Specific principal ARNs.
* `aws:PrincipalArn` conditions.
* MFA conditions.
* External IDs for third parties.
* Organization-based conditions where supported and appropriate.

### Confusing the Role Trust Policy with the Permissions Policy

* The **trust policy** controls who may assume the role.
* The **permissions policy** controls what the role session may do.

A correct trust policy with no permissions produces an assumable but ineffective role.

A powerful permissions policy with no valid trust relationship produces a role that cannot be assumed by the intended principal.

### Assuming `AdministratorAccess` Overrides SCPs

It does not.

An SCP explicit deny remains effective.

### Treating Switch Role Labels as Security Controls

Names such as `prod` and colors such as red are local usability aids. They do not prevent operations or enforce policy.

### Reusing an Email Address

Every AWS account requires a unique email address, including accounts created inside an organization.

Email subaddressing may work with providers that support it, but it is an email-provider behavior rather than an AWS Organizations security capability.

| AWS IAM Identity Center | Workforce authentication and account assignments                        | Need centralized human access to accounts                                    |
| AWS STS                 | Temporary security credentials                                          | Need cross-account role sessions                                             |

AWS Control Tower uses AWS Organizations but does not replace IAM Identity Center, IAM roles, or AWS STS.

## Common Exam Traps

1. **An invited account does not automatically receive `OrganizationAccountAccessRole`.**

2. **An organization-created account receives the role by default, but the caller still needs permission to assume it.**

3. **SCPs do not grant permissions.** They limit the permissions that IAM policies can grant.

4. **The management account is not restricted by SCPs in the same way as member accounts.** Do not depend on an SCP to secure management-account principals.

5. **Role switching uses temporary credentials.** It does not copy the source IAM user into the target account.

6. **A trust policy is not a permissions policy.**

7. **`AdministratorAccess` cannot bypass an explicit deny.**

8. **IAM Identity Center is for workforce access.** Amazon Cognito is primarily for application end-user identity.

9. **AWS Organizations is not an identity provider.** It organizes accounts and applies governance controls.

10. **The role-switch display name and color are browser conveniences, not authorization controls.**

11. **Organization membership does not automatically provide access to member-account resources.**

12. **Creating an account is asynchronous.** A submitted request does not mean the account is immediately ready.

13. **Account IDs are not secret credentials.** Accuracy matters because a wrong account ID can create an unintended trust relationship.

14. **The management account should not be used as a general workload account.**

15. **Manual IAM users may work in a lab but are not the preferred scalable workforce-access solution.**

## Memory Hooks

### One-Line Memory Hook

> **Invite an account and build the access role; create an account and Organizations builds the default role.**

### Service Memory Hook

> **Organizations groups accounts, IAM defines trust and permissions, STS issues temporary credentials, and IAM Identity Center manages workforce access.**

### Decision Memory Hook

> **Need account governance? Think Organizations.
> Need centralized employee access? Think IAM Identity Center.
> Need temporary cross-account credentials? Think STS AssumeRole.
> Need to know who assumed the role? Think CloudTrail.**

### Trust and Permission Memory Hook

> **Trust answers “who may enter”; permissions answer “what they may do after entering.”**

### SCP Memory Hook

> **SCPs set the ceiling; IAM policies provide the permissions below that ceiling.**

### Created Versus Invited Mnemonic

> **Created comes Configured; Invited needs IAM.**

* **Created:** AWS configures the default access role.
* **Invited:** You create the role when needed.

### Mental Model

Think of every AWS account as a secured building:

* AWS Organizations places buildings inside one managed campus.
* The role trust policy defines who may request a visitor badge.
* The source IAM policy allows the visitor to request that badge.
* AWS STS issues a temporary badge.
* The role permissions define which rooms the visitor may enter.
* SCPs define campus-wide restrictions that local badges cannot override.

## Quick Review

* The account that creates an AWS Organization becomes the management account.
* Existing accounts join by accepting an invitation.
* Invited accounts do not automatically receive `OrganizationAccountAccessRole`.
* Accounts created through AWS Organizations receive the role by default.
* Cross-account console switching uses AWS STS `AssumeRole`.
* The target trust policy and source permissions must both support role assumption.
* The target role’s permissions determine what the session can do.
* SCPs limit permissions but do not grant them.
* `AdministratorAccess` does not override explicit denies or service-specific controls.
* IAM Identity Center is the recommended current solution for workforce access across multiple accounts.
* CloudTrail records organization-management and role-assumption activity.
* Keep workloads and routine workforce identities out of the management account where possible.

## Self-Check Questions

### 1. Why must `OrganizationAccountAccessRole` be created manually in the invited Production account?

<details>
<summary>Answer</summary>

AWS Organizations automatically creates the default access role only when it creates the member account. An existing account that joins through an invitation retains its existing IAM configuration, so the cross-account role must be created manually when required.

</details>

### 2. Which two authorization components are normally required before a principal can assume a cross-account role?

<details>
<summary>Answer</summary>

The role’s trust policy must trust the source principal or account, and the source principal must have permission to call `sts:AssumeRole` for the target role. SCPs, permissions boundaries, session policies, and explicit denies must also permit the request.

</details>

### 3. What credentials are used after a successful console role switch?

<details>
<summary>Answer</summary>

AWS STS temporary credentials are used. They include a temporary access key ID, secret access key, and session token with a limited lifetime.

</details>

### 4. A role has `AdministratorAccess`, but an Amazon S3 action is denied. What should be checked?

<details>
<summary>Answer</summary>

Check applicable SCPs, resource policies, permissions boundaries, session policies, bucket policies, and other explicit denies. `AdministratorAccess` does not override an explicit deny.

</details>

### 5. Which service should normally be selected for centralized employee access across hundreds of AWS accounts?

<details>
<summary>Answer</summary>

AWS IAM Identity Center. It centrally manages workforce identities, groups, permission sets, and AWS account assignments while providing temporary role-based access.

</details>

### 6. What is the difference between a role trust policy and the role’s permissions policy?

<details>
<summary>Answer</summary>

The trust policy identifies who or what may assume the role. The permissions policy determines which AWS actions the assumed role session may perform.

</details>

### 7. Does an SCP granting `s3:*` give a role permission to access Amazon S3?

<details>
<summary>Answer</summary>

No. SCPs do not grant permissions. An IAM policy or another applicable permissions mechanism must allow the action, and no applicable explicit deny may block it.

</details>
