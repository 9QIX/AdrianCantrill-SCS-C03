# CloudFormation Custom Resources

## Overview

Custom resources let CloudFormation call custom provisioning logic for operations not available as native resource types. A service token identifies an AWS Lambda function or Amazon Simple Notification Service (Amazon SNS) topic that handles create, update, and delete requests and returns a response.

## Exam Alignment

- **Primary SCS-C03 Domain:** Security Foundations and Governance
- **Secondary Domain(s):** Infrastructure Security, Identity and Access Management
- **Main AWS Services:** AWS CloudFormation, AWS Lambda, Amazon SNS, IAM, Amazon CloudWatch Logs
- **Lesson Type:** Architecture / Troubleshooting
- **Exam Importance:** Medium
- **Core Skill:** Secure idempotent custom-resource providers and prevent stack hangs, privilege abuse, or data leakage.

## How It Works

```text
Stack operation -> custom resource request -> Lambda/SNS provider
                <- signed response URL result <- provider logic
```

Requests include a request type, stack and request identifiers, logical resource ID, resource properties, and—during update/delete—the physical resource ID. The provider must send a success or failure response to the supplied response URL.

## Security Best Practices

- Give the provider role only the required actions and resources.
- Validate all properties; templates can supply attacker-controlled input.
- Make create, update, and delete idempotent because retries occur.
- Return stable physical resource IDs unless replacement is intended.
- Never include secrets in response data, logs, errors, or physical IDs.
- Configure logging, concurrency, timeouts, and dead-letter or failure handling appropriate to the provider.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Stack hangs then times out | Provider failed to send response | Inspect Lambda/SNS delivery and CloudWatch Logs | Ensure every code path responds |
| Unexpected replacement | Physical resource ID changed | Compare provider responses | Keep ID stable for in-place updates |
| Delete fails | Provider assumes external object exists | Inspect delete logs and request ID | Make deletion idempotent and tolerant of absent state |
| Access denied | Provider role lacks permission or is guardrailed | Review CloudTrail and effective policies | Add narrow permission or correct target scope |

## Common Exam Traps

- CloudFormation does not infer external side effects performed by custom code.
- A Lambda timeout does not automatically send a valid failure response.
- Provider permissions, not the template operator's direct permissions, commonly perform the external action.
- Custom resources increase operational and security responsibility compared with native resource types.

## Memory Hooks

> **Custom resource means custom code, custom permissions, and custom failure handling.**

## Quick Review

- Prefer native resource types when available.
- Validate input and minimize provider permissions.
- Respond on every execution path.
- Design idempotently for retries.
- Keep physical IDs stable unless replacement is intended.
- Sanitize logs and response data.

## Self-Check Questions

1. Why does a custom-resource stack operation remain in progress until timeout?

<details><summary>Answer</summary>

The provider commonly failed before sending the required success or failure response to the presigned response URL.

</details>

2. Which identity needs permission to perform the custom action?

<details><summary>Answer</summary>

The provider's execution role, subject to applicable resource policies and organizational guardrails.

</details>

3. What must a custom resource provider always return?

<details>
<summary>Answer</summary>

It must return a success or failure response to CloudFormation's response destination with the required identifiers. Missing responses leave the stack waiting until timeout.

</details>
