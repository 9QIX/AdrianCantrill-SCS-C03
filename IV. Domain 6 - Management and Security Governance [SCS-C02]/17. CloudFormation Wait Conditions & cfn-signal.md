# CloudFormation Wait Conditions and cfn-signal

## Overview

CloudFormation signaling coordinates stack progress with external initialization. A wait condition pauses until its presigned handle receives the required success signals or the timeout expires; `cfn-signal` can report bootstrap status to supported CloudFormation resources.

## Exam Alignment

- **Primary SCS-C03 Domain:** Security Foundations and Governance
- **Secondary Domain(s):** Infrastructure Security
- **Main AWS Services:** AWS CloudFormation, Amazon EC2, Amazon EC2 Auto Scaling
- **Lesson Type:** Architecture / Troubleshooting
- **Exam Importance:** Medium
- **Core Skill:** Make deployments wait for verified initialization instead of mere resource creation.

## Core Concepts

- `AWS::CloudFormation::WaitConditionHandle` provides a presigned signaling endpoint.
- `AWS::CloudFormation::WaitCondition` defines required signal count and timeout.
- `cfn-signal` reports success or failure from bootstrap scripts.
- Creation policies are generally preferable for signaling supported EC2 and Auto Scaling resources; wait conditions remain useful for other coordinated work.
- Signals prove only the checks the bootstrap process performs.

## How It Works

```text
CloudFormation creates resource -> bootstrap executes -> validation succeeds
                               -> signal sent -> stack continues
                               -> failure/timeout -> stack operation fails
```

The workload must reach the signaling endpoint. Private networks therefore need appropriate egress or service connectivity. Never log or expose a presigned wait-condition handle.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Timeout | Script failed or endpoint unreachable | Inspect instance console/cloud-init logs and network path | Correct bootstrap or connectivity |
| Failure signal | Initialization validation failed | Inspect script exit status and application logs | Correct configuration and retry stack operation |
| Stack continues too early | Signal sent before meaningful validation | Review bootstrap sequence | Signal only after security and health checks pass |

## Common Exam Traps

- A timeout is not a sleep duration; it is the maximum wait.
- `DependsOn` orders creation but does not verify application readiness.
- A success signal is only as reliable as its validation logic.

## Memory Hooks

> **DependsOn says “start after”; a signal says “continue because initialization passed.”**

## Quick Review

- Use supported creation policies where appropriate.
- Signal only after validation.
- Plan network access to signaling endpoints.
- Protect presigned handles.
- Use bootstrap logs plus stack events to troubleshoot.

## Self-Check Questions

1. Why can a private EC2 instance cause a wait-condition timeout?

<details><summary>Answer</summary>

Its bootstrap may be unable to reach the signaling endpoint, or initialization may have failed before sending the signal.

</details>

2. What must a wait-condition signal include?

<details>
<summary>Answer</summary>

It must reach the correct presigned handle before timeout and report the expected success count. Network egress, bootstrap logic, and signal command parameters must all work.

</details>

3. Why is `cfn-signal` often preferable for EC2 and Auto Scaling resources?

<details>
<summary>Answer</summary>

It integrates resource creation policies with instance bootstrap success, avoiding a separate wait-condition handle for those supported patterns.

</details>
