# CloudFormation Service Roles

## Overview

A CloudFormation service role supplies the permissions CloudFormation uses to create, update, and delete stack resources. This separates the operator's permission to manage a stack from the service's permission to manipulate underlying resources.

## Exam Alignment

- **Primary SCS-C03 Domain:** Identity and Access Management
- **Secondary Domain(s):** Security Foundations and Governance
- **Main AWS Services:** AWS CloudFormation, IAM, AWS STS
- **Lesson Type:** Policy Analysis
- **Exam Importance:** High
- **Core Skill:** Delegate stack operations through a least-privilege service role without enabling privilege escalation.

## Policy or Permission Analysis

- The role trust policy allows the CloudFormation service principal to assume it.
- The role permissions policies allow only the resource actions required by the templates it serves.
- The human or pipeline needs CloudFormation stack-operation permissions plus tightly scoped `iam:PassRole` for the approved service role.
- After a service role is associated with a stack, CloudFormation uses it for stack operations; anyone able to operate that stack may cause actions under the role's authority.
- Explicit denies, SCPs, permissions boundaries, and resource policies still apply as relevant.

## How It Works

```text
Operator -> CloudFormation API permission + iam:PassRole
         -> CloudFormation assumes service role
         -> Role permissions create/update/delete stack resources
```

## Security Best Practices

- Scope `iam:PassRole` by role ARN and, where appropriate, service condition.
- Use separate roles for workloads with different trust or impact.
- Review templates and change sets before allowing execution under a powerful role.
- Monitor `PassRole`, stack changes, and role-policy changes with CloudTrail.

## Common Exam Traps

- `iam:PassRole` does not mean the caller assumes the role.
- A constrained operator can still cause powerful changes if allowed to use a broad stack role with arbitrary templates.
- The trust policy and permissions policy solve different questions.

## Memory Hooks

> **The operator requests; PassRole delegates; CloudFormation assumes; the service role acts.**

## Quick Review

- Separate stack control from resource permissions.
- Scope both CloudFormation APIs and `iam:PassRole`.
- Apply least privilege to the service role.
- Treat template submission as security-sensitive.
- Audit role and stack changes.

## Self-Check Questions

1. Why can `iam:PassRole` create privilege-escalation risk?

<details><summary>Answer</summary>

A caller may cause CloudFormation to perform actions using a more privileged role, especially if the caller controls the template or stack operation.

</details>

2. Why use a CloudFormation service role?

<details>
<summary>Answer</summary>

It gives CloudFormation a consistent permission set for stack operations and can separate deployer permission from resource-provisioning permission.

</details>

3. What is the key escalation risk?

<details>
<summary>Answer</summary>

A principal who can pass a powerful stack role and modify templates may cause CloudFormation to create privileged resources. Restrict `iam:PassRole`, stack actions, templates, and role scope.

</details>
