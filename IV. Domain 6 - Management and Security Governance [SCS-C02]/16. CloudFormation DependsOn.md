# CloudFormation Dependency Ordering with DependsOn

## Overview

CloudFormation builds a dependency graph from references and creates independent resources in parallel. The `DependsOn` attribute adds an explicit ordering dependency when CloudFormation cannot infer the required sequence.

## Exam Alignment

- **Primary SCS-C03 Domain:** Security Foundations and Governance
- **Secondary Domain(s):** Infrastructure Security
- **Main AWS Services:** AWS CloudFormation
- **Lesson Type:** Troubleshooting
- **Exam Importance:** Supporting
- **Core Skill:** Distinguish implicit dependencies from explicit creation and deletion ordering.

## Core Concepts

- `Ref`, `Fn::GetAtt`, and `Fn::Sub` references commonly create implicit dependencies.
- `DependsOn` forces the named dependency to complete before the dependent resource is created.
- On deletion, the dependent is deleted before its dependency.
- Explicit ordering does not wait for application readiness unless the resource contract itself reports readiness.
- Excessive dependencies reduce parallelism and can conceal a poor resource model.

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Resource created before prerequisite | No inferable reference | Inspect template dependency graph and events | Add a justified `DependsOn` or real reference |
| Service exists but application is not ready | Ordering mistaken for readiness | Inspect application health/bootstrap | Use an appropriate signal or health mechanism |
| Stack is slow | Unnecessary serial dependencies | Review `DependsOn` chain | Remove dependencies CloudFormation already infers |

## Common Exam Traps

- `DependsOn` is an attribute, not an intrinsic function.
- It controls order, not permission.
- It does not solve every eventual-consistency or bootstrap problem.

## Memory Hooks

> **References imply order; DependsOn states order; signals prove readiness.**

## Quick Review

- Prefer inferred dependencies.
- Add explicit ordering only when required.
- Read stack events for failures.
- Do not equate resource creation with application readiness.
- Understand reverse deletion ordering.

## Self-Check Questions

1. When is `DependsOn` unnecessary?

<details><summary>Answer</summary>

When a reference already lets CloudFormation infer the dependency.

</details>

2. When is `DependsOn` required?

<details>
<summary>Answer</summary>

Use it when an ordering relationship is not already expressed by a resource reference and one resource must complete before another starts.

</details>

3. Does `DependsOn` make an application ready?

<details>
<summary>Answer</summary>

No. It controls CloudFormation operation order, not guest or application readiness. Use health checks, signals, or service-specific stabilization where required.

</details>
