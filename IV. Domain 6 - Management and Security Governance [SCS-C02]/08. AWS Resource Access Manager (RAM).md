# AWS Resource Access Manager

## Overview

AWS Resource Access Manager (AWS RAM) shares supported AWS resources across accounts, organizational units, an organization, or supported external principals without duplicating the resources. The resource owner retains ownership; consumers receive permitted use.

## Exam Alignment

- **Primary SCS-C03 Domain:** Security Foundations and Governance
- **Secondary Domain(s):** Identity and Access Management
- **Main AWS Services:** AWS RAM, AWS Organizations, IAM
- **Lesson Type:** Architecture
- **Exam Importance:** Medium
- **Core Skill:** Securely share supported resources while preserving ownership and least privilege.

## Core Concepts

- A resource share includes resources, principals, and an AWS-managed or customer-managed permission for supported resource types.
- Sharing within an organization can avoid per-account invitation acceptance when organization sharing is enabled.
- External account shares generally require acceptance and must be deliberately permitted.
- Resource-type behavior differs: consumers may create associations or dependent resources but do not become owners.
- IAM and service-specific policies still govern actions by consuming principals.

## Architecture and Service Relationships

```text
Owner account resource -> AWS RAM resource share -> Consumer account principals
         ownership remains here                 -> permitted use only
```

## Troubleshooting

| Symptom | Likely Cause | Verification | Resolution |
| --- | --- | --- | --- |
| Share not visible | Invitation pending or wrong principal/Region | Inspect share associations and Region | Accept invitation or correct scope |
| Consumer sees resource but cannot use it | Missing IAM or RAM permission action | Review effective permission and CloudTrail | Grant least-privilege actions |
| Organization sharing fails | Trusted access not enabled | Check Organizations integration | Enable approved trusted access |

## Common Exam Traps

- RAM shares only supported resource types.
- Sharing is not ownership transfer.
- RAM visibility does not itself grant every service action.
- A shared VPC subnet is not a VPC peering connection.

## Memory Hooks

> **RAM shares use, not ownership.**

## Quick Review

- Owner and consumer responsibilities remain distinct.
- Use Organizations integration for scalable internal sharing.
- Scope principals and RAM permissions carefully.
- Check Region and invitation state.
- Audit share changes and consumer actions with CloudTrail.

## Self-Check Questions

1. Does a consumer account own a RAM-shared resource?

<details><summary>Answer</summary>

No. The owner account retains ownership; the consumer receives the allowed use defined for that resource type.

</details>

2. Does an AWS RAM share bypass the recipient's IAM policies?

<details>
<summary>Answer</summary>

No. A share makes a supported resource available to accepted principals, but the recipient still needs applicable service permissions and remains subject to guardrails.

</details>

3. What is the organization-wide sharing clue?

<details>
<summary>Answer</summary>

Enable trusted access between AWS RAM and AWS Organizations when resources must be shared with the organization or organizational units without individual invitations.

</details>
