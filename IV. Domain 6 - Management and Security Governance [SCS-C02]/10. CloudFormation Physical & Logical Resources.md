# CloudFormation Logical and Physical Resources

## Overview

AWS CloudFormation templates declare logical resources. During a stack operation, CloudFormation creates or associates physical AWS resources and tracks the mapping between logical and physical identifiers. Understanding this lifecycle is essential for secure infrastructure changes and incident recovery.

## Core Concepts

- A logical ID is unique within a template and remains the template's reference to a resource.
- A physical ID identifies the deployed resource, such as a bucket name or instance ID.
- Changing some properties updates a resource in place; other properties require replacement.
- Replacement creates a new physical resource and can cause interruption, data loss, or changed identifiers.
- Direct edits outside CloudFormation can create drift between declared and actual state.

## How It Works

```text
Template logical ID -> CloudFormation stack mapping -> Physical AWS resource
Template update      -> in-place update or replacement -> Updated mapping/state
```

CloudTrail records control-plane calls; stack events explain orchestration progress and failures. Neither automatically proves application-level correctness after deployment.

## Common Exam Traps

- Renaming a logical ID is generally interpreted as removing one resource and adding another.
- A generated physical name should not be assumed stable after replacement.
- CloudFormation ownership does not prevent out-of-band changes.
- Successful creation does not establish secure configuration unless the template defines it.

## Memory Hooks

> **Logical is the template name; physical is the deployed thing.**

## Quick Review

- References normally target logical IDs.
- Property update behavior is resource-specific.
- Review replacement impact before execution.
- Detect and resolve drift.
- Protect stateful resources with deliberate retention and backup design.

## Self-Check Questions

1. Why can a harmless-looking property update be risky?

<details><summary>Answer</summary>

The resource specification may require physical replacement, affecting availability, data, names, and dependent resources.

</details>

2. Why should policies and references use logical IDs carefully?

<details>
<summary>Answer</summary>

Logical IDs define resources within the template and influence replacement behavior, while physical IDs identify deployed resources. Confusing them can break dependencies or automation.

</details>

3. Where should a failed resource creation be investigated?

<details>
<summary>Answer</summary>

Start with CloudFormation stack events and resource status reasons, then inspect the underlying service and CloudTrail for the failed API request.

</details>
