### Question 1 – Permissions boundaries

A media company lets its platform team create IAM users for short-term contractors. Every contractor user has the identity-based policy and the permissions boundary shown below. A contractor calls s3:DeleteObject on arn:aws:s3:::media-raw/clip1.mp4 and then calls s3:GetObject on arn:aws:s3:::media-archive/2019/old.mp4. Both buckets are in the same account and have no bucket policies. What is the result of the two requests?

Identity-based policy:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "s3:*", "Resource": "*" }
  ]
}
```
Permissions boundary:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::media-raw/*"
    }
  ]
}
```

- **A.** Both requests are denied because neither request is allowed by both the identity-based policy and the permissions boundary.
- **B.** The DeleteObject request is allowed because the boundary contains no explicit deny for s3:DeleteObject.
- **C.** Both requests are allowed because the identity-based policy grants s3:\* on all resources.
- **D.** The DeleteObject request is denied, but the GetObject request on media-archive is allowed because s3:GetObject appears in the boundary.

<details>
<summary>Show answer and explanation</summary>

**Answer: A**

✅ **A.** Both requests are denied because neither request is allowed by both the identity-based policy and the permissions boundary.

Effective permissions are the intersection of the identity-based policy and the boundary. DeleteObject is not in the boundary's action list, and the GetObject request targets media-archive, which is outside the boundary's media-raw/\* resource, so both requests end in an implicit deny.

**Summary:** Effective permissions for an IAM user with a permissions boundary are the intersection of the identity-based policy and the boundary (absent resource-based grants). DeleteObject is not in the boundary's action list, and the GetObject request targets media-archive, which is outside the boundary's resource. Both requests therefore fall to an implicit deny.

❌ **B.** The DeleteObject request is allowed because the boundary contains no explicit deny for s3:DeleteObject.

A permissions boundary is an allow-list ceiling, so s3:DeleteObject is implicitly denied because the boundary never allows it; no explicit deny is needed, and the delete fails.

❌ **C.** Both requests are allowed because the identity-based policy grants s3:\* on all resources.

A permissions boundary caps identity-based permissions, so an allow in the identity policy alone is not sufficient.

❌ **D.** The DeleteObject request is denied, but the GetObject request on media-archive is allowed because s3:GetObject appears in the boundary.

The boundary allows s3:GetObject only on media-raw/\*, so the media-archive object is outside the boundary.

</details>

### Question 2 – Session policies

A SaaS analytics company runs a multi-tenant ingestion service on Amazon ECS. The task role can assume an IAM role named TenantDataRole that has read/write access to a single Amazon DynamoDB table, in which each item's partition key is the tenant ID. The company has more than 5,000 tenants and wants every request to be processed with credentials that can reach only the calling tenant's items. The solution must not require creating IAM roles or policies per tenant. Which solution meets these requirements?

- **A.** Attach a permissions boundary to the ECS task role that limits dynamodb:LeadingKeys to ${aws:username}.
- **B.** Have the service call sts:AssumeRole for TenantDataRole on each request and pass an inline session policy that allows the DynamoDB actions only when dynamodb:LeadingKeys matches the caller's tenant ID.
- **C.** Attach an SCP to the workload account that restricts dynamodb:LeadingKeys to the tenant ID of the caller.
- **D.** Create one IAM role per tenant with a permissions boundary that restricts dynamodb:LeadingKeys to that tenant, and have the service assume the matching role.

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** Have the service call sts:AssumeRole for TenantDataRole on each request and pass an inline session policy that allows the DynamoDB actions only when dynamodb:LeadingKeys matches the caller's tenant ID.

A session policy passed at AssumeRole time limits the session to the intersection of TenantDataRole's permissions and the session policy. Generating it per request with a dynamodb:LeadingKeys condition for the tenant ID gives tenant-scoped credentials from one role, with no per-tenant IAM roles or policies.

**Summary:** A session policy passed in AssumeRole further restricts the resulting session to the intersection of the role's permissions and the session policy. Generating a tenant-specific session policy at request time gives per-tenant credentials from a single role, with no per-tenant IAM resources. The dynamodb:LeadingKeys condition key limits access to items whose partition key equals the tenant ID.

❌ **A.** Attach a permissions boundary to the ECS task role that limits dynamodb:LeadingKeys to ${aws:username}.

aws:username is not present for role sessions, and a boundary on the task role does not scope the credentials issued for TenantDataRole.

❌ **C.** Attach an SCP to the workload account that restricts dynamodb:LeadingKeys to the tenant ID of the caller.

SCPs are static organization guardrails and cannot express per-request tenant scoping for a single workload role.

❌ **D.** Create one IAM role per tenant with a permissions boundary that restricts dynamodb:LeadingKeys to that tenant, and have the service assume the matching role.

This requires per-tenant roles, which violates the constraint and does not scale well against IAM role quotas.

</details>

### Question 3 – Lambda resource-based policy / confused deputy

An image-processing team configured Amazon S3 event notifications on the bucket img-uploads-prod to invoke a Lambda function in account 111122223333. A security review of the function's resource-based policy (shown below) flags a confused deputy risk. Which change BEST addresses the finding?

```json
{
  "Effect": "Allow",
  "Principal": { "Service": "s3.amazonaws.com" },
  "Action": "lambda:InvokeFunction",
  "Resource": "arn:aws:lambda:us-east-1:111122223333:function:thumbnailer",
  "Condition": {
    "ArnLike": { "AWS:SourceArn": "arn:aws:s3:::img-uploads-prod" }
  }
}
```

- **A.** Add a StringEquals condition on sts:ExternalId so that only S3 notifications that include the external ID can invoke the function.
- **B.** Change the ArnLike operator to ArnEquals.
- **C.** Add a StringEquals condition on aws:SourceAccount with the value 111122223333, because S3 bucket ARNs do not contain an account ID and a bucket with the same name could exist in another account after deletion.
- **D.** Replace the s3.amazonaws.com service principal with arn:aws:iam::111122223333:root.

<details>
<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Add a StringEquals condition on aws:SourceAccount with the value 111122223333, because S3 bucket ARNs do not contain an account ID and a bucket with the same name could exist in another account after deletion.

S3 bucket ARNs contain no account ID, so aws:SourceArn alone would match a same-named bucket in any account. Adding aws:SourceAccount 111122223333 ensures only a bucket owned by the company can invoke the function, which is the AWS-recommended confused deputy protection for service principals.

**Summary:** For service principals, AWS recommends aws:SourceArn and aws:SourceAccount to prevent the cross-service confused deputy problem. Because an S3 bucket ARN has no account ID, aws:SourceArn alone cannot prove that the bucket belongs to the expected account. Adding aws:SourceAccount ensures only the bucket owned by 111122223333 can trigger the function.

❌ **A.** Add a StringEquals condition on sts:ExternalId so that only S3 notifications that include the external ID can invoke the function.

sts:ExternalId applies to AssumeRole calls by third parties, not to service principals invoking a Lambda function.

❌ **B.** Change the ArnLike operator to ArnEquals.

The operator change does not add an account check, so a same-named bucket in another account would still match.

❌ **D.** Replace the s3.amazonaws.com service principal with arn:aws:iam::111122223333:root.

S3 invokes the function as a service principal, so replacing it with the account principal would break the notification.

</details>

### Question 4 – sts:ExternalId / third-party access

A startup is building a SaaS cost-optimization product. The product's backend, running in the startup's AWS account, will assume an IAM role that each customer creates in the customer's own account. The startup wants to follow AWS guidance to prevent the confused deputy problem between customers. Which TWO design choices should the startup implement? (Select TWO.)

- **A.** Ask each customer to create an IAM user with access keys that the startup stores for API calls.
- **B.** Add an aws:SourceArn condition to the customer trust policy that references the startup's backend Lambda function.
- **C.** Have the SaaS platform generate a unique external ID for each customer and not allow customers to choose or change it.
- **D.** Treat the external ID as a password, store it in AWS Secrets Manager, and rotate it every 30 days.
- **E.** Instruct each customer to add a StringEquals condition on sts:ExternalId, with the customer's assigned value, to the trust policy of the role that trusts the startup's AWS account.
- **F.** Allow each customer to pick any external ID value and enter it in the SaaS console.

<details>
<summary>Show answer and explanation</summary>

**Answer: C, E**

✅ **C.** Have the SaaS platform generate a unique external ID for each customer and not allow customers to choose or change it.

The external ID must be unique per customer and generated by the SaaS provider so that no customer can supply another customer's value; the startup then always sends the ID tied to the customer whose role it is assuming.

✅ **E.** Instruct each customer to add a StringEquals condition on sts:ExternalId, with the customer's assigned value, to the trust policy of the role that trusts the startup's AWS account.

The customer's trust policy must require the assigned value with a StringEquals condition on sts:ExternalId; without that condition, any AssumeRole call from the startup's account succeeds and the external ID gives no confused deputy protection.

**Summary:** The external ID pattern requires the third party to generate a unique value per customer and the customer to require that value in the role trust policy with an sts:ExternalId condition. The startup then always sends the external ID associated with the customer whose role it is assuming. This prevents one customer from tricking the startup into accessing another customer's account by supplying that customer's role ARN.

❌ **A.** Ask each customer to create an IAM user with access keys that the startup stores for API calls.

Long-term access keys shared with a third party increase risk and do not address the confused deputy problem.

❌ **B.** Add an aws:SourceArn condition to the customer trust policy that references the startup's backend Lambda function.

aws:SourceArn is evaluated for AWS service principals acting on a customer's behalf, not for a role session from another account calling AssumeRole.

❌ **D.** Treat the external ID as a password, store it in AWS Secrets Manager, and rotate it every 30 days.

An external ID is not a secret; its protection comes from being unique per customer and controlled by the provider, not from rotation.

❌ **F.** Allow each customer to pick any external ID value and enter it in the SaaS console.

Customer-chosen values can collide with or guess another customer's value; the third party should generate a unique ID per customer.

</details>

### Question 5 – Role chaining / session duration

A data engineering team runs a nightly job on an Amazon EC2 instance. The instance profile role assumes an IAM role named EtlRole in the same account, and the job then uses the EtlRole session credentials to assume an IAM role named WarehouseLoader in an analytics account with DurationSeconds set to 10800. WarehouseLoader has a maximum session duration of 12 hours. The final AssumeRole call fails with a validation error about the requested duration. What is the cause, and what should the team do?

- **A.** The WarehouseLoader trust policy must include sts:TagSession to allow durations longer than 1 hour.
- **B.** Call sts:GetSessionToken from the EtlRole session to obtain credentials valid for up to 36 hours.
- **C.** EtlRole has the default 1-hour maximum session duration; increase EtlRole's maximum session duration to 12 hours.
- **D.** Role chaining limits the session to a maximum of 1 hour regardless of the role's maximum session duration; request 3600 seconds or less and refresh credentials before they expire.

<details>
<summary>Show answer and explanation</summary>

**Answer: D**

✅ **D.** Role chaining limits the session to a maximum of 1 hour regardless of the role's maximum session duration; request 3600 seconds or less and refresh credentials before they expire.

Using EtlRole session credentials to assume WarehouseLoader is role chaining, which AWS caps at 1 hour regardless of MaxSessionDuration. The 10800-second request therefore fails validation, so the job must request 3600 seconds or less and re-assume the role before the credentials expire.

**Summary:** Using role session credentials to assume another role is role chaining, and AWS limits the resulting session to a maximum of one hour. The MaxSessionDuration setting does not override this limit. The job should request a duration of 3600 seconds or less and re-assume the role (or rely on SDK credential refresh) for long-running work.

❌ **A.** The WarehouseLoader trust policy must include sts:TagSession to allow durations longer than 1 hour.

sts:TagSession only permits passing session tags during AssumeRole; it has no effect on session duration, so the role-chaining 1-hour limit would still reject the 10800-second request.

❌ **B.** Call sts:GetSessionToken from the EtlRole session to obtain credentials valid for up to 36 hours.

GetSessionToken cannot be called with role session credentials; it is intended for IAM users and the root user.

❌ **C.** EtlRole has the default 1-hour maximum session duration; increase EtlRole's maximum session duration to 12 hours.

The limit is imposed on role-chained sessions, so changing either role's maximum session duration does not raise it.

</details>

### Question 6 – SCPs with principal exceptions

A company applies the SCP below to its Workloads OU so that the security team's audit roles in every member account cannot be tampered with. Only the deployment pipeline role should be able to modify them. Which TWO statements about this SCP are correct? (Select TWO.)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectAuditRoles",
      "Effect": "Deny",
      "Action": [
        "iam:DeleteRole",
        "iam:DetachRolePolicy",
        "iam:PutRolePolicy",
        "iam:UpdateAssumeRolePolicy"
      ],
      "Resource": "arn:aws:iam::*:role/security-audit-*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalArn": "arn:aws:iam::*:role/PipelineDeployer"
        }
      }
    }
  ]
}
```

- **A.** The PipelineDeployer role in a member account can modify the audit roles only if its own identity-based policy allows those IAM actions.
- **B.** The SCP grants PipelineDeployer permission to modify the audit roles even if PipelineDeployer has no identity-based policies.
- **C.** The SCP also prevents principals in the management account from deleting audit roles in the management account.
- **D.** An IAM role with the AdministratorAccess policy in a member account of the Workloads OU cannot change the trust policy of security-audit-reader.
- **E.** The root user of a member account in the Workloads OU can still delete the audit roles because SCPs do not apply to the root user.
- **F.** Service-linked roles in member accounts are blocked by this SCP from performing actions on the audit roles.

<details>
<summary>Show answer and explanation</summary>

**Answer: A, D**

✅ **A.** The PipelineDeployer role in a member account can modify the audit roles only if its own identity-based policy allows those IAM actions.

The ArnNotLike exception only removes PipelineDeployer from the deny. SCPs never grant permissions, so PipelineDeployer still needs an identity-based policy that allows the IAM actions on the audit roles.

✅ **D.** An IAM role with the AdministratorAccess policy in a member account of the Workloads OU cannot change the trust policy of security-audit-reader.

iam:UpdateAssumeRolePolicy on security-audit-\* is explicitly denied for every principal whose ARN is not PipelineDeployer, and an explicit deny in an SCP overrides AdministratorAccess in the member account.

**Summary:** The deny applies to every principal in affected member accounts, including administrators and the member root user, unless the principal ARN matches PipelineDeployer. The exception only removes the deny; PipelineDeployer still needs an identity-based allow because SCPs do not grant access. SCPs have no effect on service-linked roles or on the management account.

❌ **B.** The SCP grants PipelineDeployer permission to modify the audit roles even if PipelineDeployer has no identity-based policies.

SCPs never grant permissions; the condition only exempts PipelineDeployer from the deny, so without an identity-based allow its requests are still implicitly denied.

❌ **C.** The SCP also prevents principals in the management account from deleting audit roles in the management account.

SCPs never apply to principals in the management account, so this SCP cannot stop management account principals from deleting audit roles there.

❌ **E.** The root user of a member account in the Workloads OU can still delete the audit roles because SCPs do not apply to the root user.

SCPs apply to the root user of member accounts; the root user's principal ARN does not match the exception.

❌ **F.** Service-linked roles in member accounts are blocked by this SCP from performing actions on the audit roles.

SCPs do not restrict service-linked roles, so this deny has no effect on them; the statement claims a restriction the SCP cannot impose.

</details>

### Question 7 – Resource control policies (RCPs)

A pharmaceutical company has 300 accounts in AWS Organizations with all features enabled. A new requirement states that Amazon S3 buckets and AWS KMS keys in any member account must never be accessible to principals outside the organization, even if an account administrator writes a bucket policy or key policy that grants access to an external account. AWS service principals must continue to work. The control must be preventive and have the LEAST operational overhead. Which solution meets these requirements?

- **A.** Create a resource control policy (RCP) that denies s3:\* and kms:\* when aws:PrincipalOrgID does not equal the organization ID and aws:PrincipalIsAWSService is false, and attach it to the organization root.
- **B.** Create an organization-level IAM Access Analyzer external access analyzer and use Amazon EventBridge to trigger a Lambda function that removes external grants.
- **C.** Create a service control policy (SCP) with the same deny and conditions, and attach it to the organization root.
- **D.** Deploy an AWS Config conformance pack with S3 and KMS policy rules and automatic remediation through Systems Manager Automation.

<details>
<summary>Show answer and explanation</summary>

**Answer: A**

✅ **A.** Create a resource control policy (RCP) that denies s3:\* and kms:\* when aws:PrincipalOrgID does not equal the organization ID and aws:PrincipalIsAWSService is false, and attach it to the organization root.

An RCP is a preventive, organization-wide ceiling on permissions for member-account resources, so it denies external principals even when a bucket policy or key policy grants them access. One RCP at the root covers all 300 current and future accounts, and the aws:PrincipalIsAWSService exception keeps service principals working.

**Summary:** RCPs set the maximum available permissions on resources in member accounts, regardless of who the calling principal is, so they block external principals even when a resource policy allows them. Attaching one RCP at the root covers every current and future account. The aws:PrincipalIsAWSService exception keeps AWS service principal access working.

❌ **B.** Create an organization-level IAM Access Analyzer external access analyzer and use Amazon EventBridge to trigger a Lambda function that removes external grants.

Access Analyzer with EventBridge remediation is detective and reactive: the external grant is live until the finding appears and the Lambda removes it, so it is not preventive and adds custom code to maintain.

❌ **C.** Create a service control policy (SCP) with the same deny and conditions, and attach it to the organization root.

SCPs restrict only principals in the organization's member accounts, so they cannot stop an external account's principals from using a permissive resource policy.

❌ **D.** Deploy an AWS Config conformance pack with S3 and KMS policy rules and automatic remediation through Systems Manager Automation.

Config rules evaluate after the change is made, so they are not preventive and require ongoing remediation management.

</details>

### Question 8 – RCP evaluation

A security team attaches the resource control policy (RCP) below to the root of its organization. The default RCPFullAWSAccess policy remains attached at every level. Which statement correctly describes the effect of this RCP?

```json
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "*",
      "Condition": {
        "BoolIfExists": { "aws:SecureTransport": "false" }
      }
    }
  ]
}
```

- **B.** Requests made without TLS to S3 buckets in member accounts are denied, including requests from principals in external accounts, regardless of what the bucket policies allow.
- **C.** S3 buckets in the management account are also protected by this RCP.
- **D.** Only principals that belong to the organization are denied when they use HTTP; external principals are evaluated only against bucket policies.

<details>
<summary>Show answer and explanation</summary>

**Answer: B**

✅ **B.** Requests made without TLS to S3 buckets in member accounts are denied, including requests from principals in external accounts, regardless of what the bucket policies allow.

RCPs apply to requests against member-account resources no matter which account the caller belongs to, and RCPFullAWSAccess still allows everything else. The only effect is an explicit deny for S3 requests where aws:SecureTransport is false, which no bucket policy allow can override.

**Summary:** An RCP deny applies to requests against supported resources in member accounts regardless of which account the calling principal belongs to (service-linked roles are the exception). With RCPFullAWSAccess still attached, the only change is that requests where aws:SecureTransport is false are denied. RCPs, like SCPs, do not affect the management account and never grant permissions.

❌ **A.** Because the RCP contains no Allow statement, all S3 access in member accounts is blocked until an Allow RCP for HTTPS is added.

RCPFullAWSAccess remains attached, so only the explicit deny for non-TLS requests takes effect.

❌ **C.** S3 buckets in the management account are also protected by this RCP.

RCPs, like SCPs, do not apply to resources in the management account, so buckets there would still accept non-TLS requests unless their own bucket policies deny them.

❌ **D.** Only principals that belong to the organization are denied when they use HTTP; external principals are evaluated only against bucket policies.

That describes SCP behavior. An RCP is evaluated for the resource regardless of the caller's account, so external principals using HTTP are also denied.

</details>

### Question 9 – IAM Identity Center ABAC

<summary>Show answer and explanation</summary>

**Answer: C**

✅ **C.** Enable attributes for access control in IAM Identity Center and add a CostCenter key mapped to the user's costCenter attribute from the identity store.

❌ **D.** Edit the trust policy of each AWSReservedSSO role in the member accounts to add sts:TagSession.

Identity Center manages those roles, and the missing piece is attribute mapping, not trust policy edits.

</details>
