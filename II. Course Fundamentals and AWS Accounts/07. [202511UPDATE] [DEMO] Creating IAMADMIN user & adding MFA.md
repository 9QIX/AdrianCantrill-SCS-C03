# Creating a Privileged IAM User and Adding MFA

## Overview

This demonstration creates a privileged IAM user for a standalone training account, assigns administrator permissions, enables console access, and registers MFA. For production workforce access, federation through AWS IAM Identity Center and role-based temporary credentials is generally preferred over long-lived IAM users.

## Exam Alignment

- **Primary SCS-C03 Domain:** Identity and Access Management
- **Secondary Domain(s):** Security Foundations and Governance
- **Main AWS Services:** IAM, IAM Identity Center
- **Lesson Type:** Demonstration
- **Exam Importance:** High
- **Core Skill:** Configure and validate privileged non-root access while understanding the preferred federated alternative.

## Demonstration Goal

Stop routine root use by creating a named lab administrator protected by MFA.

## Prerequisites

- Root or delegated authorization to manage IAM users, policies, aliases, and MFA devices.
- A supported MFA device.
- A standalone lab context where an IAM user is intentionally required.

## Demonstration Steps

1. In IAM, optionally create an account alias to make the account-specific IAM sign-in URL recognizable.
2. Create `iamadmin` with console access and a strong initial password.
3. Attach `AdministratorAccess` only because this is the designated lab administrator; broad permissions are inappropriate for ordinary identities.
4. Register an MFA device for `iamadmin` and complete code verification.
5. Sign out of root and use the IAM sign-in URL, account alias or ID, username, password, and MFA response.
6. Test required administrative access, then monitor and review use of this privileged identity.

## Validation

- The IAM user signs in only with the expected password and MFA factor.
- The user can perform intended lab administration.
- Root is no longer used for routine tasks.
- CloudTrail attributes actions to the IAM principal.

## Policy or Permission Analysis

`AdministratorAccess` broadly allows AWS service actions but remains subject to explicit denies, resource policies, SCPs, permission boundaries, and service-specific authorization such as KMS key policies. MFA authenticates the user; it does not narrow this policy.

## Pitfalls and Misconfigurations

- Directly attaching broad policies makes review and lifecycle management harder than governed group, permission-set, or role patterns.
- An account alias is not a security secret.
- Console MFA does not remove risks from any access keys later created for the same user.
- Keeping both root and privileged IAM sessions active increases the chance of acting as the wrong principal.

## What the Demonstration Proves

A named, MFA-protected identity is safer and more attributable than routine root use, but federation with temporary credentials is the preferred enterprise workforce model.

## Memory Hooks

> **Root for root-only tasks; federation for people; roles for temporary authority.**

## Quick Review

- Use this IAM-user pattern only where intentionally required.
- Protect privileged human access with MFA.
- Administrator access remains subject to explicit denies and guardrails.
- Prefer IAM Identity Center for workforce access.
- Use CloudTrail for attribution and monitoring.

## Self-Check Questions

1. Can `AdministratorAccess` override an SCP deny?

<details><summary>Answer</summary>

No. An applicable explicit deny overrides the identity-policy allow.

</details>
