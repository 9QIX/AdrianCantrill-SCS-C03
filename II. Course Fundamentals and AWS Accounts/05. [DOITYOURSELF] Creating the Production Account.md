# Creating a Separate Production AWS Account

## Overview

This exercise creates a second account for production when the learner's plan and lab design permit it. The security purpose is workload isolation: a production account has a separate root user, IAM boundary, resource ownership, quotas, and blast radius.

## Exam Alignment

- **Primary SCS-C03 Domain:** Security Foundations and Governance
- **Secondary Domain(s):** Identity and Access Management
- **Main AWS Services:** AWS Organizations, IAM
- **Lesson Type:** Demonstration
- **Exam Importance:** Medium
- **Core Skill:** Establish a distinct production security boundary and harden its initial access.

## Demonstration Goal

Create and secure a production account without weakening ownership or recovery controls.

## Prerequisites

- An account plan and lab design that support an additional account.
- A unique, secured root email address.
- An MFA device and documented account owner.
- Authorization to accept AWS terms and potential charges.

## Demonstration Steps

1. If an additional account is unavailable or unnecessary, retain the single lab account and clearly separate exercises from real production.
2. Otherwise, create the production account with a unique organization-controlled root email.
3. Register MFA for the production root user and ensure no root access key exists.
4. Configure account contacts, billing visibility, logging, and approved administrator access.
5. If using AWS Organizations, place the account in the intended organizational unit and validate applicable guardrails.

## Validation

- Production has a distinct account ID and root identity.
- Root MFA and recovery details are correct.
- Administrative access works without routine root use.
- Expected organization policies apply to the account.
- No real production data is introduced into an unmanaged training account.

## Common Exam Traps

- Separate accounts improve isolation but do not automatically establish centralized logging or least privilege.
- An SCP restricts maximum permissions; it does not grant administrator access.
- Reusing a root email or MFA recovery channel carelessly creates ownership risk.

## What the Demonstration Proves

Account boundaries can separate environments and reduce blast radius, but every new account must receive baseline identity, logging, billing, and governance controls.

## Quick Review

- A second account is optional for this lab.
- Production isolation is stronger than naming resources “production.”
- Harden every account root user.
- Apply central logging and guardrails deliberately.
- Keep training and real production data separate.

## Self-Check Questions

1. Does placing an account in a production OU grant users production permissions?

<details><summary>Answer</summary>

No. Organizational placement can apply guardrails; permissions still require applicable IAM or resource-policy allows.

</details>
