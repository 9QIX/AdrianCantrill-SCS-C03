# Creating and Initially Securing an AWS Account

## Overview

This demonstration creates an AWS account and identifies the immediate controls required before workload use. AWS plan names, credits, and signup screens can change; the enduring security objective is to establish protected ownership, recovery, billing, and root-user authentication.

## Exam Alignment

- **Primary SCS-C03 Domain:** Security Foundations and Governance
- **Secondary Domain(s):** Identity and Access Management
- **Main AWS Services:** AWS account management, AWS Billing, IAM
- **Lesson Type:** Demonstration
- **Exam Importance:** Supporting
- **Core Skill:** Create an account with protected ownership information and prepare it for secure administration.

## Demonstration Goal

Create a functional AWS account, verify its owner, and prepare to harden the root user.

## Prerequisites

- A unique, secured email address the organization controls.
- A strong unique password and a supported MFA device.
- Valid contact, identity-verification, and payment information as AWS requests.
- An approved account name, owner, environment classification, and cost owner.

## Demonstration Steps

1. Start from the official AWS signup page and enter the unique root email and account name.
2. Verify the email and set a unique root password.
3. Select an offered account plan appropriate to the intended services; promotional limits are not a security boundary.
4. Supply accurate contact and payment information and complete identity verification.
5. Select a support option if prompted and wait for account activation.
6. Sign in as root only to perform initial hardening: register MFA, verify alternate contacts, and configure secure administrative access.
7. Configure billing and security notifications before deploying resources.

## Validation

- Root sign-in succeeds only with the expected credentials and, after hardening, MFA.
- Account ID, name, contacts, and billing owner are recorded in the organization's inventory.
- No root access key exists.
- The intended administrative access path works without routine root use.

## What the Demonstration Proves

Account creation establishes ownership; it does not finish security configuration. Root hardening, governed administrator access, logging, budgets, and organization enrollment are separate controls.

## Pitfalls and Misconfigurations

- Using a personal or inaccessible email can undermine recovery and offboarding.
- Assuming free-plan or credit limits prevent every charge can create financial risk; verify current terms.
- Deploying workloads before logging and access controls are established creates evidence and governance gaps.

## Memory Hooks

### One-Line Memory Hook

> **Create, verify, harden, govern—then deploy.**

## Quick Review

- Use an organization-controlled root email.
- Register root MFA immediately.
- Do not create root access keys.
- Record ownership and contacts.
- Establish non-root administration and logging before workloads.

## Self-Check Questions

1. Does successful signup mean the account is securely configured?

<details><summary>Answer</summary>

No. Root MFA, contacts, non-root administration, logging, monitoring, and governance still require configuration.

</details>
