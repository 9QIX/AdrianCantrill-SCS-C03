# Multi-Factor Authentication in AWS

## Overview

Multi-factor authentication (MFA) requires more than one factor during authentication, reducing the value of a stolen password. It is essential for the account root user and privileged access, but it does not replace least privilege, credential monitoring, or secure recovery.

## Exam Alignment

- **Primary SCS-C03 Domain:** Identity and Access Management
- **Secondary Domain(s):** Security Foundations and Governance
- **Main AWS Services:** AWS Identity and Access Management (IAM), AWS IAM Identity Center
- **Lesson Type:** Concept
- **Exam Importance:** High
- **Core Skill:** Select and enforce MFA for human authentication and sensitive API operations.

## Core Concepts

- Factors include something known, possessed, or inherent. Two passwords are not two factors.
- AWS supports MFA options for root and IAM users; federated identity providers can enforce MFA before role federation.
- Policies can test MFA context, commonly with `aws:MultiFactorAuthPresent`, but applicability varies by credential path.
- Temporary credentials obtained after MFA can carry MFA context; long-term access keys do not prompt interactively for MFA.
- MFA protects authentication. Authorization policies still determine allowed actions.

## How It Works

```text
User -> password/federation + MFA -> authenticated session
     -> IAM policy evaluation -> allowed or denied AWS action
```

## Security Best Practices

- Register phishing-resistant MFA where supported and operationally appropriate.
- Require MFA for root and privileged human identities.
- Protect device recovery and maintain tested account-recovery procedures.
- Prefer federation and short-lived role sessions over IAM-user credentials.
- Alert on root-user activity and MFA device changes.

## Common Exam Traps

- MFA does not grant permissions.
- MFA on console sign-in does not automatically protect every pre-existing access key workflow.
- A condition that checks `aws:MultiFactorAuthPresent` must be designed carefully for long-term credentials and service calls.
- MFA cannot compensate for an overly broad role or resource policy.

## Memory Hooks

### One-Line Memory Hook

> **MFA strengthens proof of identity; policies still decide authority.**

## Key Terms and Definitions

| Term | Definition | Exam Relevance |
| --- | --- | --- |
| MFA | Authentication using factors from more than one category | Reduces password-only compromise risk |
| TOTP | Time-based one-time password | Common authenticator-app factor |
| MFA context | Session information indicating MFA use | Can be evaluated in policy conditions |

## Quick Review

- Enable MFA for root and privileged users.
- Prefer temporary credentials for workloads and people.
- Authentication and authorization are separate.
- Protect enrollment and recovery workflows.
- Monitor MFA changes and root activity.

## Self-Check Questions

1. Does MFA allow an otherwise unauthorized API action?

<details><summary>Answer</summary>

No. MFA establishes stronger authentication; an applicable authorization allow is still required and explicit deny still wins.

</details>

2. Why are long-term access keys a concern even if console MFA is enabled?

<details><summary>Answer</summary>

They can be used programmatically without an interactive MFA prompt unless a deliberately designed policy and session workflow requires MFA-backed temporary credentials.

</details>
