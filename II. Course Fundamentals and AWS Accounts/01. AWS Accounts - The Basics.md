# AWS Accounts: Security Boundaries and Fundamentals

## Overview

An AWS account is a billing, ownership, quota, and security isolation boundary. Account separation is a primary method for limiting blast radius, delegating administration, and separating production from non-production workloads.

## Exam Alignment

- **Primary SCS-C03 Domain:** Security Foundations and Governance
- **Secondary Domain(s):** Identity and Access Management
- **Main AWS Services:** AWS Organizations, AWS Identity and Access Management (IAM), AWS Billing
- **Lesson Type:** Concept
- **Exam Importance:** High
- **Core Skill:** Use accounts as governance and isolation boundaries while protecting root-user access.

## Core Concepts

- Each account has a unique account ID, a root user, independent IAM configuration, service quotas, and resource ownership.
- The account root user is created with the account and has unrestricted account-level authority. It is not an IAM user.
- Use the root user only for tasks that require it; protect it with multi-factor authentication (MFA), avoid root access keys, and secure its email and recovery channels.
- IAM identities are account-scoped. Cross-account access normally uses roles and AWS Security Token Service (AWS STS) temporary credentials.
- AWS Organizations groups accounts, enables consolidated billing, and applies governance policies. It does not merge accounts or their resources.

## Architecture and Service Relationships

```text
AWS Organization
  |-- Management account
  |-- Security / log archive accounts
  |-- Production accounts
  `-- Development accounts
```

Account boundaries reduce the impact of compromised credentials or a mistaken deployment. Organizational policies add centralized guardrails, while IAM policies still determine permissions inside each account.

## Security Best Practices

- Use multiple accounts where workload isolation, ownership, compliance, or recovery requirements differ.
- Centralize workforce access with federation and temporary credentials.
- Monitor root-user activity and account-contact changes with CloudTrail-backed alerting.
- Keep billing, security, and operations contacts current and use protected distribution addresses where appropriate.

## Common Exam Traps

- The management account is not affected by service control policies (SCPs); minimize workloads and access there.
- Consolidated billing does not grant member accounts access to one another.
- Account separation complements—not replaces—least privilege.
- A role's trust policy controls who may assume it; its permissions policies control what the session may do.

## Memory Hooks

### One-Line Memory Hook

> **Accounts isolate; Organizations govern; IAM authorizes.**

## Key Terms and Definitions

| Term | Definition | Exam Relevance |
| --- | --- | --- |
| Root user | Identity created with and owning the account | Protect strongly and reserve for root-only tasks |
| Account boundary | Isolation boundary for resources, identities, billing, and quotas | Reduces blast radius |
| Member account | Account joined to an organization | Can receive organization guardrails |

## Quick Review

- An AWS account is a strong security and ownership boundary.
- Root is distinct from IAM and has exceptional authority.
- Prefer federated roles and temporary credentials.
- Use AWS Organizations for multi-account governance.
- Keep workloads out of the management account where practical.
- Cross-account access must be explicitly authorized.

## Self-Check Questions

1. Does consolidated billing provide cross-account resource access?

<details><summary>Answer</summary>

No. Access still requires appropriate identity, resource, trust, and guardrail policies.

</details>

2. Why use separate production and development accounts?

<details><summary>Answer</summary>

They provide stronger isolation, separate quotas and administration, and reduced blast radius.

</details>
